> device 省了而 e2e 没省），或采集结果要**作为交付件交出去 / 交给下游分析**时。
> 只要"算子级形态普查"（哪族算子占多少）且不出拆分结论的，读 SKILL.md 正文与
> `profile-dir-isolation.md` 即可，不必读本文件。

> 本文件只写**判据 / 契约 / 流程**；实测读数与来源环境按数字纪律出库（见 §7 归档指针）。

## 1. 交付件标准集：一次"特性收益"分析至少三档

### 1.1 三档（缺一档则收益不可归因）

| 档 | 定义 | 为什么要它 |
|---|---|---|
| **带特性档** | 该特性开启（ON 臂） | 收益的分子 |
| **不带该特性档** | **同树、同脚本、同请求**，只关掉该特性（OFF 臂） | 收益的分母；**不同窗、不同脚本的读数不得相减** |
| **换精度档** | 仅当该特性涉及**精度变化或权重形态变化**时（如换 dtype、换量化形态、适配器合并/移除） | 把"精度/格式代价"与"特性本身收益"分开算——否则两者会在同一个差值里互相抵消，得出"该特性没收益"的假结论 |

三档必须**同一采集 hook、同一导出方式、同一请求形态**（同一调用序号、同一 elected worker、同一
level 与 `aic-metrics` 档）；任一项不同即三档不可比，须重采。

### 1.2 每档必备的交付件（契约）

| 文件 | 地位 | 说明 |
|---|---|---|
| `trace_view.json` | **必备** | 时间线（Chrome trace 事件数组）；缺它 = 交付未完成 |
| `kernel_details.csv` | **必备** | 逐 kernel 明细（重复列名以外的字段按 `op_summary_*.csv` 一致） |
| `op_statistic.csv` | 附带 | 按 OP Type 聚合（**只有聚合表不算交付完成**） |
| `api_statistic.csv` | 附带 | host 侧 API 族 |
| `step_trace_time.csv` | 附带 | step 级汇总（Computing / Comm / Free / Stage）——**属被采集放大的窗口，见 §5** |
| `communication.json` | 有通信时附带 | 通信算子详情；无通信可缺 |

- **落位**：一档一目录，目录名从名字能反推档身份（`{run_results_dir}/…/profile/{档名}/`，
  内含 `ASCEND_PROFILER_OUTPUT/`）；命名与并行隔离纪律见 `profile-dir-isolation.md`。
- **交付清单**：每档写明**每个文件的大小 + 摘要（md5/sha256）+ 它属于哪个 step**
  （第几次被采集的调用、哪个 rank、窗口 span）。缺任一字段即视为该文件未交付。
- **逐档过门禁**：`python scripts/check_output.py --dir {档}/ASCEND_PROFILER_OUTPUT --start-marker <运行开始标记>`
  （六项检查、退出码三态；`3`＝无法判定，**不得当通过**）。

## 2. 导出流程判据：raw dump → `ASCEND_PROFILER_OUTPUT/`

**流程**：profiler 在设备上先落 **raw dump**（目录名以 `_ascend_pt` 结尾）→ 再用**离线导出入口**
把它解释成 `ASCEND_PROFILER_OUTPUT/`：

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
python -c "from torch_npu.profiler.profiler import analyse; analyse('<raw>_ascend_pt', max_process_number=8)"
ls -la <raw>_ascend_pt/ASCEND_PROFILER_OUTPUT/   # 必须看到 trace_view.json + kernel_details.csv
```

**要点（陷阱）**：**有些臂脚本以强杀结束进程**（收尾 `pkill -9` / 被判定失败后失手杀掉），
于是 torch_npu 的**退出期导出**（`tensorboard_trace_handler` 挂在进程退出路径上）**永不执行**
⇒ 磁盘上只剩 raw dump（外加 `msprof --export=on` 的 MindStudio 布局，而它**不含**上表两件必备文件）。
⇒ **导出必须由外层显式调用**，不能指望采集进程"结束时自己落盘"。

**如何判定导出确实发生**（唯一判据）：`ASCEND_PROFILER_OUTPUT/` 下存在**本次采集之后生成**的
`trace_view.json` 与 `kernel_details.csv`，且行数 > 0。
**不得**以日志里的 `done` / `OK` / 退出码 0 为准（同类静默失败见 SKILL「导出类操作一律
『无新文件即失败』」）。导出必须在**独立进程**里做：在采集进程内调 `analyse()` 会被装饰器吞掉
异常、什么都不写。

**零卡耗优先**：对**已存在**的 raw dump 做离线导出不碰设备 ⇒ 需要 trace 时**先复用已有 dump**，
不要为了一次导出重跑一整轮 A/B。

## 3. 端到端拆分仪器与闭包对账

### 3.1 取数字段（管线 profiler 阶段统计，契约）

| 字段 | 覆盖 |
|---|---|
| `forward_time_s` | 管线一层 `forward`：提示编码 + 去噪 + 解码 + 管线内胶水 |
| `diffusion_engine_exec_time_s` | 扩散引擎执行段（即 DiT 去噪段） |
| `denoise_step_latency_ms` | 单个去噪步延迟（× 步数 ≈ 去噪段；**步级口径，见 §5**） |
| `serving_time_to_first_output_ms` | 首输出时间（含排队 / 权重加载等前置） |
| `stage_gen_time_ms` | 服务端阶段总时长：请求进入 → 最后输出交付 |

外加两个独立来源：**各 rank 的解码阶段计时行**（用于把 `decode` 段拆成视频/音频子项）与
**请求墙钟**（HTTP 客户端测得的总时长，如 `curl` 的 total）。

### 3.2 闭包关系（三层，逐层对账）

```text
forward_time_s         ≈  encode_prompt + diffusion_engine_exec_time_s + decode + 管线内胶水
stage_gen_time_ms      ≳  forward_time_s + 阶段间 / API 胶水
请求墙钟（HTTP 总时长） =  stage_gen_time_ms + 产物封装（mux/编码）+ HTTP 传输与后处理
```

### 3.3 各段之和与墙钟对不上时怎么定位

1. **先核对口径，再谈差值**：两侧是否**同一请求**（冷/热）、同一计时域（服务端 vs 客户端）；
   日志取数先确认"一个请求占几行"（多 rank 会每 rank 一行），否则会把冷请求或别的 rank 当成当前值
   —— 取数纪律单点在 `../../perf-gate/references/evidence-toolbox.md` §4.1。
2. **差值为正且集中在末段** ⇒ 归 **HTTP 封装 / 传输 / 后处理**：用"服务端最后输出时刻"与
   "客户端请求结束时刻"夹逼，把该窗口内的步骤逐个点名（落盘 mux、编码、响应体大小与链路速率）。
   报表里这几个百分点**要单列**，不要混进 DiT 段——交付强制的封装开销不是优化空间。
3. **解码段**用各 rank 的计时行分配子项，但**不要把多 rank 的行相加**当请求耗时（并行/重复执行会重复计数）。
4. **差值为负、或阶段间空隙突然放大数倍** ⇒ 先怀疑**跨窗口拼接**或**同卡并发**（同一批卡上还有第二个
   服务在跑时，阶段间空隙会成倍放大）⇒ 该请求的墙钟不可引用，只能引用其
   `diffusion_engine_exec_time_s`；两服务并发的识别与资源独占预检见
   `../../remote-access/references/arm-driver-traps.md` §5.3/§5.4。

## 4. 量级判据：收益只能来自 DiT 段

- **DiT 去噪段是端到端主体**：占请求墙钟 **85–95%** 量级（区间随步数、精度形态与适配器形态移动）。
- **其余合计只占小头**：解码（视频 + 音频）+ 提示编码 + 管线/API 胶水 + 封装与 HTTP 传输
  合计约 **5–10%**，其中封装/传输本身可占 4% 上下。
- ⇒ **端到端优化优先看 DiT 段**：非 DiT 段的天花板被这个占比钉死——把整个非 DiT 段砍半也只值几个
  百分点，故"声称 e2e −X%"的单点若改动只落在非 DiT 段，先按占比算天花板再判（上限提升 ≠ e2e 变快，
  口径见 `../../perf-gate/references/measurement-discipline.md` §10）。
- ⇒ **同族推论**：某特性"device 侧省了、e2e 没省"时，先看它的收益是否全部落在被采集放大的步级口径上
  （§5），以及是否被同档的**格式代价**抵消（§1.1 换精度档）。
- ⚠️ **占比不是常量**：它随步数、分辨率、精度、拓扑与适配器形态移动。**换组合必须重测**，方法即 §3
  的闭包账（一次热请求即可）；本组合观测到的占比读数见 §7 归档指针。

## 5. 「采集单步 ≠ wall 均值」

- **事实**：采样窗口内的**单步耗时被采集本身放大**（dump/落盘落在计时窗口内），`step_trace_time.csv`
  的 step 汇总同属该窗口 ⇒ 这些读数**不是**该配置的性能。
- **规则**：
  1. **性能结论只引 wall**（同窗 A/B 的请求墙钟，或服务端阶段账口径）；
  2. 单步数据只用于**算子普查**（算子族、实例数、dtype、利用率档）与**相对归因**
     （哪族算子被增删、增删比例——比值可用，绝对值不可用）；
  3. 被采样的那个请求的 e2e **不计入均值**（与 perf-gate 同口径）。
- **如何判定采集是否污染结论**（复核方法）：**同配置、同脚本、同请求数**各跑一次"开采集"与"关采集"，
  比 wall 与阶段账。若"开采集"那次明显更长 ⇒ 该次的设备侧单步读数只能做相对归因；
  两者落在噪声内才可当量级参照。**换框架 / 换采集档 / 换 level 后必须重做**（采集开销随档位变化）。
- **不受污染的部分**：算子**形态**与**组成**（谁被融合掉、谁被新增）在单步里就成立；kernel diff 用单步
  数据即可（见 SKILL「少步快速采集经验」）。

## 6. 两条采集陷阱（判定 + 复核；流程单点在 remote-access）

### 6.1 采集臂不回收服务 ⇒ 残留 worker 长占卡 ⇒ 下一次采集 OOM

- **现象**：上一条采集/服务臂结束后**没有回收**（脚本异常退出、被强杀、或只杀了父进程），
  worker 仍持有设备内存；下一条**重负载**采集在**模型初始化 / 权重加载阶段**就 OOM，
  而它的代码与上一条成功臂完全相同 ⇒ **先查残留，不要先怀疑"优化吃爆显存"**。
- **判定**：`npu-smi info` 的**进程表**（每卡持有者 pid + 占用）+ `npu-smi info -t memory` / `-t usages`
  看到与本轮端口/标签对应的**非当前臂**进程与高占用；进程名 grep 不是判据（见
  `../../remote-access/references/arm-driver-traps.md` §5.4）。
- **复核（如何判定清理生效 / 该陷阱是否仍在）**：按**端口范围或进程组**精确清理后，
  设备进程表应为空；**确认设备无进程再启动下一条采集**。若某次收尾后进程表本来就为空，
  说明该脚本已自带收尾 ⇒ 删掉该臂的手工清理步骤，不要"以防万一"留着。
- **完整判定 / 清理 / 防误杀流程**（只清自己的端口/标签、父死子留、跨租户先上报）：
  单点在 `../../remote-access/references/arm-driver-traps.md` §9，本节不复述。

### 6.2 大体积 trace 直拉易超时（上百 MB 量级）

- **判定**：单文件到**上百 MB 量级**时，一条命令整体拉取会超时/断流，且有的工具会把"部分文件"
  当成功 ⇒ **判据是"本地落盘大小 / 摘要与源端一致"，不是传输工具的退出码**。
- **做法**：源端分片 → 逐片拉取（失败只重试该片）→ 本地**二进制**拼接 → 摘要与源端比对一致。
- **失败回退**：调小片长 / 逐片校验定位坏片；仍失败则**在源端减少产物**
  （只导出需要的单 step、只回传必备两件套），或先打包压缩再分片。
- 流程细节（分片命令、拼接模式、失败回退顺序）单点在
  `../../remote-access/references/arm-driver-traps.md` §10。

## 7. 归档指针与引用方

- **交付件坐标**：三档目录落 `{run_results_dir}/…/profile/{档名}/`（`ASCEND_PROFILER_OUTPUT/` 为档内根）；
  分析工具在 `{run_results_dir}/tools/` 下（算子普查 + 两档 pairwise `--diff`）。

  `{run_results_dir}/archive/`，**正文只留判据与流程**（本组合的逐档读数与三档交付清单见

## 8. 维护与更新

- **更新触发条件**：①交付件文件集或**必备两件套**变化（CANN / torch_npu 导出器改名或改布局）；
  ②离线导出入口（`analyse(...)` / `ParallelStrategy` 等签名）或"退出期导出"行为变化
  ⇒ §2 的判据与"外层显式导出"结论须重判；③管线 profiler 的**阶段字段名**变化（§3.1）；
  ④非 DiT 段占比量级变化（步数/分辨率/精度口径改口径时）；⑤采集开销档位变化（§5 复核必须重做）。
- **复核方法**：换框架 / 换版本 / 换采集档后，取**一次**采集按序自查——
  (a) 关掉"外层显式导出"，看 raw dump 是否仍被自动解释（若已自动完成，§2 的"必须显式"降级为提示）；
  (b) 同配置开/关采集各跑一次比 wall，确认 §5 的污染判定仍成立；
  (c) 任取一档核对必备两件套存在、行数 > 0、摘要与源端一致。
- **失效信号**：若某档交付件里 `trace_view.json` / `kernel_details.csv` 由**采集进程自身**稳定产出且带新
  时间戳，说明该链路的退出期导出已可靠 ⇒ 删除"必须外层显式导出"的强制措辞，只保留"如何判定导出发生"。
  若一次采集的墙钟与不采集同配置落在噪声内，§5 的"不得引单步"可降级为"优先引 wall"。
