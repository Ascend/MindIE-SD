# 远端「多臂驱动」陷阱（改一个开关，整轮 A/B 静默失效）

**加载时机**：写 / 跑**同一份代码、多个开关档位（arm）的远端对比批**时 —— 例如 env 开关、量化开关、
融合开关的 OFF/ON 对照。当出现"**四臂结果完全一样**"、"**结果好得不像话**"、
或"**跑完才发现跑的是旧代码**"时，先读本文件再怀疑算法。
**共用机器上还要在推送 / 启动 / 收尾脚本前读 §5**（两次现场事故：推送即执行、按类名全机清理）；
**臂异常结束 / 强杀之后、要起下一条重负载臂前读 §9**（残留 worker 占卡 ⇒ 下一条臂在加载阶段 OOM）；
**要回传上百 MB 级产物前读 §10**（直拉超时 ⇒ 分片 + 拼接 + 摘要校验）。

**一句话**：多臂对比里，**"臂没生效"不会报错**——它会伪装成"这个优化没用"或"这个优化完美"。
所以每一条臂都必须**自证生效**（见 §3），而不是靠"我传了环境变量"。

## 1. 环境块被 shell 字面量化（整轮跑成同一个配置）

- **症状**：四臂日志的产出一致到字节级；回看驱动日志才发现每条臂的 env 块里躺着一个**字面 `\n`**
  （两个字符），于是 `export A=1\n export B=2` 被当成**一个**变量名，两条 export 全部没设上，
  四臂实际跑的是**同一个默认配置** ✗。
- **成因**：把多行 env 块当**普通字符串**经多层 shell（PowerShell → ssh → `docker exec bash -lc`）传递，
  反斜杠转义在某一层被吞/被保留。与「内联 vs 脚本」是同一个根因（见 SKILL 正文「上传同步纪律」）。
- **处置（按此顺序）**：
  1. **在 Python 里构造** env 块并**逐行断言**：每行以 `export` + 一个空格开头、且**不含字面 `\n`**；
  2. 写进 `.sh` 上传（SFTP，CRLF→LF）后 `bash {file}`，而不是内联进 `docker exec` 的命令串；
  3. 每臂**开头** `env | grep -E '^(A|B)=' | sort` 把**实际生效值**打进该臂日志。
- **反面教训**：断言要**窄**。曾经用"整条命令里任何地方都不许出现字面 `\n`"的超广断言，
  把一条**本来正常**的臂判死并中断了整批 —— 断言只覆盖它要保护的那几行（`export` 行）。

## 2. "臂跑起来了"不等于"臂生效了"（回退式静默降级）

- **症状**：ON 臂的结果**与基线逐字节相同**，看着像"完美无回归"。
- **成因**：ON 臂的入口处有一个**宽泛的 `except`（如 `except ImportError`）**，真实原因是模块导入路径
  在包内调用下不成立，于是**静默回退到原路径**；它还把真实错误信息替换成了一个更迷惑的名字。
  记录里因此出现了成百上千行同一句噪音，而不是一次致命失败。
- **处置**：
  - **禁止宽泛 except 包住"选路径"的逻辑**；确实要回退时，**必须让回退可见**：回退即**打一次醒目日志**
    并**提高退出码或标记失败**，不许静默继续；
  - ON 臂加**一次性生效计数**（例如进到新路径时打印 `ENGAGED=<次数>`，只打第一次），
    日志里**必须 grep 到这个计数**才算 ON 臂有效；
  - 相对的，OFF 臂要用**缺席检查**：确认 `ENGAGED` **不出现**（否则 OFF 臂其实也走了新路径）。

## 3. 每条臂的"三件套"证据（缺一即该臂作废）

| # | 证据 | 取法 |
|---|---|---|
| 1 | **生效** | ON 臂日志出现一次性生效计数；OFF 臂该计数缺席 |
| 2 | **真跑了新代码** | 远端实际加载的文件 hash 与刚上传的一致（不是"我以为传上去了"） |
| 3 | **失败计数分开报** | 回退 / 异常 / 非法输入的计数**单独一行报出**，不与"生效"合并成一个"成功数" |

> 判据是**两个方向都要**：`md5 相同 ≠ 路径没跑`（可能跑了但真是等价），`md5 变化 ≠ 路径跑了`
> （可能是别的东西变了）。**只有生效计数 + 文件 hash 才能把它们分开**（口径见
> `../../perf-gate/references/measurement-discipline.md` §9）。

## 4. 顺序与窗口纪律（多臂批专用）

- **每条臂独立进程**：不许在同一进程里靠改环境变量"切臂"（Python 里 import 过的模块不会重载，
  环境变量也多半只在进程启动时读一次）→ 会把后几臂偷偷跑成第一臂的配置。
- **同窗口对比**：所有臂在同一登录会话 / 同一时间窗内跑，**不跨窗口拼表**
  （跨窗口的极差可达数个百分点，足以淹没要测的小收益，见 measurement-discipline §6）。
- **臂序无关性**：至少做一次**反序复跑**（ABBA），确认结论不随顺序漂移。
- **收尾释放**：结束用 `pkill -9 -f "[x]…"` 释放卡，模式首字符加 `[x]` 断字符是**必须**的
  （裸写 pattern 会匹配执行命令的 shell 自身）；释放后用 `npu-smi info` 复核进程为 0。
  详见 SKILL 正文「长任务三段式」与 `../../dev-workflow/references/rework-lessons.md`。

## 5. 共用机器的启动与收尾纪律（两次现场代价）

多 agent 共用一台机时，**「推送」与「清理」这两个"以为自己无害"的动作**最容易越界。两条各付过一次代价。

### 5.1 推送 ≠ 执行：推脚本的工具可能"推送即执行"

- **事实**：用推送工具把**自带默认参数**的臂脚本传上去（脚本默认就起一个 8 卡 serve），
  本意只是"放到远端"——结果**推送这一步就把它跑起来了**，与另一位 agent 正在跑的臂
  **并发抢同一批卡数分钟**，两边的窗口一起废掉（并发 serve 不会报错，只会两边都变慢）。
- **规则**：
  1. **推送与执行必须分两步**；推送完先 `echo` / `head` 确认落盘，**不在同一次调用里触发副作用**；
  2. 臂脚本必须**默认不自启**：没有显式 tag / port / 卡数参数就不动卡，或默认进 `--dry-run`；
  3. 推之前先读一遍被推脚本的**默认分支**——默认值就是"没人看着时它自己会做的事"。

### 5.2 清理必须"作用域内"：绝不用按类名全机匹配

- **事实**：`pkill -9 -f '<角色名>'` 这类**无锚点类名模式会匹配全机所有同类进程**，
  把另一位 agent 正在跑的臂的 worker 一并杀掉 ⇒ 那一臂作废（签名是**不对称**的：
  请求计数非 0，而进展类日志行数为 0）。**更糟的是这个坏模式还躺在既有驱动脚本的收尾行里**
  —— 它不是一次性失误，而是**会被复制的模板**。
- **规则**：
  1. **启动时就记下作用域**：让 serve 自立进程组（`setsid`）并记下 pid ⇒ 收尾 `kill -9 -<PGID>`，
     **只杀自己这一组**；
  2. 退而求其次用**端口限定**（例如 `pkill -f 'port <端口>'`）——**端口 / 卡组是本组的身份证，类名不是**；
  3. **永不**用类名 / 角色名（worker / engine / decoder / serve 之类的泛词）做无锚点 `pkill -f`；
     模式首字符加 `[x]` 断字符只解决"**自杀**"，**不解决"杀别人"**（两件事必须一起做）；
  4. 收尾后复核：进程数归零 + **自己这一组的日志不再增长**（别人的进程不归你复核，也别动）。

### 5.3 启动前自检资源独占（把"负对照"用在资源上）

- 启动前先查**是否已有别的 serve 存活**（进程 + 端口 + 卡占用）：有则**拒绝启动并打印它们的端口**，
  而不是"先跑起来再说"；并发 serve 不报错，只会让两边都变慢、两边数字都变垃圾。
- 这与 `../../perf-gate/references/measurement-discipline.md` §8 的负对照同源：
  **先证明环境干净，再相信读数**——环境不干净的窗口里，"差异"根本不可解释。

### 5.4 资源独占预检清单（**占用判据必须用设备管理接口**，不能用进程名 grep）

> 本节是本会话**最贵的一次误判**：用 `pgrep -f '<框架> serve'` 判"整机空闲"⇒ 通过；**真凶是另一个
> 容器里的 `serve`（名字不同 ⇒ 匹配不到）**，而**容器 PID 命名空间让我们看不到它**（连
> `nsenter -t 1 … ps` 也只给残缺视图）⇒ 据两个错误前提**发出了两次 GO**，其中一次直接废掉一个窗口 ✗。

**判据（按权威性排序）**：

1. **设备管理接口 = 权威**：`npu-smi info` 的**进程表**（每卡的持有者 pid + 显存占用）+ `npu-smi info -t usages`
   —— 谁真的握着设备，这里一定看得见；
2. **主机侧进程表 = 交叉核对**（不是判据本身）：用于把 pid 认到某个进程 / 容器；
3. **进程名 grep = 辅助线索，永不作唯一判据** ✗：**无人占用 ≠ 没有匹配的进程名**，
   也**不**等于"我可以起臂"。

**可见性必须自证**（"我能不能看到别人的进程"）：先确认自己**在哪个命名空间**、能否看到宿主进程；
若答案是否定的，就**只能**依赖第 1 条，**不得**用"我没看到"推出"没有"。

**跨租户冲突的标准动作（三步 + 一条禁令）**：

| 步 | 做什么 |
|---|---|
| **上报** | 发现外部作业占卡：**先上报让人决定**，**不得**单方面去杀（这一条子 agent 做对了） |
| **验身份** | 授权后**先守卫校验**：读 `/proc/<pid>/cmdline` 等确认**确实是那个作业**（例如必须含约定的端口参数），不匹配就**拒绝执行**并返回错误码 |
| **限作用域** | 按**进程组**杀（启动时 `setsid` + 记 PGID ⇒ `kill -9 -<PGID>`），**不按进程名**；端口限定次之 |
| **复核残留** | 杀后复核：设备侧进程表归零 / 目标消失；注意**"父死子留"**（父进程消失但 worker 仍持设备） |

**报告纪律**：**没杀成不许写成"我们释放了它"** ✗ —— 本会话那次外部作业最终是**自己消失**的
（父进程还在、子进程带走了显存）；报告只能写"已上报 / 已授权 / 已按作用域尝试"，
**结果以设备侧复核为准**。

**元规则**：**收尾动作的作用域，要和启动动作的作用域一样被审查。**
我们习惯审查启动（资源、配额、并发），却默认收尾是安全的——本节事故都出在
「推送」「清理」「判空闲」这些"以为自己无害"的动作上（复盘清单已登记，见 `dev-workflow/SKILL.md` §6.3）。

## 6. 反模式

- 用"我传了开关"当生效证据；
- ON 臂结果与基线一致就宣布"无回归"（先过 §3 三件套）；
- 把宽泛 `except` 当工程稳妥（它把"配置错了"变成"结果对了"）；
- 多臂共享同一输出目录 / 同一日志文件（分不清哪行属于哪臂）；
- 跑完整批才第一次打开某条臂的日志（应在**每条臂结束时**就检查三件套，坏臂早点重跑）；
- 把"推脚本"当成无副作用动作（工具可能**推送即执行**，见 §5.1）；
- 收尾用类名 / 角色名全机 `pkill`（跨越 agent 边界，见 §5.2）；
- 因为"并发 serve 不报错"就先跑起来再说（见 §5.3）；
- 用**进程名 grep** 当"整机空闲"判据（跨容器 / 跨命名空间看不到 ⇒ 假通过，见 §5.4）；
- 跨租户冲突时**单方面去杀**别人的作业（先上报；授权后也要先验身份、限作用域，见 §5.4）；
- 把"尝试清理"写成"已释放"（外部作业可能自己消失，父死子留也常见 —— 见 §5.4 报告纪律）。

## 7. 算子级 harness 不要依赖别的框架：本环境**根本没有** `vllm_ascend`

**现象**（实测，2026-09-19）：一个只测算子的 harness 报
`ModuleNotFoundError: No module named 'vllm_ascend'`，栈为
`vllm_omni/platforms/npu/ar_platform.py:20 -> from vllm_ascend.platform import NPUPlatform`。

**事实**（都已在机器上核对，不要凭印象回答）：

| 检查 | 结果 |
| --- | --- |
| `{生产同一解释器} -c "import vllm_ascend"`（在目标容器与目标 venv 内各测一次） | `ModuleNotFoundError` |
| 容器默认 `python3.12 -c "import vllm_ascend"` | `ModuleNotFoundError` |
| `grep -rn "import vllm" <mindiesd>` | **0 处** |

⇒ **`vllm_ascend` 本环境未安装**，MindIE-SD / mindiesd 也**从不**导入 `vllm` 或 `vllm_ascend`。
唯一的依赖来自「harness 导入了 `vllm_omni`，而它按 `VLLM_OMNI_DISABLE_VLLM_ASCEND` 的取值去选平台」：
该变量为 `true` 时走 `platforms/npu/dit_platform.py`，为假时才走会导入 `vllm_ascend` 的 `ar_platform.py`
（`platforms/__init__.py:99` 读该变量；生产臂脚本 `arm_best.sh:17` 正是 `export ... VLLM_OMNI_DISABLE_VLLM_ASCEND=true`）。

**正确做法，按优先级**：

1. **算子级 harness 不要导入 `vllm_omni`**。生产形状的张量直接构造即可（算子只吃张量）。少一个框架就是少一个失败面，
   也让"我测的是算子"这句话成立。
2. 确实需要 `vllm_omni`（例如要跑真实模型/权重加载）时：**照生产臂那样显式** `export VLLM_OMNI_DISABLE_VLLM_ASCEND=true`，
   并且**用与生产同一个解释器**（`{生产同一解释器}`；**不要用容器默认解释器**——两者 torch 版本可能不同），
   测出来的数不可用。
3. 不要试图 `pip install vllm_ascend` 去"修"它：本机没有该包，而正确路径是**根本不走那条分支**。

**归因纪律**：这类报错出现时，先分清是「解释器选错」「少了一个显式开关」还是「真缺依赖」——
三者现象相同、处置相反；用上表三条检查一次定死，不要靠猜。

## 8. 部分回滚陷阱：改 N 个文件、只回滚一部分 ⇒ 未验证的混合态

**事故（2026-09-19，代价约两轮排查 + 一次错误基线）。** 一次"生产者按 chunk 流水"的实验改了 4 个文件
（`prodcons.py` / `h3_vq_twopass.py` / `rf_v2.py` / `_comm.py`），实验判定为负收益后**回滚只落到了
`rf_v2.py`**。此后线上一直是"**已回滚的入口 + 未回滚的 kernel 族**"这种从未验证过的组合，它的数值与
正典产物**不等**（帧级 10–11 dB ≈ 换种子量级），却**编译通过、运行无告警、速度还略快**——于是被当成
"优化空间"追了半轮，直到同工具两臂 profile 显示设备侧几乎相等（窗口差 0.06 %）才转向。

**判据**：一次实验性改动**只要跨文件**，就必须把它当成**一个原子变更集**：

| 步 | 要求 |
| --- | --- |
| 记录 | 改动集写成清单（文件 + md5），并在推送前**保存改动前的推送包**（`push_*.tgz` 就是本轮救命证据） |
| 回滚 | **整批回滚**，逐文件 md5 与"改动前"清单对齐；禁止"只回滚入口/只回滚一半" |
| 复核 | 回滚后**至少跑一条会产出可比产物的臂**，确认结果回到**参考值**（例如正典产物 md5），而不是"跑起来没报错" |
| 留痕 | 若确实要保留部分改动，必须**单独声明保留哪几个文件、为什么**，并把该组合当作**新状态**重新验证 |

**为什么危险**：这种混合态的**症状是"变快 + 数值不对"**，最容易被读成"优化有效"。凡是"加速但产物/数值
变了却没有等价性证据"的组合，先怀疑是不是残留态，而不是惊喜。

## 9. 残留占卡：臂结束后 worker 仍握设备内存 ⇒ 下一条重负载臂 OOM

**现象**：一条臂**异常结束 / 被强杀 / 只杀掉了父进程**之后，session 里那条残留的 worker 仍持有设备内存；
下一条**重负载**臂（起服务、加载权重、或做 profiling 采集）在**模型初始化 / 权重加载阶段**就
`torch.OutOfMemoryError: NPU out of memory`。此时**先查残留，不要先怀疑"这条臂的优化吃爆了显存"** ✗
—— 同一个 `__init__` 在上一轮同样的臂里是跑得起来的。

**判定方法（如何判定它仍存在）**：

1. **设备管理接口 = 权威**：`npu-smi info` 的**进程表**（每卡持有者 pid + 设备内存占用）+
   `npu-smi info -t memory` / `-t usages`；**进程名 grep 不是判据**（跨容器 / 跨 PID 命名空间看不到，见 §5.4）；
2. **认身份**：残留进程的 pid / 端口 / tag 是否属于**本组**（本组自己启动时记下的端口段 / PGID / tag），
   还是别人的作业 —— 两者处置相反（别人的：**先上报**，见 §5.4）；
3. **形态判据**：设备侧有占用，而**本组当前没有任何一条臂在跑**（自己的日志不再增长、自己的端口无响应）
   ⇒ 是残留；若自己的臂还在跑，占用就是它自己的，不是残留。

**复核方法（清理是否生效）**：按**端口范围 / PGID / tag** 精确清理之后，**先复核设备侧归零、再启动下一条**
——「清理完 → `npu-smi info` 进程表为空（或只剩别人的、与本次无关的进程）→ 才允许起重负载臂」。
**父死子留**是常态（父进程消失、worker 仍持设备），故复核必须看**设备侧**，不能看"我杀的那个 pid 还在不在"。

**清理/绕行（作用域内，规则单点在 §5.2）**：

| 步 | 做法 |
|---|---|
| 限作用域 | 启动时 `setsid` + 记 PGID ⇒ 收尾 `kill -9 -<PGID>`；退一步用**端口限定**（`pkill -9 -f 'port <端口>'`）或 tag；**永不用类名 / 角色名**做无锚点 `pkill -f`（会杀掉别人的臂） |
| 不误杀 | **只清自己的端口 / 标签**；模式首字符加 `[x]` 只防"自杀"，**不防"杀别人"**，两件事要一起做；身份不匹配就拒绝执行 |
| 兜底 | 让臂脚本**收尾自带释放 + 自证**（释放后打印设备侧复核结果），把"手工清理"降级为异常路径 |

**作用域与归档指针**：残留的进程数 / 每卡占用 / OOM 时的 allocated 与 capacity 属**单案例读数**，
按数字纪律出库到会话产物归档 `{run_results_dir}/archive/`（本条的触发实例见会话证据账本的
profiling 交付件轮次，其**判据**即本节三条，**数值不回填**）。

**如何判定该陷阱已不在本环境**（防固化）：跑完一条臂后**立即**查设备进程表 ——
若**每次都空**，说明该臂脚本已自带收尾 ⇒ 删掉人工清理步骤，不要"以防万一"留着；
若只在**强杀 / 异常退出**后才非空，则本陷阱仍存在（正常退出路径不必加清理，异常路径必须加）。
**设备管理接口与进程模型变化（换容器运行时、换命名空间可见性）后逐条复核本节的判定顺序。**

## 10. 大文件传输：上百 MB 的产物直拉会超时 ⇒ 源端分片 + 拼接 + 摘要校验

**现象**：profiling / 产物回传时，单个文件到**上百 MB 量级**（一个 step 的 trace 常见量级），
一条命令整体拉取会**超时或半途断流**；重试仍失败；更糟的是**有的传输工具会把"拉了一部分"当成功**
（本地只落了半个文件，而退出码是 0）⇒ 下游解析出一个截断的产物，或报"文件损坏"却查不出原因。

**判定方法**：

1. **量两边**：源端大小（`ls -l` / `stat -c %s`）与本地落盘大小对比；**不一致 = 传输未完成**，
   不看传输工具的退出码与进度输出 ✗（与 §3「新文件才算证据」同源：**产物侧的事实优先于工具的自述**）；
2. **量摘要**：源端与本地各算一次摘要（md5 / sha256）比对；这是"传完了"的最终判据；
3. **预判**：单文件超过"本地工具能在其超时内拉完"的量级就直接走分片，不要先试直拉再补救。

**做法（分片 → 逐片拉 → 二进制拼接 → 校验）**：

| 步 | 动作 | 要点 |
|---|---|---|
| 分片 | 源端 `split -b <片长> -d <file> <前缀>_part` | 片长取"单次传输能在超时内完成"的量级（几十 MB 档先试，失败再调小） |
| 拉取 | 逐片单独传输 | **每片独立一次调用** ⇒ 失败只重试该片，不必重传整档 |
| 拼接 | 本地按片名序**二进制**拼接 | `cat <前缀>_part* > <file>`；**Windows 侧必须二进制模式**（`copy /b`、或 Python 以 `rb`/`wb` 读写）——文本模式会改换行、size 变，**摘要必然对不上** |
| 校验 | 本地与源端摘要比对 | 一致才算完成；写进交付清单（大小 + 摘要 + 属于哪个 step / 哪个 rank） |

**失败回退（按序）**：

1. 某片反复失败 ⇒ **调小片长**，或**逐片各带摘要**定位坏片（只重传坏片）；
2. 仍失败 ⇒ 换通道：先在源端打包压缩再分片（压缩率对 trace/CSV 通常可观），或改从**另一个可达路径**取；
3. 仍失败 ⇒ **减少产物本身**：只导出/只回传需要的单 step 与必备文件，别为了一次交付硬传整档
   （最小代价采集与"先复用已有 dump"见 `../../profiling-collect/references/e2e-split-and-capture-traps.md` §2/§6.2）。

**作用域与归档指针**：片长、超时阈值与"多大算大"**取决于链路与工具超时，故不写死**（本文件不承载
具体数值）；本案例的文件量级与逐档清单见会话产物归档 `{run_results_dir}/archive/`。

**如何判定该陷阱仍存在（复核方法）**：任取一个上百 MB 级文件做**一次直拉试探**——
若能在工具超时内拉完且摘要一致，说明链路/工具已变好，本条可降级为"链路不稳时用"；
若仍超时或摘要不一致，则分片流程继续适用。**换了传输工具、增大了超时、或换了网络路径后都要重做这一次试探**，
不要凭"上次超时"永久绕行。

## 11. 写文件前**先测源文件的换行约定**（一次真实的损坏）

**判据**：把**交付的产物**写进工作树之前，**先量源文件自己的换行约定**（数 `\r\n`），
**再决定是否转换**。不要按"目标树是 CRLF"的假设，去转换一个**已经是 CRLF** 的产物。

**失效形态**：对已是 CRLF 的产物再做一次 LF→CRLF，会把每个 `\r` 翻倍 ⇒ 内容被破坏，
但**语法检查仍会通过**（本仓一次实例即如此，是"双归一化哈希往返"当场抓到的，
若只看 `py_compile` 就会把这个损坏放过去）。

**执行**：

1. 写入前打印源文件的 **raw md5** 与 **LF 归一化 md5**，与交付方给的两个哈希**同时**核对；
2. 能**逐字节复制**就不要做任何转换（`open(...,'rb').read()` → `open(...,'wb').write()`）；
3. 写完**再复核双归一化哈希** + 语法/结构检查；
4. 保留备份，文件名带上**写前哈希**，便于回退与对账；
5. **交付契约**：交付方应**同时给出 raw 与 LF 两个 md5**（本仓的算子补丁交付已按此执行）；
   只给一个哈希时，先问清它是哪一种，**不要猜**。

**复核方法**：任取一个"需要转换"的交付做一次往返——若 raw 与归一化哈希都能复现，
说明约定已明确；若只能复现其一，说明**约定本身没被写清**，应先补契约再写文件。

### 11.1 对拍/取证路径同样必须归一化行尾（2026-09-20 一次**假阳性告警**）

**判据**：凡"这是不是同一份文件"的判断（md5 对拍、`diff`、用 `git apply --reverse` 复现补丁基线），
**必须先声明并归一化行尾再比**。只比 raw md5，会把"同一文件不同行尾"读成"不同文件"。

**真实失效形态（本仓一次，代价是差点退回一个正确的补丁）**：用 `git apply --reverse` 复现某补丁的
基线时，Git 在 Windows 下按 `core.autocrlf` 把工作副本写成了 CRLF，而比较对象是 LF 版 ⇒ 得出
"两版相差 287/287 行、无共同上下文"的结论，并据此**发出"补丁基线不符、不得部署"的告警、写进总表**。
字节裁定后：两者的 **LF 归一化 md5 完全相同**，字节差 **恰好等于行数**（11,387 + 286 = 11,673）
⇒ **纯行尾假阳性，告警撤回**。若照告警执行，会退回一个本来正确的补丁并白费一轮返工。

**执行（对**对拍脚本自身**的要求）**：

1. 脚本内**先归一化再比**，并**同时打印 raw 与 LF 归一化两份哈希**——让行尾差异**可见**而不致命；
2. 调 `git apply` 一律带 `-c core.autocrlf=false`，并把工作副本先写成 LF；
3. 结论里必须给**两个数**：差多少**字节**、差多少**行**。**"字节差 == 行数"是行尾问题的特征签名**；
4. **禁止**只凭一个 raw md5 就下"这是两个不同文件"的结论，**尤其是下游要据此否决一个补丁时**：
   否决前必须做一次**归一化后**的复比，或直接比内容。

**失效信号**：diff 呈"整文件全变"（`added == removed == 行数 + 1`，**一处上下文行都没有**）
⇒ **先怀疑行尾，再怀疑内容**。本仓 `r4/l1_provenance.py` 已按本节修正：同一输入由 FAIL 变为 PASS。

## 12. 跨文件补丁的**接口一致性**：`py_compile` 与单卡都查不出（2026-09-20 现场）

**事故。** 一条"把 mask 构建挪到侧流、与设备 FA 重叠"的补丁改了**两个文件**：
`parallel/_comm.py`（transport，**调用点**）用关键字把侧流上建好的句柄传下去 ——
`consume(gi, rq, rk, rv, out_dst=…, prep=prep_h[gi])`；而 `parallel/mask/rf_v2.py`（consumer，
**被调方**）的闭包仍写作 `def consume(gi, rq, rk, rv, out_dst=None)` —— **没有 `prep` 形参**。
后果：多卡上**该分支的请求全部 HTTP 500**，`diffuse` 阶段耗时出现数量级异常（读数见会话产物归档）；serve log 只有一句真因。

```text
RuntimeError: <fn>.<locals>.consume() got an unexpected keyword argument 'prep'
```

**为什么三道常见防线全部漏掉**：

| 防线 | 为什么没用 |
|---|---|
| `py_compile` / 语法检查 | Python 的关键字不匹配是**运行期**错误，编译期完全合法 |
| 私有 harness / 单卡跑一遍 | 决定性证据来自一个**自建 harness**：它自己建侧流、自己实现各条臂，**从不调用被打补丁的调用点** ⇒ 只验证了机制、没验证集成。而**单卡 serving** 又被下游前置条件（`if st is None: prepare = None`）静默禁用 ⇒ 两条路都到不了调用点（详见 `../../perf-gate/references/measurement-discipline.md` §9.3） |
| 归档哈希对得上 | 归档的**正是这个坏形态** ⇒ 哈希一致只证明"没传错文件"，**不证明补丁能用**（与 §11 是姊妹条：§11 是"哈希对得上但内容坏了"，本条是"哈希对得上但跑不了"） |

**判据（跨文件补丁按原子变更集对待，并在推送前做接口对拍）**：

1. **签名对拍**（最省，工位内可做）：把**调用点传的关键字集合**与**被调函数的形参集合**做子集检查，
   不满足即 fail。改任何跨文件接口后**先跑这一条**，再谈上机。
   **机械出口（本技能自带，零依赖）**：
   `python scripts/patch_iface_check.py <调用点文件> <被调方文件> [--callee NAME] [--lines 379,386-388]`
   （单文件补丁可只给一个文件，脚本自动逐个函数交叉校验）。
   **它带负控**：`--selftest` 内建正控（不报）与负控（必报）；本仓用它对本条事故的**归档坏补丁**
   实测得到 `L379 / L386 -> MISMATCH ['prep']`、`error=2`（恰好那两个调用点），
   修复后的树 `error=0`。
2. **真实入口烟测**：用**能触发该分支的条件**（这里是"存在侧流"，即多卡）跑一次最小请求，
   断言**没有 `TypeError`**。**私有 harness 与单卡烟测都不构成**该分支的烟测——
   harness 自己实现调度（不走调用点），单卡被前置条件禁用（见 §12 表与 measurement-discipline §9.3）。
3. **与 §3 的"三件套"合并**：新增"**接口计数**"——ON 臂必须出现"新路径真正被调用"的计数；
   本例若早有该计数，单卡 ON 臂就会显示 `ENGAGED=0`，症状会当场暴露而不是留到八卡。
4. **归档清单**：跨文件补丁的归档必须**同时**记录（a）每个文件的 md5、（b）**调用点↔被调方的接口契约**
   （传了哪些关键字）、（c）**该分支的触发条件**（本例：需要侧流 ⇒ 必须多卡验证）。
   只记 md5 的归档无法回答"这个补丁在什么条件下才真的被执行"。

**失效信号**：若某次改动把跨文件调用改成**位置参数**或**单一数据结构**（不再用关键字），
第 1 条的检查形态要随之改写；若新路径改为**默认开**，第 2 条的触发条件也随之变化。

## 13. 门控补丁的**形状审计**：removed 行必须几乎全部重新出现

**问题**：一个"加开关、默认关、行为不变"的补丁，很容易在实现时顺手重写原有函数。
一旦重写，**默认路径的行为也变了**——收益归属不清、回归面变大，评审成本陡增。
diff 里"删了 53 行"这种数字本身看不出是"包了一层 if"还是"重写了逻辑"。

**判据（机械、可脚本化）**：把 diff 的**删除行**与其**新增行**都去掉空白后比对：

```text
# 对每个文件：removed_normalised - added_normalised 应为空集
# 非空 ⇒ 那些行在补丁后没有以同样内容再现 ⇒ 默认路径可能真的被改了，逐条人工看
```

**本仓实测（一个 11 文件、+415/−53 的门控补丁）**：**只有 5 行删除行未再现**，且逐条看全是
**文档字符串改写（2 行）+ 调用被换成多行/换分支写法（3 行）**，**没有任何逻辑删除**
⇒ 可以判定为"**纯包一层 `if`，默认路径逐行保留**"，评审面从 53 行收缩到 5 行。

**纪律**：

1. **先跑形状审计再逐行读 diff**：把评审注意力集中到那几行"未再现"的删除行；
2. 未再现行**必须逐条给出解释**（文档/格式/换分支）；给不出解释的，按"默认路径行为变更"对待，
   要么改回"只包一层"，要么补默认路径的等价性证据；
3. 与 §12 配套：§12 查**跨文件接口**（调用点关键字 ⊆ 被调方形参），本条查**默认路径是否被改**；
4. 归档时把该审计结果一起写进 patch 交付说明（"removed 53 / unmatched 5，逐条解释见…"）。

**失效信号**：若某后端/语言让 diff 无法按行比对（如格式化器全量重排），
本条退化为"必须提供默认路径的逐字节/逐位等价证据"，不能省略。

## 维护与更新

- **更新触发条件**：远端 shell 层次变化（新增一层包装 / 换登录方式）、
  `docker exec` 语义或 `MaxStartups` 行为变化、多臂批的驱动脚本重写时；
  以及**推送/执行工具的行为变化**（是否推送即执行）、容器进程模型变化（进程组 / `setsid` 是否可用）、
  **共用机器的多人约定变化**（谁在跑哪批卡）、**设备占用查询接口变化**（§9 的判定顺序依赖它）、
  **传输工具的超时与流式行为变化**（§10 的"直拉是否可行"随之改判）、
  **补丁的跨文件调用形态变化**（§12：回调改名、关键字改位置参数、或引入 `**kwargs` 之后，
  签名对拍的判定方式要随之改写）。
- **复核方法**：对每一个新写的多臂批驱动，先跑**一次只有两臂、其中一臂故意写错**的假批：
  确认（a）生效计数只在正确臂出现、（b）文件 hash 比对能发现"没传上去"、
  （c）坏臂会被判失败而不是静默降级。三项都过再跑真批。
  另加两项**作用域**复核：在只有自己的窗口里推一个"默认不自启"的脚本，确认推送后**进程数与卡占用不变**；
  对一个无关的假进程验证收尾**只杀本组**（按 PGID / 端口），不影响它。
- **失效信号**：若某条臂出现"**请求计数非 0 而进展类行数为 0**"这类**不对称**读数，
  先怀疑**资源被外部动过**（清理越界或他人抢占），该臂结论作废、重跑；
  若某条陷阱在环境变化后不再复现（如内联传参已验证安全），删除该条或降级为一句提示，不保留"以防万一"。
