## 1. 假数字：最大的风险不是测不准，是测错了还在报

**定义与判据单点在 `evidence-toolbox.md` §1**（返回码 + 产物字节数 + 成功日志条数，三缺一即作废）。
本节只留并行场景特有的一条提醒：

**“漂亮数字”在并行改动上格外容易出现假象**：失败运行**返回得更快**，而并行改动本来就以“更快”为
预期，于是失败读数会被读成“分片生效了”。实践中同一个漂亮的耗时下降曾**两次**都来自失败运行
（全部 `http=500`、产物只有 KB 级）。⇒ 报任何“并行改动有收益”之前，先过 `evidence-toolbox.md` §1。

## 2. 交错对照（ABBA）与“哨兵翻转”

当效应量接近噪声时，顺序执行两个配置的 A/B 会被热漂移污染（共享机器上十几秒量级的长任务，漂移可达百分之几）。

**做法**：

- 在**同一个服务进程内**交替请求两个配置（ABBA 顺序），让两个配置经历同样的热状态；
- 用一个**哨兵文件**在请求之间翻转模式；程序每次调用都重新读该文件（而不是只在启动时读一次）
  —— 这是“门控可逐请求翻转”的实现形态（门控纪律见 `../SKILL.md`「门控纪律」）；
- 报告**每块的差值符号**，而不只是总均值 —— 一致同号的块数比均值更有说服力。

**判读**：

- 4/4 块同号 → 效应可信；
- 符号翻转 → **效应未解析**，不要报“有收益”或“没收益”。

**需要多少块**：由目标效应与噪声地板之比决定。同环境口径下，要判定**百分之几量级**的效应至少需 **6~8 块**
ABBA（此时的块间标准误远小于目标效应）；预测效应与地板同量级（约 1.5σ 以内）时判**不可分辨**。地板数值与判定表见
`window-ab-protocol.md` §4。

> **不要与 A/B/A 混用**：`window-ab-protocol.md` §3 的 **A/B/A** 是**窗口级**漂移校正
> （`base → arm → base`，用前后两个 base 的均值抵消窗口内单向漂移，代价 3 倍卡时）；
> 本节 **ABBA** 是**臂内请求级**交错（两个配置在同一进程内轮流跑，代价是同一次运行的机时）。
> **两者针对的漂移不同，不可互相替代。**

## 3. 先做敏感性校准，再判断“差异是不是 bug”

**在把“输出不一样”当作 bug 之前，必须先建立这个模型/任务的数值敏感度基线。**

做法：找一对**已知无害**的改动（如 1-ULP 的归约序变化、已验收的等效优化），量它们的输出差异；
这个值就是噪声地板之上的“正常差异”。**换模型、换分辨率、换精度路径或换硬件都必须重做这项校准。**

> ⚠️ **作用域**：这是**该模型 / 该任务类型**的性质，**禁止跨任务类型迁移**
> （不要把扩散模型的 20–50/255 用到别的任务上）。
> 具体锚点数值（某 4 步蒸馏扩散模型的 `0.000 / 22.0 / 48.0 / 32.4`）保留在
> `../../accuracy-gate/references/quality-gate.md` 的「校准经验（数值敏感度地板）」；
> **本文件只定义 SOP，不复述数值。**

**补充判据**：若输出差异是**局部化**的（某一段 / 某个 rank 明显更差、有接缝），那更可能是实现错误；
若**全局均匀**，则更可能是数值发散或整体功能缺失。**做分区/分段统计**比看总体均值更有判别力。

> 若不先做这项校准，很容易把模型固有的混沌敏感度当成 bug：实践中曾有排查据此追了**十几轮**，
> 并做了三次后来被证伪的修改。

## 4. 单测优先于端到端

**能离线验证的，绝不跑端到端。**

实践收益示例：一个“分组池化”函数在端到端上表现异常（差异明显恶化）。
写一个 20 行单测，以**“全窗口时该函数必须与参考实现逐元素相等”**为不变式，
**一次运行**就定位到根因是 bf16 累加精度不足。

| | 单测 | 端到端 |
|---|---|---|
| 耗时 | 秒级 | 分钟级（含模型加载 4–5 min） |
| 定位能力 | 精确定位到函数 | 只知道“有问题” |

**设计单测的原则**：找一个**在正确实现下必然成立**的等式或不变式，让数值本身成为判据，
而不是靠肉眼比对。

## 5. 外推纪律：站点 ≠ 阶段、部件不可加、不变量复核

### 5.1 站点级收益 ≠ 阶段级收益

**实践中两者反复不一致**：

| 改动 | 站点 | 端到端 |
|---|---|---|
| 某 kernel 多行优化 | **约 2 倍** | **测不出（符号翻转，中位与均值跨零）** |
| 移除大块内存流量 | 约 3 倍 | **降幅与预测完全一致（个位数百分点）** ✓ |
| 融合 FFN（结构化） | — | **降幅约一成**，是站点外推的 3 倍（未能解释） |

**规律（实测观察，非普适定律）**：**省“内存流量 / 计算结构”的改动能传导；
纯“kernel 延迟”的改动可能被流水线吸收而不传导。**

**操作含义**：做外推时必须说明依据，并在报告里把“站点值”与“端到端值”分开列，**不要把外推当结论**。

**关键加强：外推实践中在两个方向都错过** —— (d) 低估约 3 倍、(b) 高估（预测值明显大于实测值）、
(a) 高估且最终不可分辨。**不存在“外推偏保守”或“外推偏激进”的稳定偏差**，因此不能靠经验系数校正，
只能实测。

### 5.2 部件不可加：必须实测组合

单个改动的收益**不能相加**。实测示例：两个部件单独计时之和小于合并后的实测值（两者同量级）
—— **负交互**。

同理，写“理想融合式”（如 `fused_ideal = A + B − 共享I/O`）预测收益是**有价值的前置判断**，
但**实测偏离量本身常常就是交付物**：预测值小幅优于阈值（略赢），
实测值明显劣于阈值（输）—— **这个差额正是“为什么这条融合走不通”的答案**，
比一句“没收益”有价值得多。

**操作含义**：门控收益要**逐个组合实测**，不要用单点收益外推组合收益。

### 5.3 用不变量校验测量本身（Amdahl 时长不变性）

一个改动如果只去掉**与序列长度成正比的流量**，而主导核的耗时也随序列长度成正比，
那么在两个不同序列长度上它的**百分比收益应当不变**。

实测示例：`sparse + (b) + (a)` 三门控在 5s 与 15s **降幅恰好相同** → 这个“巧合”既是
**测量可信的旁证**，也说明该改动的作用机制与推理一致。

**反之**：若百分比随规模漂移，必须解释机理。一个例外（(d) 融合）：绝对节省只涨 1.5×
而 token 涨 2.9× → 比例掉 2.2×，机理是 two-block Mmad-per-tile 结构开销在大 M 下摊销更好
（**两效应各自占比未测**，属未解释项，应如实标注而非含糊带过）。

**操作含义**：多时长复测不只是“多一组数据”，它是对**因果推理的独立检验** —— 值得优先做。

## 6. 上报模板

给出性能结论时，同时给出：

1. **配置**（完整命令行 / 环境变量）
2. **有效性三证据**（返回码、输出大小、日志条数 —— 口径见 `evidence-toolbox.md` §1）
3. **基线对照值**，以及对照是否交错进行（ABBA 见 §2；A/B/A 见 `window-ab-protocol.md` §3）
4. **站点值与端到端值分列**，并标注哪些是外推（§5.1）
5. **失败运行的数字单独列出并标注作废**（这比隐藏它们更有价值）
6. **“不可分辨”作为正式结论写出**，而不是从跨零的点估计里挑有利的那个符号
7. **未验证项**明确标注“未实测”

“不可分辨”的可复用表述（实测口径示例）：

> 3 轮 ABBA 无法分辨（中位数为负、均值为正、consistent_sign=False）
> → **判为不可分辨，点估计跨零**

注意此处 median 与 mean **符号相反** —— 这正是“不能用均值代表结论”的直接证据。

## 7. clean-window 与热降频判定（取数口径）

> **口径单点在本节。** 本节只定义「**怎么取数、怎么判热降频**」；**具体读数**留在被测对象的
> 带作用域文件——多卡/拓扑档在 `../../dit-parallel-opt/references/ascend-topology-bandwidth-diag.md` §5，
> 分析侧的污染判读在 `../../profiling-analyze/references/performance-analysis-methodology.md`。
> 归因顺序上也有一条硬约束：**先排除环境劣化，再怀疑代码**（见下表的两种现象）。

### 7.1 clean-window（干净窗口）

**定义**：从 per-step 序列里**剔除热降频 / 环境劣化窗口后**再取数，而不是对整段直接取平均。

- 默认窗口 **steps 2-14**（跳过第 1 步的预热 / 编译影响），取 **avg 或 p50**；
- **固定 rank0 口径**：多卡各 rank 的 per-step 值不同，混 rank 取平均会掺入 rank 不均衡；
- **取数前先验窗是否干净**：窗内步长应**无单调抬升趋势**；若窗内已出现降频斜率，把窗口缩到斜率出现
  之前的步，并在报告里写明**实际取的步区间**（**不许**只写「取平均」）。

### 7.2 热降频 vs 环境劣化：两种现象必须分开判

| 现象 | 判据（**先复核，再套用**） | 处置 |
|---|---|---|
| **热降频** | 长跑**后段**步长**单调抬升**（约在十数步后起）；与代码 / **编译档** / 同机租户**无关**；缩短步数或降载后现象消失 | 取 clean-window 数；**不得**把降频段算入性能结论。绝对耗时仍不可跨窗口比较 |
| **驱动损伤残留态**（环境劣化） | 整组**每步时长均匀**偏大（量级级抬升，约 10×）且**无降频斜率**；`npu-smi` Health 仍报 OK | **不是测量问题**：换健康卡组重跑；组可用性必须用**真实多卡 run**核对 per-step cost（步骤见 `ascend-topology-bandwidth-diag.md` §4） |

> **与 §1 / §2 的分工（勿混用）**：clean-window 解决的是**窗口内部**的漂移；
> **跨窗口不可比**仍由同窗 A/B 口径解决（`window-ab-protocol.md`）——
> **clean-window 取数 ≠ 可以拿两个不同窗口的 clean-window 相减**。
> 判定「有没有收益」一律以同窗相邻对 / 交错对照为准（§2）。

### 7.3 功耗墙：**秒级**就降频，绝对值跨运行不可比（地板干净也救不了）

§7.2 的降频形态是**长跑后段单调抬升**；本节是另一种更隐蔽的形态：**持续 cube 负载在数秒内就把
频率压下来**，而**同一次运行内的 A/A 地板仍然极小**——于是"地板很干净"会让人误以为绝对值可信。

**取数方式（现场取数）**：用 `npu-smi` 按**物理** id 采样 AIC 频率 / 温度 / 功耗，
比对「空闲 / 持续融合 GEMM / 持续量化 matmul」三种状态（具体读数见会话产物归档
`{run_results_dir}/archive/`，属设备状态量，不写进本文正文）。

**实测后果**：**同一个 2 分钟运行内**，固定参考 GEMM 在两轮 round-robin 里相差 **+10.8 %**，
而该运行的**同运行 A/A 地板只有 0.02–0.3 %**。
⇒ **"地板干净"不能证明"绝对值可比"**；跨运行的绝对值可因占空比浮动到 **~30 %**。

**强制动作（每次计时都做，缺一即该轮绝对值不可引用）**：

1. **带一个固定参考 GEMM 的达成 TFLOP/s**：同一 session 内对一个**固定参考 GEMM 块**计时，
   取**首个健康读数作参考区**；后续读数相对参考区的**比值明显低于参考区**即判**已被压频**
   （本机由参考区比值量出该状态下所有绝对值约虚高 40 %；比值可用，绝对值不可跨运行引用）
   ⇒ 一行读数，直接 accept/reject。
2. **单块持续 cube 时间要短到参考区漂移仍在可接受范围内**（以第 1、3 条的参考 GEMM 比值 /
   漂移读数判定）。
3. **参考区先测一次、最后再测一次并报漂移**——本仓用它抓到过 2 分钟段内 **+8.0 %** 的漂移，
   而同运行地板 0.25 % 完全看不出来。
4. **结论写成比值，或同一 round-robin 内的差**，绝不写成跨运行绝对值；有进程内参考时，
   比值把时钟状态整个对消（用法见 §5.3）。
5. **窗与窗之间让板子降温**：多卡 arm 跑完后板温升高，紧接着的单卡运行参考 GEMM 会明显变慢
   （本机用参考区读数复核：实测慢 **21–28 %**）。
6. **`ASCEND_RT_VISIBLE_DEVICES` 下不要用 `npu-smi -i 0`**：`npu-smi` 取的是**物理** id，
   会静默采到另一张卡（本仓曾把一张空闲卡的读数当成被测卡）。

> 与 §7.1 的关系：clean-window 是**纵向**（同一序列内剔段），本节是**横向**（跨运行的时钟状态不可比）。
> 两者都不替代同窗交错对照。

### 7.4 同卡并发抬高：**整模 profile 的逐算子绝对耗时不可直接引用**

§7.2/§7.3 讲的是**时钟**（热降频、功耗墙）。本节是**另一个**、与时钟无关的机制：
在整模 profile 里，一个算子测到的时长包含**它自己与同卡上其它流/其它算子的相互干扰**，
因此**比该核在隔离条件下慢**。

**本仓实测**：某融合核 profile vs 隔离 = **1.2054×**，其中两个可测项相乘即 1.2040（残差 +0.12%）：

| 项 | 幅度 | 说明 |
|---|---|---|
| **同卡并发** | **+15.2%** | 同 session 配对、逐对设备事件、多轮一致（逐对幅度与标准差见会话产物归档 `{run_results_dir}/archive/`）；**另需排除**是时钟效应——本仓用 AIV 饱和验证十分位均值平坦、参考 GEMM 前后一致，**功耗墙被排除** |
| profile 自身前若干次调用 | +4.5% | profile 窗口的头几次与稳态不同 |

**而且抬高是"整步性"的、不是某算子特有**：同一 profile 里**共跑的 GEMM、`IndexPutV2`、
`GatherV2`、`HcclLaunch` 都被一起抬高**（逐算子幅度见会话产物归档 `{run_results_dir}/archive/`）。

**规则**：

1. **同一 profile 内**：**相对份额、排序、调用次数、形状、管线占比可用**；
2. **逐算子绝对耗时不可跨运行引用**，也不可与隔离/单卡测量**直接相减**——两者差着约 20%；
3. 需要绝对量时：**把该核放回隔离/单卡测量**，或做**同 session 配对比值**（比值把并发与时钟一起对消）；
4. 诊断"某个核是不是变慢了"时，**先做 §7.4 的比值**，再进 §10.1 的等功对照——
   否则会把测量误差当成 kernel 缺陷去修。

### 7.5 慢启动 vs 卡死：用**独立观测量**判别，且**设备状态必须当场重取**

> **为什么必须写成规则**：静息不动的读数无法自证它属于哪一种——**跨时钟域的时间戳对减、
> 或把"等了多久"当判据，都会把"慢"读成"死"**。两类形态必须用下面这套独立观测量分开：
> 真死锁是「请求在飞 + 日志停 + 设备空闲」，而另一类"慢"（权重加载 / compile prime）
> **日志一直在推进** —— 两者形态完全不同（单案例读数见会话产物归档 `{run_results_dir}/archive/`）。

**判慢 vs 判死的检查顺序（按优先级）**：

1. **服务端日志自身在不在长** —— 只比**同一时钟域**的时间戳：用日志文件自己的 `stat` mtime /
   行数增量，**绝不用 `date -u` 与带时区的日志行对减**（这是最常见的误读来源）；
2. **请求是否在飞**：客户端 curl 仍在挂起（没有返回码、没有字节数）；
3. **设备侧有没有在算**：`npu-smi info -t usages` / 功耗 / 温度。**空闲 = 没在算**（死锁或空转），
   **有活动 = 还在算**（慢）；
4. **进程级 CPU**：worker CPU 占用在档（相对该 worker 的核数明显偏高）⇒ 在推进；CPU 近空转而请求在飞
   ⇒ 在等一个永远不会来的事件。

**判别式**：请求在飞 + 日志停 + 设备空闲 ⇒ **判死锁**（挂死/事件依赖问题）；日志在推进 **或**
设备有活动 ⇒ **判慢启动**（继续等，阈值取本任务**健康臂**的初始化耗时，不凭感觉）。

**同一条纪律的另一半 —— 设备状态快照会过期（缓存不得当真值）**：
一次"卡占用结论"读的是一份**写在清理动作之前**的快照文件，于是把已经释放的卡读成占用 ✗。
⇒ **设备占用/状态只能来自当场查询**：复用**任何**快照（哪怕同一会话里更早写的）都必须先证明它不早于
**上一次清理 / 目标变更**，并在结论里标注快照时刻；否则**不构成占用证据**。
这与 §10.1 的前提是同一条血统门（"只找到历史 `kernel_details.csv` ⇒ 本次未验证"），
也与 §8.7 profile 血统门同源：**状态类读数跟 profile 一样有血统**。

## 8. 先证明仪器，再用它下结论（诊断可信性门）

**判据**：任何“**被测对象坏了**”的结论都由**仪器 + 对象**共同产生；仪器不可信时两者无法区分。
所以**在把差异写成缺陷之前，先证明这台仪器能测到东西**。

### 8.1 两次假阳性，同一个根因（本仓实测）

| 仪器 | 缺陷 | 它给出的假结论 | 修好后 |
|---|---|---|---|
| 逐腿校验探针：参考侧张量在**计算流**上构造，参考 a2a 发在**侧流**上，两者之间**漏了跨流依赖** | 参考 a2a 可能读到未构造完的参考张量 | 大量“载荷被污染”记录（占受审记录绝大多数） | 同一批样本 **0** 条 |
| 2 卡微基准：发送缓冲与集合通信之间的等待**方向写反**（等成了反方向） | 集合通信可能读到尚未填完的发送缓冲 | “集合通信静默丢 3%~16% 的腿，连主机屏障都挡不住” | 顺序修正后同一原语 **0** 条（受审腿全过） |

两者同属一类：**跨流依赖写错或漏写**。危险之处在于**症状与被测对象的真实缺陷形态高度相似**
（连续区间、落在单一来源、事后复查“稳定”），**靠看形态猜不出来** —— 只能靠下面三条判据。

### 8.2 三条判据（缺一不可）

1. **负对照**：故意去掉那一步依赖/顺序，**证明仪器确实会报错**。
   若去掉后仍然“一切正常”，说明这条通路根本没被覆盖 —— 此时任何“0 差异”都不算数。
   > **推论（最常踩的一种）**：负对照也要施于**用例本身** —— 若被测的量在**任何**实现下都必然相等，
   > 那么“差异 = 0”是**用例不可能失败**，不是“没有问题”。实例：把除数取成 **2 的幂**时，除法在
   > **任何** lowering 下都精确 ⇒ 对拍恒为 0 差异，一条可能成立的条款差点被“0 就删条”的规则误删 ✗。
   > 做法：让用例**有能力失败**（选非精确参数）+ 一条**本应出现差异**的对照
   > （实例见 `../../operator-dev/references/triton-ascend-lowering-pitfalls.md` 维护节「通则 2」）。
2. **同窗比例检查**：同一份脚本、同一输入、**换窗口重跑**。若失败比例本身大幅变动
   （本仓实测：同一脚本在两个窗口给出个位数百分比与二十几个百分点），**可疑的是仪器与调度余量，
   不是被测对象** —— 硬件级缺陷的失败比例不会这样漂。
3. **哨兵法**：把接收/输出缓冲**预填哨兵值**，于是两种故障可被分开：
   - 仍是哨兵 ⇒ **那一块从未被写入**；
   - 匹配**上一次迭代**的内容 ⇒ **写了陈旧内容**。
   二者混在一个“值 ≠ 期望”的总计数里永远分不开（本仓实测：只校验首字节的探针把两者混为一谈，
   结论一度指向“传输丢数据”）。

### 8.3 三种“看不到被测时刻”的仪器

- **减法观测**：`device = total − host`（§10.1）—— 主机是瓶颈时它趋零；
- **事后快照**：在**读取之后**才取快照的校验 —— 滞后写入此时已落盘，比较必然“无变化”，
  于是它**永远无法反驳早读**。快照必须与**被测动作同时刻**（或在其之前）取。
- **跨流事件差**：把**两条不同流**上的事件配对求 `Event.elapsed_time` —— 本机实测返回
  **无符号下溢量级**的垃圾值（实测值 / (`2**64/1e6`) ≈ **0.999999997**，即该签名可对到 9 位有效数字），
  而同流成对事件精确。
  规则：① 只配对**同流**事件；② 要问“A 流被 B 流拖了多久”，只能从**等待流自己的 WAIT 段**
  求和，**绝不**用跨流时间差；③ 窗口末做**一次**主机同步后统一**延迟读取**即可，
  不必每次调用都同步（设备侧复跑：同流**不**同步直接读、以及窗口末一次同步后延迟读，
  两者读数相同且都 sane ⇒ 那次同步是**省成本**，不是正确性前提）。
  > **为什么必须靠规则、不能靠"看着合理"**（设备侧复跑最有价值的一点）：跨流配对的危险**不是
  > "总返回垃圾"**，而是**有时返回一个量级完全合理的假值** —— 按自然顺序的跨流配对实测给出一个
  > 看起来正常的读数（与同流值同量级）。**因此防线是"只配同流"这条规则本身**；
  > 用"数值看起来合理"给它放行，正是它下一次骗到你的方式 ✗。

### 8.4 计时臂的"仪器毒药"：一个调试开关就能改变结论

- **事实**：一个**正确性调试开关**（打开后逐调用做一致性检查）让每请求的生成阶段**增加约三分之一**
  （本仓实测：同配置下该段从此前的十几秒量级升到二十秒量级）⇒ **带该标记的臂永远不能进计时表** ✗。
- **规则**：凡"**打开后开销大到会改变结论**"的调试开关都要**单列** —— 计时臂与调试标记臂**分离**，
  报表写明"该臂是否带调试标记"；调试标记支撑**正确性**结论，**不得**用于性能结论。
- **自证仪器代价**：用**同窗**的"带标记 vs clean"对比量一次它的代价（本仓实测同一窗口内差异
  **≤0.5%** ⇒ 该次 instrumentation 可视为免费）；但这是**实测结论**、不是默认前提，
  **每换窗口 / 换臂都要重量**。

### 8.5 先证明基线：可信度来自**时间上独立**于本次操作的记录

- **问题**：所有人都拿同一个"交付基线"当基准，而**那个基线本身可能是同一轮操作（回滚）的产物**
  ⇒ 基准与结论**互相印证**，属于**自我循环** ✗，看不到任何问题。
- **规则**：基线的可信度**只能**来自**时间上独立于你这次操作**的记录 —— 例如**只读核对**部署文件
  与一份**时间戳早于参考运行**的备份逐字节相同；**不得**拿"我自己刚做的备份 / 我刚算出的哈希"
  当独立证据（它只能证明"我没改坏"，证明不了"交付态就是它"）。
- **与 §8.2 的关系**：这是"先证明仪器"的**基线版** —— **仪器可信 ≠ 基线可信**，两者都要自证。

**复核**：换 CANN / 驱动 / 框架版本、换卡组、改脚本后，**负对照与比例检查都要重跑一次**；
通过标准是“负对照会报错 + 同窗比例稳定”，而不是“这条仪器从没出过问题”。

**失效信号**：若某仪器在负对照下**不再报错**，或它的失败比例随窗口漂移，则它此前所有“通过”结论作废。

---

### 8.6 负控必须"**能够失败**"：先验证它咬得住，再拿它当证据

**规则**：任何负控（negative control）在**用于支持结论之前**，必须先用一个**必然触发**的取值
验证它**确实失败**。一个恒为空操作的负控会让"负控通过"变成假证据，把没有验证过的路径读成"已验证"。

**本仓反例**：某核的 `FORCE` 负控传入 `forced = U[0.5, 1.5)`，而各 block 自身的 amax 约 **2–6**，
`maximum()` 恒为空操作 ⇒ 该负控**不可能失败**，首轮却报"相等/通过"。改用**明显越过被测对象自然
量级**的取值后，它按预期失败（载荷值与 scale **都出现差异**，且正落在边界 block），
这才把 `FORCE` 路径验完。

**执行**：

- 负控的取值必须落在**被测分支真正起作用**的区间（先量被测对象的自然量级，再取一个明显越过它的值）；
- 报负控结果时**同时报它的"咬合幅度"**（差了多少个元素/多少 µs），只报"通过/失败"不算证据；
- 若负控的差距落在噪声地板内 ⇒ 该负控**无效**，换更狠的取值重做。

**作用域包含「测试」与「交付的门禁脚本」**（不只是测量）：§8.6 的适用面是**任何**用来支持"没问题"
这一结论的断言，**测试用例与交付的门禁脚本都在其内**。判据同构：

- 一条测试若在**任何**实现下都会通过，它证明的是"没被覆盖"，不是"已通过"。**写的测试必须先证明
  它可以失败**：故意破坏被测实现跑一次，或用必然触发的输入。本仓实例：`test_diffusion_ipc.py`
  的"unpack 后没有段残留"断言，在 Windows 上因为 `SharedMemory.unlink()` 是 no-op 而**恒真**
  （同一份探针里，故意去掉 unlink 的负控跑完仍打不开任何段 ⇒ 该断言在该平台上恒真、拿不到信号）
  ⇒ 该平台上的"通过"是空过；
- 交付的**门禁脚本**若从未在其目标平台上跑通一次最小用例，它同样不是证据——判据与模板见
  `scripts/check_gate_script.py`（脚本平台归属与自证门）。

### 8.7 profile 血统门：**从任何 profile 推理之前，先证明它是哪个配置产出的**

**规则**：profile 文件本身不携带"我是哪棵树/哪个配置跑出来的"。**在用它推理之前**，必须先给出
它的**配置指纹**并写进口径声明；指纹无法给出时，该 profile 只能用于**与自身内部的横向比较**，
不得作为"现状"或"基线"。

**可用指纹（任取一组合，必须在报告里写出）**：

- **算子在不在**：某配置特有的算子存在/缺失（例如某个融合核、某个 boundary 修复核）；
- **同名算子的调用次数**：例如某几何链在一档是 **N 次/step**，在另一档是 **0**；
- **同名算子的元数据**：输入/输出个数（例如某量化核在某档是 **2 个输出**、另一档是 **3 个**）；
- **树/库的哈希**：源码文件或库的 md5。

**为什么写成强规则**：同一个配置假设会被**多处独立引用反复咬中**——
融合收益的对照基线取自另一个配置、机会点预登记用的是旧档普查、某核的前提是旧拼写、
某次归因用的是旧 profile、某个"回归"用的是旧档数字。**这些没有一次是 kernel 的问题，
全都是 profile 血统没被证明。**

## 9. 断言“新路径真的跑过”（参与度门）

**问题**：当优化**在设计上就应当与基线逐字节相同**时，**md5 一致无法区分“跑了且精确”与“静默回退到基线”**。

本仓实测：一条融合臂 md5 与基线**完全一致**、字节数一致、耗时只差零点几秒，看起来是完美结果；
实际上新路径**每次调用都抛 `ModuleNotFoundError`**（数千次），框架捕获异常后**回退到基线分支** ——
这条臂等价于“什么都没开”✗。回退的根因是**同级绝对导入在包上下文下失败，而兜底的 `except` 把它掩盖成
“模块不存在”**。

### 9.1 四条要求（每次验收 A/B 都做）

1. **参与度计数器**：新路径首次生效时打一条**唯一**日志（每 rank 至少一次），断言计数 ≥ rank 数；
2. **失败计数器 == 0**：静默回退通常伴随一条被框架捕获的异常日志（易被当噪音），必须单独断言为 0；
3. **两个计数器分开 grep**：写在同一条模式里会**把失败数报成参与数**（本仓实测：数千次回退被读成
   “已生效”）✗；
4. **导入冒烟**：烧掉一条臂之前先做一次**包上下文导入检查**（`PYTHONPATH=… python -c "import <pkg>.<mod>"`）
   —— 让同类失败在任何一条臂付出机时之前就大声失败。

### 9.2 与 md5 的关系（两个方向都别误读）

- md5 一致**不能**作为“新路径生效”的证据（本条）；
- md5 **变了**也**不等于**“门控没生效” —— 字节精确的优化本来就应当保持 md5 不变，
  本仓曾有臂把“md5 与基线一致”误读为失败信号（反向陷阱见 `../../quantization-dev/SKILL.md` §五.5）。

**复核（§9.1 的四条）**：新增/修改门控后，构造一条**故意打开但底层必然失败**的臂，
验证 §9.1 第 2 条能报出来；再恢复。

### 9.3 两种"新路径其实没跑"的成因（异常回退之外）

§9 的原始形态是"入口处宽泛 `except` 把新路径吞掉"。**2026-09-20 现场**补上另外两种，都**不报错、不回退**：

**成因 A —— 用私有 harness 复刻机制，于是只验证了"机制"，没验证"集成"。**
某"把 pre-FA 半边挪到侧流"的补丁，其决定性证据来自一个**自建 harness**：它自己 `torch.npu.Stream()`
建侧流、自己实现 `SER` / `PIP1..3` 四条臂，**从不调用被打补丁的那个调用点**。
结论："这个调度思路在本组合观测下有效"成立；"**这个补丁能跑**"**不成立**——
集成在八卡那一臂之前**从未被执行过一次**，一跑即 `TypeError`，4/4 请求失败。

**成因 B —— 新路径被下游前置条件静默禁用。** 本仓代码里就有这样一个前置条件：

```python
if st is None:          # 没有侧流
    prepare = None      # 特性被静默取消；循环里走的是未改动的原路径
```

⇒ **单卡 serving A/B 里"门控 ON"与"门控 OFF"是同一条路径**，两边读数必然相同（看起来"无回归"）。

**判据（合并两条，适用于"依赖多卡 / 侧流 / 集合通信 / 特定几何"的改动）**：

1. **机制证据与集成证据分开要，且不可互替**：私有 harness / 单测证明**机制**；
   **真实入口**（服务 + 一次请求）证明**集成**。缺集成证据的补丁**不得**进入 A/B 排期。
2. **触发条件要写进归档**：交付时必须写明"**在什么条件下新路径才会真的被执行**"
   （本例：需要侧流 ⇒ 必须多卡）。只给 md5 的归档无法回答这个问题。
3. **单卡读数要标注它测的是哪条路径**：若单卡读数其实来自未改动的路径，
   它**只能**作为"改动中性"的证据，**不得**作为收益证据（收益必须在**触发条件满足**的窗口量）。
4. **与 §9.1 合并执行**：参与度计数器在**单卡 ON 臂**上应当报 **0**——
   若它报了非 0，说明笔者对"新路径何时执行"的理解是错的；若它报 0 而结论仍被当成"ON 臂已验证"，
   就是本条要防的错误。

**复核**：对每个"ON 臂"问两句——① **这份证据走的是真实入口吗？**
② **满足什么条件，这段新代码才会被执行？该条件在本臂成立吗？**
任一答不上来或答"不确定"，该臂作废。

**失效信号**：门控改名、默认值变化、或把新路径改为“默认开”之后，本节的断言位置要同步搬移，
否则会退化成“只在部分臂上有效”；若某改动的**触发条件从"多卡"变成"恒成立"**（例如侧流改为总是创建），
§9.3 第 1 条的"单卡失明"结论随之失效，须重判。

## 10. 上下限账：device 省了 e2e 没省 ≠ 该关掉优化

### 10.1 不要用 `device = total − host`

实测：某链路用“总时长 − 主机时长”算出**亚毫秒级**设备时间，而 profiler（`op_summary` 任务时长求和）
对同一链路给出**约二十倍**的值 —— 因为**主机才是瓶颈**，设备在等，差额自然趋零 ✗。
⇒ 设备时间一律用 **profiler 或显式事件**取；减法只能作粗估并显式标注（同 §8.3）。

**复核（本条的验证前提，设备侧实测踩过）**：本条的复核**依赖 profiler 真的产出新的 `kernel_details.csv`**。
若采集只找到**历史**文件（日志形如 `no NEW kernel_details.csv (found N pre-existing) -- skipped`），
则**本次不构成验证** —— 既不能说本条成立、也不能说被推翻，只能记"未验证"△。
⇒ 判读前先确认这次采集**确实产生了新表**（比对文件时间戳 / 计数），否则一切"设备侧无差异"都不作数。

### 10.2 上限提升规则（本仓最重要的一条方向性判据）

> **当一项优化确实降低了设备侧工作量、但端到端没有变快时，不要关掉它 —— 它抬高了性能上限。
> 下一步是找出真正的绑定约束，而不是否定这项优化。**

顺序固定，四步：

1. **先量化上限提升**：把每个阶段的设备/主机**增量**逐项实测相加，得到“理论上限提升”。
   本仓口径示例（比例与量级，绝对值见会话产物归档）：把某段集合通信的载荷减半 ≈ 该通信阶段
   **约三分之一**；消费侧去掉一段重排+量化 ≈ 每分块**零点几毫秒**量级 ⇒ 合计约为该阶段**两成**。
2. **再对账**：把上限提升与**同窗 A/B 的实测差**放在一起，**要求各项之和与实测墙钟差在 ±10% 内对上**
   （同窗口径见 `window-ab-protocol.md`）。对不上就是**还没测全**，不是“没有收益”✗。
3. **点名绑定约束**：把未对上的那部分归到具体候选 —— 通信是否真在关键路径上 / 新 kernel 是否与
   通信或注意力**串行**而非重叠 / 每层新增的集合通信与事件 / 占位与交接路径的每调用开销 /
   分配器行为 / 设备侧竞争 —— **用一次 profile 或事件计时点名**，不要继续推理。
4. **只对绑定约束动手**：约束未点名之前做的任何“再优化”都是猜 ✗。

> 反例形态（本仓实测）：一项优化把某阶段设备工作量降了**约两成**，端到端却是**小幅回退**；
> 此时若按“没有收益”关线，会把已经拿到的上限提升一并扔掉。正确动作是把**未对上的那部分**
> 当作下一个优化目标 —— 量级上它比回退本身**大一个数量级**。

### 10.3 绑定性判据：从某资源移走的工作，必须变成该资源新增的**空闲**

§10.2 只说“去找绑定约束”。本节给出**可证伪**的判法：**分别测该资源自己的忙碌段与空闲段**，
把工作从它身上移走，然后**只问空闲有没有等量增长**。

> **判据**：若某资源的**空闲段增长量与移走的工作量基本相等**，而它的**忙碌段基本不变**，
> 则该资源**从来不是绑定约束** —— 停止优化它，转去测**另一条流**。
> 反向同样成立：**忙碌段自己降了，才算真省**。

本仓实测形态（比例与量级，绝对值见会话产物归档）：把某段集合通信的载荷减半后，
**通信流的空闲**每层增长约**五分之一**、增长量与“省下的工作量”**相差不到数个百分点**，
而它的**忙碌段变化不到一个百分点**（视为不变）；同窗口端到端**没有变快**（小幅回退）⇒
该通信段**不是**绑定约束，动作应转向**另一条流**（本例是计算/主机侧）。

配套三条：

1. **对账要闭合**：把“仪器化后计算流的每层增量”与“**干净墙钟**的同窗增量”对账 ——
   本仓实例闭合到 **±7%**，且**计数账对总账**的偏差在**千分之几**量级（每臂数百个样本）。
   闭合了，才允许说“谁在关键路径上”；
2. **闭合后看罪魁的形状**：本例新路径里**生产者段的新增成本是整段端到端回退的四倍多**（比值约 4.5×）
   ⇒ 一般形态是：**账一闭合，罪魁通常是“被加到关键流上的新成本”，而不是你本来想缩的那块资源**；
3. **空闲增长 ≠ 端到端收益**：空闲增长只证明“那块资源被松开了”，收益要到**墙钟**上再验一次
   （两者可能被新成本吃掉，见第 2 条）。

### 10.4 反模式

- 阶段表只记主机（或只记设备）⇒ “各项之和”永远对不上 ✗；
- 用“占比高”直接推收益（见 `../SKILL.md` 坑 3），或用“设备省了”当“端到端会变快”；
- 把“端到端没变”写成“该优化无效”并关闭 —— 缺的往往是**绑定约束那一步实测**；
- 只看“那块资源变快了”就继续加码（绑定性判据 §10.3：空闲没等量增长 ⇒ 它不是约束）；
- 用跨流事件差推“谁拖了谁”（§8.3，本机给出下溢量级的垃圾值）。

**复核**：换硬件 / 拓扑 / 形状 / 步数后，上限账与绑定约束都要重算（设备与主机谁先到瓶颈会变）。
通过标准 = 阶段表各项之和与同窗实测差在 ±10% 内对上，且绑定约束有**一条**实测证据点名
（最省事的一条就是 §10.3 的“空闲是否等量增长”）。

**失效信号**：若某次对账中“各项之和”能对上而端到端仍不动，说明绑定约束已不在原先那一处，需重新点名。

### 10.5 归因规则：wall 差 ≫ device 差 ⇒ 差额归主机与下发（强约束）

**判据（一条即可分流优化方向）**：把一个特性开/关做同窗 A/B，取三个量——

1. **wall 差**（阶段墙钟差，或每请求端到端差）；
2. **device 差**（同口径下逐算子耗时之和的差）；
3. **下发计数差**（同口径下算子**实例数**的差，可从逐算子清单直接求）。

分流：

| 观察 | 归因 | 优化方向 |
|---|---|---|
| wall 差 ≈ device 差 | 设备算力/访存 | 做**算子级**优化（写法、tile、融合内核本身） |
| **wall 差显著大于 device 差**（实测中出现过 2 倍以上的量级差） | **主机侧与下发**（每算子启动、流同步、Python 侧组装） | 做**去冗余/减少算子数量**（融合、离线固化、合并候选），把单个算子做快收益有限 |
| device 差 ≈ 0 而 wall 差大 | 完全在主机侧 | 先查参与度门（§9）与流同步（§8.3），再谈算子 |

**配套要求**：归因结论必须同时给出上面三个量（缺 device 与计数差就无法分流），并按
`report-contract.md`/`overview-report.md` 的**拆分表**落到交付件里；
**拆分表的各项不可相加**（争夺同一处收益的候选必须标注）。

**复核方法（判定该归因是否仍然成立）**：换精度档 / 换权重形态 / 换拓扑后，同一特性的 wall 差与
device 差之比会变——**每次重测三个量再重判方向**，不要沿用上一次的归因。

### 10.6 同窗 A/B 的硬要求（每次验收都做）

- **臂数**：每臂 **≥4 个请求**（1 冷 + ≥3 热），性能结论取**热请求中位**，并写明"中位/均值/样本数"；
- **臂内确定性**：同臂各请求产物应逐字节一致（不一致 ⇒ 先当噪声/竞态处理，不得直接比时间）；
- **控制臂可信**：控制臂必须能**复现历史同配置的产物摘要**（md5/字节数）；不能复现 ⇒ 先定位再比；
- **唯一变量**：两臂同脚本、同请求、同窗口，唯一变量写在交付件里；跨窗数字只作"量级参考"；
- **单位统一**：多档同屏对比统一到 **step** 口径并在括号内给百分比；DiT block 级一律 `ms`
  （见 `../../model-auto-optimization/references/overview-report.md` §2 单位契约）；
- **采集污染**：若某臂带 profiler 采集，其 wall **不得**直接与他人比（§8.4 / `profiling-collect`）。

### 10.7 补丁**自己**新增的每调用开销要单独立账（热路径日志是最常见的一种，2026-09-20 实测）

**判据**：验收一个补丁时，除了问"它省了什么"，还要问"**它每调用新加了什么**"。
补丁新加的日志行、计数器、同步、临时张量都落在**同一条关键流**上，会与省下的量**直接对消**。

**本仓实测**：一个在隔离测量下把某向量核**每调用耗时明显压低**的补丁（隔离测量、逐字节通过），
在启动器里**每次调用**打一行带 `flush=True` 的 stderr 日志 —— 真实管线一个臂因此打出**大量日志行**，
而该臂端到端**没有变快**（比同窗对照略慢）。日志是否吃掉了全部收益
尚未逐项对账，但它是**与收益同量级、且由补丁自己引入**的新增项 ⇒ **必须先排除它**，
再去论证"不在关键路径上"。

**执行**：

1. 诊断输出**改为每进程一次**（模块级标志），不要每调用一次；确实需要每调用时，
   做成**独立开关**并**默认关**；
2. 验收臂至少跑两遍：**诊断开** 与 **诊断关**，差值即"仪器自身代价"；
3. 把"补丁新增的每调用开销"作为**负数项**写进 §10.2 第 1 步的上限提升台账，否则对账永远差一截；
4. 隔离 harness **必须把补丁的启动器/宿主外壳一起压测**——只压 kernel 会把补丁新加的宿主侧开销全部漏掉。

**失效信号**：隔离收益是"每调用微量级 × 每步大量调用"，而管线里连**符号**都测不出来
⇒ 先查补丁新增的每调用开销，再怀疑"不在关键路径上"。

## 基线可信度先于对比（强制前置项）

**规则：任何 A/B 的第一件事，不是跑候选，而是证明"基线臂的产物 = 参考产物"。**

典型形态：某轮的两条臂都跑在同一个（被残留态污染的）库上，因此**同窗差值仍然有效**，但两者**绝对产物都
不等于正典**（产物字节数与校验和见会话产物归档 `{run_results_dir}/archive/`）。后果有三层：

1. **绝对数字不可引用**：任何"本档 e2e = X"的外推都描述了一个从未产出参考产物的状态；
2. **会被读成优化空间**：一条"本档比交付路径慢"的结论，若同工具 profile 显示那一 step
   的设备侧两臂几乎相等（逐算子清单一致）⇒ 该差值根本不在设备侧；
3. **差值仍可用**：唯一变量确实只有树，所以**差值**结论不受影响——但必须在记录里写明
   "本次 A/B 的基线非参考态，差值有效、绝对值不可引用"。

**执行清单（A/B 之前）**：基线臂产物/字节数与**参考值**逐字节比对（md5 或计数）；不等则**先定位再测**，
不要"先跑起来再说"。**A/B 之后**：两臂各自的产物在臂内一致（4/4 同 md5）才算确定性成立。

## 11.1 交付的验证/门禁脚本必须自证"能在目标平台上跑"（2026-09-20 现场）

**规则**：任何作为**判据**交付的脚本（gate / 校验器 / 对照脚本），在它被当作证据之前必须自证四件事；
缺任一项 ⇒ 该脚本**不是证据**，复核者按未验证退回（口径同 §8.6：**先证明它能跑、能失败**）。

| # | 要证明什么 | 交付物里必须出现 |
|---|---|---|
| 1 | **平台归属** | 明确写出它**只能/必须在哪个平台跑**（POSIX / Linux 容器 / Windows；是否需要 `/dev/shm`、NPU、特定框架） |
| 2 | **互相依赖** | 它依赖哪些**外部前提**（目标主机可达、某目录已暂存、某个包已安装）；**依赖不可达时要显式判"无法判定"**，不得静默降级为"通过" |
| 3 | **可运行自证** | 一条**最小用例**的命令 + 退出码 + 环境指纹（`sys.platform` / python 版本 / 关键目录是否存在），并发进回执（模板见 `../../model-auto-optimization/workflows/references/dispatch-templates.md`） |
| 4 | **路径可解析** | **不得**把本机绝对路径写成唯一默认值；输入路径从 CLI 参数或环境变量取，缺失即**报错退出**（写死默认值 = 换台机器就静默跑错对象） |

**判读纪律（两句话定生死）**：

- **「跑不通」≠「跑过但失败」，更不是「通过」**：目标平台不可达时，结论只能写
  **"未证明"**，并给出不可达的证据（例如两个端点 TCP/22 均超时、本地无 `/dev/shm` / `wsl` / `docker`）；
- **平台语义属"被测对象的性质"，不是"环境的抱怨"**：若被验证的机制要求某平台语义
  （本仓实例：`SharedMemory` 的名字存活 = POSIX 语义），必须**先证该语义在本平台成立**，
  否则该平台上的全部读数与"通过"都无意义（同源纪律见 §8.5 基线自证、§8.7 血统门）。

**执行**：`scripts/check_gate_script.py <交付脚本/目录>`（本技能自带、零依赖）机械检查第 1/3/4 条
并报 `error/warn`；第 2 条（外部依赖与不可达处置）仍需人读，脚本只列"无法机检项"。
第 4 条只判**代码行**里的默认值：docstring 与夹具字面量**内部**的举例按文本跳过（否则门禁会
对自身举例自报假阳性）；这类夹具**落盘成文件后**仍是代码，照常被抓。
**自测**：`python scripts/check_gate_script.py --selftest`（负样本必须被抓到、合规样例 0 违规）。

**失效信号**：门禁脚本改判据、或目标平台/依赖发生变化（换容器运行时、换远端路径、换 Python 版本）后，
第 3 条的最小用例必须**重跑一次**；重跑不过 ⇒ 该脚本此前的"通过"结论作废。
