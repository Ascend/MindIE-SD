# 证据工具箱：三证、md5 双证据、忠实度对照、profiling 三张表

本文件回答：**每个数字要带什么证据才算可信，以及怎么采。**

内容索引：§1 三次证明 → §2 md5 双证据 → §3 忠实度对照（门禁盲区补救）→
§4 日志 `t=` 污染判据 → §5 profiling 三张表（同窗口）→ §6 判读规则。

---

## 1. 三次证明：HTTP 200 + 字节数 + 日志行

写进报表的性能数字必须同时具备这三样，缺一不可：

| 证据 | 作用 | 失败时会怎样 |
|---|---|---|
| HTTP 状态码 | 请求确实成功 | 500/超时被当成"跑完"，得到一个假 e2e |
| 产物字节数 | 产物量级正常 | 错误页/空响应（实测实例：全部 500，产物只有几百字节量级）被当作产物 |
| 日志行 | 能解释数字来源 | 无法区分"配置生效"与"静默回退" |

补充：日志行里要专门 grep **静默回退**的痕迹（实测遇到过"唯一完成的臂静默回退、
`latent_shape=None`、每次调用都退化为基线"这种情况：e2e 与基线一致，
如果不 grep 这行，会把它当成"该优化无收益"，而真相是"该优化根本没生效"）。

## 2. md5 双证据（无损声明的底线）

声明"无损/逐字节一致"需要两个证据：

1. **产物 md5**：同一臂多次请求 md5 必须一致（实测判据：4/4 请求一致），
   且与基线产物 md5 相同；
2. **关键中间张量 dump md5**（或 `torch.equal` 计数）：产物 md5 相同可能是巧合（例如编码器抹掉了差异），
   中间张量相同才说明计算路径没有引入差异。实测实例：音频张量 dump md5 与基线一致
   （`max|Δ| = 0`），配合产物 md5 才能说"逐字节无损"。

再进一步：如果声明"分片/并行无损"，额外做 **分片 vs 整段的对拍**——
在 CPU 上要求 `max|diff| = 0`（bitwise），这样后续在 NPU 上出现差异时，可以立刻判定
"是平台差异，不是算法差异"。

## 3. 忠实度对照：md5 门禁的盲区补救

**盲区**：所有臂共用同一个（可能有缺陷的）实现时，md5 一致只说明"优化没改变产物"，
不说明产物是对的。实测的真实翻车：解码器选错了权重布局（预览版），
全部臂 md5 稳定一致、门禁全绿，但产物与真值几乎无关（相关系数近零）。

**做法**：

1. 选一个**独立实现**当真值（另一个解码器/参考实现/高精度路径）；
2. 同一输入分别解码，对齐后计算 **MAE（以 0–255 为单位更直观）与 Pearson r**（可再给 4×4 池化后的 r）；
3. 把结论写进报表：实测实例——官方时间维解码器 vs 真值 **MAE 在 0–255 尺度上很小、相关系数接近 1**
   （4×4 池化后更高）判为**忠实**；另一个预览档 **相关系数几乎为零** 且含 **大量冻结帧**（相邻帧几乎相同）；
4. 若真值实现太慢，只跑**尾段切片**（例如全局帧 238–361）也能给出判据——实测真值侧就用了尾段切片。

**额外信号**：帧间差（`d_prev`）长期接近 0 的"冻结帧"、通道均值异常（某通道翻倍）、
高频能量骤降，都是"看起来通过门禁但实际坏了"的可用探测器。

## 4. 日志 `t=` 会被污染：判据与处理

**污染源**：profiler 采集阶段（trace dump 落在 worker 的计时窗口内）、并发请求排队、
共享机器邻居负载。

**实测实例**：某臂 arm 日志 `t=` 被污染（读数数十秒量级），但同一请求的服务端阶段账 `forward` 只有十几秒，
服务端请求节拍也在十几秒量级 ⇒ 日志 `t=` 不可用。

**判据（按优先级）**：

1. 服务端阶段账（管道内 stage 计时）> 服务端阶段时间戳节拍 > arm 日志 `t=`；
2. 用节拍交叉验证：相邻两个请求的 forward 时间戳差 ≈ 真实 e2e（同环境实测为十几秒量级）；
3. 冲突时**以服务端为准**，并在报表里写明"该臂 arm 日志 t= 受污染，未采用"。

**顺带**：交付开销（`e2e − forward`）也要用服务端口径算，否则会把 profiler 开销算成交付开销。

### 4.1 先数「每请求几行」，再切片（日志形状会造出幽灵基线）

同一段日志里**一个请求往往对应多行**（管道 profiler 常**每 rank 打一行**），于是
「排序后取尾部 N 行」这类切片会**跨请求**取数，且常常正好落在**冷请求**（首个请求最慢）上。

**实测实例**：某管道 profiler 每请求打**每 rank 一行**（8 卡 ⇒ 一个请求 = 8 行），
`sort -n | tail -4` 于是取到**第一个（冷）请求**的那几行，凭空造出一个偏高的「基线读数」✗ ——
该读数一度被当成基线写进对比。

**规则**：

1. 切片前**先确认每请求行数**（是否等于 rank 数、是否含预热行/汇总行）；
2. **按请求序号显式点名热请求**取数，不要靠排序取尾部；
3. 报表里**写明数字来自哪个请求**（冷/热）；冷启动**单独记录**、不进均值。

**复核**：换管道/框架版本、rank 数或日志格式后重数一次行数；判据 = 任取一个请求号，
其行数应等于该管道的已知每请求行数（多或少于 rank 数都要先解释清楚，再切片）。

> 同族的另一半在 `../../profiling-analyze/references/performance-analysis-methodology.md` §2.1：
> **同一行里每个 rank 各一个值**时，`head -1` 会取到不同的 rank（跨 run 对比时收益被夸大）。
> 两处互补、都不复述对方：**本节管“一个请求占几行”，那一节管“一行里有几个 rank”。**

### 4.2 失败日志的行数是**标定**出来的计数单位（别把 `grep -c` 当失败次数）

- **事实**：同一类失败会产出**固定行数**的日志 —— **行数与请求数无关、与臂无关**；于是
  「含签名行数 ÷ 每次失败行数」可以跨历史日志反推失败请求数（实测：行数按失败请求数成整数倍自洽）。
- **规则**：**先标定"一次失败产出多少行"，之后才允许用行数当计数**。直接把 `grep -c` 当"失败次数"，
  在异常多帧 / 多 rank 重复打印时会**高估数倍**（本例直接计数会高估数十倍）。
- **标定方法**：制造**恰好一次**失败（单请求、已知 rank 数），数它实际产出的行数；
  再制造两次验证**线性**（行数应成整数倍）；rank 数变化后**重新标定**（多 rank 会重复打印）。

### 4.3 计数型 grep：锚定"只有成功路径才打印"的行 + 用独立计数器交叉验

- **事实**：用 `grep -c '<方法> <路径>'` 统计"发了几次请求"，**启动阶段的注册行**
  （形如 `Route: <路径>, Methods: POST`）也被计入 ⇒「请求数」恒等于「注册行数 + 真实请求数」；
  据此可把一个**根本没跑起来的臂**（进展类日志行数为 0）误读成"已发若干次请求"。
- **规则**：
  1. 统计"**发生了几次**"时，模式必须锚定到**只有成功路径才会打印**的那一行
     （例如 HTTP 状态行 `HTTP/1.1 200`），**不要**锚 URL / 路由 / 方法名；
  2. 用**同一份日志里另一个独立的、不可能由启动阶段产生的计数器交叉验**
     （例如每步的进展行数）——两者不一致时，**先判"任务没跑起来"**，再谈"请求失败"；
  3. 启动 / 注册 / 握手阶段的日志会污染**几乎所有**"计数"型 grep：写统计前先问一句
     "这一行在启动阶段会不会也出现？"

## 5. profiling 三张表（统一到同一窗口）

要回答"性能占比长什么样"，必须让三张表来自**同一次运行**（否则又是跨窗口拼接）：

| 表 | 数据源 | 口径要点 |
|---|---|---|
| 整请求层面 | 阶段计时 + `curl` e2e | 逐请求列出编码/去噪/解码/forward；交付开销 = e2e − forward，并分解（编码/传输/HTTP） |
| 设备侧内部 | 单步 trace 的 `op_summary` | 按算子族聚合；**同时给"含重叠"与"暴露"两个口径**（多流重叠时设备 busy 总和可 >100% 跨度） |
| host 侧 | `api_statistic` | 按 API 族看 launch / 同步 / 特定算子（实测三大 API 族合计占九成量级） |
| 解码段 | 整请求 trace 的尾段窗口 | 用该段的算子（卷积/resize/激活）首末时间界定窗口，避免把上一步的算子算进来 |

**采集纪律**：

- torch_npu 自带导出在同环境下可能不完整 ⇒ 用 `msprof --export=on --output=<采集目录>` 补导出；
- 单步 trace 与整请求 trace 用不同选举点（例如第 N 次 forward / 第 M 个请求），保证两次采样不重叠；
- 采样请求的 e2e 不计入均值（见 §4）。

**判读规则**：

- 先看受限类型：算子的 `aicore_time` ≈ `Task Duration` 且 cube 利用率 97–99% ⇒ **算力受限、已到屋顶线**，
  此时"调 kernel"没有空间，只能减少工作量或降精度；
- 若某个算子被标为"少写/未写尾部"（输出后半段是陈旧数据）⇒ 这是平台缺陷，
  规避方式见 §6；
- 占比高 ≠ 值得优化，先算天花板（见 SKILL.md 坑 3）。

## 6. 平台缺陷的识别与规避（实测真实案例）

**症状**：产物尾部固定位置开始塌陷（画面变平/通道异常），而 CPU 同代码同输入完全正常。

**定位路径**（逐层收敛，值得复用）：

1. 先排除自家改动：不同臂产物 md5 是否全同（全同 ⇒ 改动无关）；
2. 再排除输入/精度：把可疑输入逐位对比（实测证明 fp16 autocast 与 fp32 **逐位相同**，
   于是"fp16 精度"假设被证伪）；
3. 与权威实现逐项对拍（算子结构、归一化、padding/裁剪语义）；
4. **逐 block 打点**：在每层后打印统计量与与 CPU 的偏差，找第一个分叉的层；
5. **隔离该算子 + 阈值实验**：同一算子喂不同 batch，二分出触发条件
   （实测：某阈值以下正确、以上错误，坏区起点固定在某个绝对索引 ⇒ 是"少写尾部"，不是数值漂移）；
6. 用等价实现/分段调用验证规避（实测：等价重写与分段都干净；但等价重写需要额外分配大张量，
   在 8 卡服务内直接 OOM ⇒ 最终选**分段 + 携带状态**，且 CPU 上 bitwise 等价、峰值显存反而下降）。

**可复用的判据**：坏区内容在多次运行间**相关性 0.7–0.8（而非 1.0）** ⇒ 读的是未初始化/陈旧内存，
而不是确定性数值误差。这个判据能把"平台缺陷"与"算法误差"分开。

## 7. 维护与更新

- **更新触发条件**：§1 三证据项、§2 md5 双证据（产物 md5 + 关键中间张量 dump）、§3 忠实度对照的指标
  （MAE 与 Pearson r）、§4 `t=` 污染的优先级链、§4.1 日志形状（每请求行数）、
  §4.2 每失败行数标定值、§4.3 计数型 grep 的锚点行、§5 三张表的数据源（阶段计时 / `op_summary` /
  `api_statistic` / 整请求 trace 尾段）任一改写；§6 的陈旧内存判据（跨运行相关性显著低于 1）随版本重判。
- **复核方法**：对某臂按 §4 做交叉验证——用相邻两请求 `forward` 时间戳差与 arm 日志 `t=` 比对，
  确认优先级链仍能筛出受污染读数；再按 §1 逐项核对同一次运行的 http 码、产物字节数与日志行，缺一作废。
  日志格式 / rank 数 / 框架版本变化后：**重数**每请求行数（§4.1）、**重标定**每失败行数（§4.2）、
  并确认 §4.3 的锚点行仍是"只有成功路径才打印"的那一行。
