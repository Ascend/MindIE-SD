# 同窗 A/B 协议与判定门槛

本文件回答：**怎么设计一次能下结论的测量，以及差值多小就必须闭嘴。**

内容索引：§1 口径定义 → §2 窗口设计 → §3 A/B/A 漂移校正 → §4 噪声地板与判定 →
§5 arm 脚本骨架 → §6 常见失败模式。

## 1. 先把口径和分母钉死

测量之前必须写清四件事，否则后面所有数字都可能被重新解释：

1. **e2e 定义**：单个完整请求的墙钟，包含哪些阶段（编码 + 去噪 + 解码 + 交付编码/落盘）？
   排除哪些（模型加载、服务启动、warmup）？
2. **分母（基线）**：加速比 = 基线 e2e ÷ 本行 e2e。**分母必须在同一张表里唯一**；
   如果表里混了两个血缘（例如早期 4 卡/50 步世代与后来 8 卡/4 步世代），
   要么各自单独一张表，要么在行里显式标口径——实测踩过：同一物理配置在两个血缘的表里
   分别显示两位数倍（分母是另一世代的窗口）与 1.00×（分母就是本窗自身），两者都对，混着读就全错。
3. **首步耗时**：warmup 之后第一个 step 的墙钟，与"平均每步"（= diffuse ÷ 步数）是两个口径，
   不要在同一列里混用（实测踩过：同列 7 行是平均值、2 行是首步观测）。
4. **步数 / 形态**：步数、分辨率、时长、帧数、seed。缺一项，跨天的数字就无法对齐。

## 2. 窗口设计

一个"窗口"= 一次连续占用同一批卡、不与他人争用的测量时段。窗口内包含若干**臂**（配置）。

**要点**（窗口内取数的四条硬要求）：

- 窗口内**必须**有控制臂（当前采纳档或未优化档），它就是本窗口的分母。
- 臂之间**串行**，每臂之间清理服务进程与锁文件、等待端口释放；并发跑臂会互相污染
  （集合通信、HBM 带宽、温度），同环境实测同一臂逐请求 `diffuse` 就有可测漂移，
  跨窗口漂移可达臂内逐请求漂移的数倍。
- 每臂请求序列建议 **1 冷 + 3 热**：冷启动单独记录（同环境实测冷启动显著高于热态），
  热态取均值或中位，**不要把冷启动混进平均**。
- 若某臂带 profiler（msprof / torch_npu profiler），**被采样的那一次请求单独标注并从均值剔除**；
  实测实例：被采样的请求 forward 明显大于同臂其它请求（约为其两倍）。
- 只有在差值 **远大于** 噪声地板时，才允许"一个窗口一个臂"的快测；否则同窗多臂或 A/B/A。

## 3. A/B/A 漂移校正

**什么时候用**：同窗对照的差值已经落在噪声里（实测实例：两臂读数差异远小于噪声地板），
但你有理由认为改动有真实收益。

**怎么做**：`base → arm → base`（前后两个 base 同口径、同请求数），
控制 = 前后两个 base 的均值，净差 = arm − 控制。

```text
base_1 = B
arm    = A（低于 B）
base_2 = B（复测同口径）
控制均值 = B
净差 = A − B = 负值（arm 更快）   → 可写进报表
```

**为什么有效**：窗口内漂移多为单向（升温/邻居负载爬升），前后夹一次可以把线性漂移抵消掉。
**代价**：3 倍卡时；只在"差值与地板同量级且结论重要"时用。

**必须同时报告的量**：两个 base 的数值（证明漂移不大）、arm 的数值、净差、
以及"同窗直接对比的原始差值"（让读者知道未经校正时它不可分辨）。

## 4. 噪声地板与判定表

同环境实测（8 卡、15 s 视频、4 步去噪口径）：

| 量 | 量级 |
|---|---|
| e2e 热态 | 零点几秒 |
| 相对收益 | 约 1% |
| 单臂内逐请求 `diffuse` | 数十毫秒 |
| 跨窗口 `diffuse` | 数百毫秒 |
| 冷启动 vs 热态 | 冷启动显著更高（差值远大于地板） |

判定：

- 差值 **> 3×地板** ⇒ 可直接下结论；
- 地板 ~ 3×地板 ⇒ 报"A/B/A 校正后 = X"，并给出原始不可分辨值；
- 差值 **< 地板** ⇒ 写"不可分辨"，**不要**写成收益；也不要用"看起来快了一点"代替数据。

## 5. arm 脚本骨架（把要带回的信息一次带全）

```bash
# 1) 固定口径与指纹
TAG=armname; PORT=8210; CARDS=0,1,2,3,4,5,6,7
export <关键 env 或门控>=<值>
echo "[$TAG] START $(date '+%F %T') <配置指纹>"

# 2) 清理上一臂（否则会静默复用旧服务）
for _ in $(seq 1 20); do pgrep -f "serve.*--port $PORT" >/dev/null || break;
  pkill -9 -f "serve.*--port $PORT"; sleep 2; done
rm -f "$LOG"

# 3) 起服务（nohup，日志落盘）+ 健康检查（带超时与早错探测）
# 4) 1 冷 + 3 热请求：每次打印 http 码 / t= / 字节数
# 5) 收尾：md5 全部产物；grep 阶段账；grep 配置指纹（权重/门控是否真生效）
# 6) 清理服务与 worker 进程
```

三条硬要求：

- 请求行必须带 **http 码 + 字节数**（只看 `t=` 会把 500 当成功）；
- 收尾必须打 **md5**（无损声明的前提）；
- 收尾必须 grep **配置指纹**行（例如加载了哪个权重、门控是否生效、是否走了降级路径），
  否则"配错了"会伪装成"优化无效"。

## 6. 常见失败模式

| 现象 | 真因 | 处理 |
|---|---|---|
| 某臂数字离谱地大 | 上一臂服务没清干净 / profiler 采样 / 邻居负载 | 查进程、查 profiler 标记、重跑该臂 |
| 同配置两天数据对不上 | 跨窗口漂移 | 归因到漂移，不要写成配置差异 |
| 差值很小但方向一致 | 可能是真收益 | 用 A/B/A 或增重复次数把地板压下来 |
| 加速比与 e2e 不自洽 | 分母不同 / 列串了 | 重算 `基线 ÷ e2e`，逐行核对 |
| "无损"但结果看起来一样 | md5 只能证明没变 | 补忠实度对照（见 evidence-toolbox） |
