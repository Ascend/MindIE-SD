# 总览主表三轮打回复盘（可读性契约 §2.8 的缘起与判据）

> **性质**：事故复盘（结论类）。**真源分工**：规则的**规范文本** = `overview-report.md` §2.8；
> **复核清单** = `report-contract.md` §7/§8；**机械出口** = `scripts/report_lint.py`
> （`--selftest` 为规则自身的回归）。本文件只回答"**当时为什么没生效**"与"**逐条缺陷串是什么**"。
>
> **加载时机**：写/刷新总览主表**之前**（与 `overview-report.md` §2/§2.8 同读）；
> 也作为 §2.8 判据的**失效信号**依据——下面每条根因都对应一条机械判据。

## 1. 事件

某模型（MiniMax-H3 × vLLM-Omni 0.28）的性能优化任务产出的 `overview_report.md`，其**主表连续
三轮被人工评审打回**；同期 `report_lint.py` 一直返回 `error=0`，`audit_report.py` 返回
`error=0 warn=0`——**两道机器门禁全程放行**，全部问题由人肉发现。

## 2. 三轮拒绝意见与对应的具体缺陷（逐条证据）

| 轮次 | 评审要求（要点） | 文件里当时的实际写法（缺陷串） |
|---|---|---|
| 1 | 特性名不可懂：含内部方案代号、暂存树名、括号实现细节；说明列不解释这些指代。**特性名词汇是固定的**，具体内容只能进说明 | 特性名列出现 `O2「更少更胖的 program」`、`上排 + 跨层/多行/前缀融合组（C2 + C4 + C3b + E5 + LoRA-apply）`、`kernel融合（自编译 kernel revision）`、`并行的解码分片（音频 VAE 时间维 2 片）`、`USP8 8 卡未优化` |
| 2 | **不得用临时生成的标识符表意**（临时环境变量改动交付时会被撤回）；本文档给优化工程师看、不是给工具解析；多 agent 交接类内容另置**附录**统一显示 | 正文（附录之前）出现 48 个 `OMNI_H3_*` + 8 个 `MINDIESD_*`，另有 lane 编号（`lane G`）、窗口/臂编号（`window N`、`arm L2`）、账本条目号（`Round NN`） |
| 3 | `kernel融合` 行的说明必须写清**融合了什么 / 在什么位置 / 融合后性能变化**，且**简明**；细节移到后面的**「最佳路径下的特性说明」**节 | 说明单元格 600–900 字、以门禁名开头（`OMNI_H3_*` / `MINDIESD_*`）、**每 step（ms/step）收益被埋在中段或缺失**；**无附录**；**无「最佳路径下的特性」详情节** |

## 3. 契约当时**已经**要求了什么（所以这不是"没想到"，是"没落地"）

- `overview-report.md` §2 列 2 规则已写：特性名只允许固定名词表，**禁止自定义名/实现方法名**。
- §2.1 已写：内部代号 / 产品词 / 档位形容词 / 实现方法**一律不得作特性名**（并逐一点名
  `frontier`、`hq`、`kernel 融合(FA/mindiesd)`、`编译`、`Offload` 等），且"选项/参数一律入说明列"。
- §7 已写：特性名列**禁止括号、配置值、状态词、引用**；参数/档位/状态一律移入说明列。
- §2.3 已写：叠加链须逐行呈现，每行 = 上一行 + 一个新特性。

⇒ **规范文本不缺**；缺的是"写表那一刻会不会被拦住"与"有没有地方放细节"。

## 4. 根因逐条核对（假设 a–e）

| 假设 | 是否成立 | 证据与修正 |
|---|---|---|
| (a) 没有任何机械检查 | **成立（主因）** | `report_lint.py` 当时只查表头列序 / 必填单值 / 锚点禁估算 / 质量列语义；**特性名词汇、说明列内容与长度、附录与详情节齐备性全都不在检查范围**。故 `O2「…」` 这类特性名、900 字说明列、无附录都能 `error=0` 通过——`audit_report.py` 只做表格结构与数值自洽，同样结构性放行（`error=0 warn=0`） |
| (b) 写表时没有加载 §2.1/§7 | **成立（主因）** | `SKILL.md` 当时的接线把 `overview-report.md` 的加载时机写成"闭环复验 / 产物归档时"，`report_lint.py` 写成"闭环收尾"——**都是写完表之后**。写表是"逐格填字"的动作，名词白名单写在另一个 §2.1、单元格纪律写在 §7，写表时手上没有这份清单 ⇒ 规则只在事后被引用，不参与写入 |
| (c) 没有规定的紧凑说明写法 | **成立** | 规范只给了说明列"必含项"清单（使能子特性/口径/指针），**没有给出"三段式 + 长度上限"**。于是作者的最优策略变成"多写点更安全"，产出 600–900 字单元格并把结论埋在中段——这正是"越详细越安全"的激励失灵 |
| (d) 没有交接元数据的指定去处，也没有详情节 | **成立** | 规范没有"附录"这一承载位（开关/代号/证据指针），也没有"主表放不下的长文去哪"的规定 ⇒ 交接元数据只能挤在说明列、机制与 shape 细节也只能留在表内。**需要区分两个成因**：评审第 2 轮的原话是"多 agent 交接类内容**可以**移到附录统一显示"（备选方案），而"临时标识符不得用于表意"是**硬要求**；两者都指向附录，但前者是许可、后者是禁止 |
| (e) §2.1 与 §2.3 的"同名只许一行"张力未解 | **成立（但为次要成因）** | §2.1 写"同一特性名在总览表**只允许一行**"，§2.3 又强制叠加链**逐行**呈现（同一特性名必然重复出现，如多行 `并行 + kernel融合`），**两处从未说明谁优先**。作者无法判断该不该重名 ⇒ 一种退化写法就是"把不同落地内容塞进特性名"（`kernel融合（自编译 kernel revision）`）来避免重名，正好触发第 1 轮打回 |

**结论**：五条全部成立，但**权重不同**——(a)(b) 是"规则没被机械执行、也没在写表时到达写作者"，是主因；
(c)(d) 是"规则本身缺写法与承载位"，是主因；**(e) 是次要成因**（它解释的是"为什么特性名里长出了
实现细节"这一条路径，而不是全部打回项）。

## 5. 修复判据与落点（每条根因 → 一条机械判据/一个接线点）

| 根因 | 修复 | 落点 |
|---|---|---|
| (a) 无机械检查 | 主表内开关名 / 裸代号（error）、说明列长度 >350 字（error）/>180 字（warn）、`kernel融合` 行的位置与性能标记（error）、附录三节与详情节齐备且次序（error）、正文开关名（warn）；`--selftest` 14 用例（含"证据文件名不得误报"与"契约内标识符不得误报"两个回归） | `scripts/report_lint.py`、`scripts/report_lint_cases.md` |
| (b) 写表时未加载规则 | `SKILL.md` 标准回路新增**强制触发**："写/刷新总览主表时"先读 `overview-report.md` §2 + §2.8，写完**立即**跑 `report_lint.py`（error=0 才继续）；reference 清单里 `report_lint.py` 的加载时机由"闭环收尾"改为"写/刷新主表后立即跑" | `SKILL.md`（"闭环复验"与 Reference Files 两处） |
| (c) 无紧凑写法 | **§2.8.1 紧凑三段式模板**：① 融合/调整了什么 → ② 在什么位置 → ③ 每 step 性能变化（非逐步项给 `s/请求`），单位必须显式；目标 ≤180 字、上限 350 字（机制可校验） | `overview-report.md` §2.8、`report-contract.md` §7 |
| (d) 无承载位 | **§2.8.3 必带详情节**「最佳路径下的特性详解」（主表表头注必须指向它）+ **§2.8.4 必带附录**（开关对照表 / 内部代号对照表 / 证据指针）；开关名与代号**不进正文**，正文引用只作可追溯性（warn） | `overview-report.md` §2.8、`report_lint.py` `REQUIRED_SECTIONS` |
| (e) 张力未解 | §2.1 增补裁决：**"同名只许一行"只约束同一特性的独立成行，不约束叠加行；§2.3 优先**——判据 = 该行承载的是"新特性"还是"同一特性的新落地内容"；`report-contract.md` §1 给出复核时的一行判据 | `overview-report.md` §2.1、`report-contract.md` §1 |

## 6. 复核方法 / 失效信号

- **复核方法（任一改动后按序跑）**：
  1. `python scripts/report_lint.py --selftest` —— 负样本逐条必须被触发，合规样例必须 0 error/warn；
  2. `python scripts/report_lint.py <已定稿报表>` —— 必须 `error=0`（新规则不得把已修好的报表判错）；
  3. `python scripts/audit_report.py <报表>` —— 结构 + 数值须 `error=0`。
- **失效信号（出现其一即本条复盘与 §2.8 判据过期，须同步复核）**：
  1. `report_lint.py` 的 `SWITCH_FAMILY_PREFIXES` / `NOTE_CAP` / `NOTE_TARGET` / `REQUIRED_SECTIONS`
     或 §2.8 文本任一处变化 ⇒ 另两处必须同改（否则机械判据与规范文本会互相矛盾）；
  2. 新增开关族（前缀不在 `SWITCH_FAMILY_PREFIXES`）⇒ 机械判据会**漏检**该族，须登记前缀，
     否则"开关名不进正文"退化为人工纪律；
  3. 主表列数/列语义变化 ⇒ §2.8 三段式中的"位置/性能标记"判据须重新核对列位（说明列下标）；
  4. 出现**新形态**的可读性打回（人审发现而 lint `error=0`）⇒ 按本文件格式补一条根因与判据，
     并加 `--selftest` 用例（**人审发现的每一类问题都必须变成一条机械判据**，这是本复盘的唯一行动项）。
