# 方法：低秩适配器（LoRA）离线合并进权重的精度判据与形态选择

> **作用域（先读 · 强制）**：本文件的判据与"哪种形态更优"来自**一次「芯片 + 拓扑 + 软件栈 + 模型」组合**的实测；
> 正文只写**判据 + 现场取数方式 + 归档指针**，来源环境的具体取值（设备与代际、卡数与拓扑、版本、模型几何、绝对读数）
> 一律留会话产物归档：`{run_results_dir}/archive/`。
> **换任一维都必须本地重测**后再沿用本文任何结论与"最优形态"。
> **分工**：本文件回答「增量能否在被合并后存活、该选哪种形态、用什么收口」；量化编码/舍入/scale 粒度/退化块规则见
> `../SKILL.md` §一/§二；「该不该开量化、开哪一档」见 `../../dit-perf-opt/SKILL.md`；服务侧摆位与请求/启动参数见
> `../../framework-integration/SKILL.md`；合并省下的量能否与别的融合候选相加见 `../../fusion-scope-analyze/SKILL.md`。

## 0. 何时读：任何「把运行时计算折进权重」的候选

- 命中场景：低秩适配器（LoRA / adapter）离线合并进基座权重、把缩放/偏置折进相邻线性层、
  把量化残差折回权重、权重离线重算类改动——**共同点是"把运行时的算子链换成权重里的一份预计算结果"**。
- 命中即必须同时回答三问：① 代数上是否**精确可算**（§1）；② 合并后增量能否在**服务精度**下存活（§2）；
  ③ 选哪种**形态**（§3），并用什么**收口**（§4）。

## 1. 合并代数与「去冗余」定位

```text
W' = W + (α/r) · B · A          # 精确可算：fp32 累加，最后按目标 dtype 存储
```

- **代数恒等**：`W·x + (α/r)·B·A·x ≡ (W + (α/r)·B·A)·x`，无近似；增量与 `x` 无关 ⇒ 可以离线算一次。
  分量级规定（`α`、`r` 的关系）与 PEFT `merge_and_unload` 的语义一致，**不要自创缩放约定**。
- **合并的收益不是"加速"，是"删除"**：合并后该链在运行时**整条消失**（down-GEMM / up-GEMM / 逐元素加，
  以及它们引发的布局拷贝与量化调用），**运行时代价≈0**。因此它属**去冗余类**优化：收益量级由
  **该链原本的运行时代价**决定，而不是由"某个算子做快了多少"决定（与 `fusion-scope-analyze` 的"移除算子"判据同源）。
- **判据（运行时是否真的零残留）**：以 **op census** 为准——合并前后两臂各取一次单步 profile，
  按 `(算子名, 输入形状)` 汇总，该链的签名应**成规模消失**，而不是只降几个百分点。
  **只凭"启动参数里不再有适配器"不算证据**（开关被移除 ≠ 该链不在当前路径上）。
- **契约类事实（可写死）**：合并产物的 loader 兼容性 = `key 集合 / 形状 / dtype / index 的 weight_map` 与原始 ckpt
  **逐项一致** ⇒ **drop-in，无需改 loader**。判定方法：结构校验脚本对全部 key 做集合差、形状差、dtype 差，
  并与原 index 的 `weight_map` 做等值比较——三项均为 0 才可声称 drop-in（服务侧要改的只有"指向哪个模型根"与
  "是否还发适配器相关参数/请求字段"两处**声明**）。
- **承重前提（先判，别默认）：基座是"在 ckpt 里已量化"还是"在 load 期量化"** —— 它决定"合并的是什么矩阵"：
  - 判定法：① 读 index 的 `metadata.total_size` 是否满足 `总字节 == 元素总数 × 每元素字节数`
    （满足 ⇒ 全张量同 dtype，不存在"1 字节载荷 + scale"的组合）；② 按后缀清点是否存在
    `*.weight_scale` / `*.scale` 一类 key 与 fp8 dtype key（存在 ⇒ 量化已序列化）。
  - 若为 **load 期量化**（ckpt 是高精度、装载后由量化方法就地量化），唯一干净的合并路径是
    **高精度离线合并 → 让 loader 量化合并后的矩阵**；服务端于是算 `quant(W+Δ)`，而**不是** `quant(W) + Δ`
    ——这正是 §2 判据的适用场景（也是"合并后为什么可能不等价"的根因）。
  - 反向可选路径：把合并产物**预先量化**成低精度（fp8 + scale key）走序列化量化类。

## 2. 精度存活判据（核心）

**判据式（比值，不含绝对读数）**：

```text
存活能力 ≈ (增量的相对量级 ‖Δ‖/‖W‖)  相对  (该精度下的相对量化半步)
```

- 相对量化半步由**格式本身**决定（契约类事实，可写死）：e4m3 类 8 位格式只有 3 位尾数 ⇒ 半步相对量级约 `2^-4`；
  bf16 有 8 位尾数 ⇒ 半步相对量级约 `2^-9`。二者相差若干数量级 ⇒ **同一个增量在两种精度下的命运完全不同**。
- **不等价时的签名（结论形态不是"误差小一点"，而是"换了实现"）**：当 `‖Δ‖` 显著小于一个半步时，
  ① 绝大多数元素**根本不跨舍入桶**（合并前后逐位相同）；② 少数跨桶元素**跳的是整个桶宽**，而不是 Δ 本身。
  ⇒ 逐元素看，合并结果是**稀疏的整步跳变**：其期望等于 Δ，实现却是噪声。此时
  `quant(W+Δ) − quant(W)` 的范数会**大于 Δ 自身**、且与其**方向相关性很低**（本组合观测：范数比为个位数倍、
  相关性在名义上很弱）——这条签名比"平均相对误差"有诊断力得多。
- 反之，若增量相对量级与一个半步**同量级或更大**，跨桶元素成片出现，合并即近似精确施加（bf16 属于这一侧）。

**判定法（脚本级现场取数 · 三臂对拍）** —— 必须**同进程、同数据**，且用**真实服务 GEMM**（不是自写模拟器）：

1. `faithful`：`y_ref = serve_gemm(x, W) + 精确施加的增量`（= 生产链路当前的写法）；
2. `merged`：`y_mrg = serve_gemm(x, W + bf16(B@A))`（两个权重都按服务装载路径**同样地**打包与量化）；
3. `adapter_off`（**控制臂，必做**）：`y_off = serve_gemm(x, W)`——没有它就**无法归因**（见 §4）；
4. 权重侧另取一次「反量化权重」对比：用 `K×K` 单位（one-hot）激活喂同一个服务 GEMM，返回值即该 GEMM 实际看到的
   `dq(W)`（one-hot 在 e4m3 下可精确表示），由此得到 `dq(W+Δ) − dq(W)`，**与 scale 的打包方式解耦**；
5. 报**三个比值**（逐层做，报 min / median / max 与**是否存在例外层**）：
   `‖dq(W+Δ) − dq(W)‖ / ‖Δ‖`、`cos(dq(W+Δ) − dq(W), Δ)`、`‖y_mrg − y_ref‖ / ‖Δ‖`。

**读法**：拿 `‖y_mrg − y_ref‖ / ‖Δ‖` 与 `1.00` 比 —— `adapter_off` 的该比值按构造**恒为 1.00**，
所以 **> 1 的含义是"合并比直接关掉适配器离参考更远"**；此时**不得**写成"基本无损"（只能写成"不等价，见 §4 收口"）。

**必须避开的假证据（每条都带复核方法）**：

- ❌ **用自写量化模拟器（CPU emulator）当证据**：它通常落在**与真实算子不同的舍入网格**上。
  **复核方法**：取一张真实权重，比 `‖模拟器反量化权重 − 真实算子反量化权重‖ / ‖真实值‖`；若该差异与
  "一次量化误差自身的相对量级"同阶 ⇒ 网格不同 ⇒ 该模拟器的**量化列全部作废**（其 bf16 列若为严格精确的整数
  RNE 实现仍可用）。实测起点：模拟器曾给出比真实算子大数倍的结论，改用真实算子后被推翻。
- ❌ **基线选错**：基线只能是 `faithful`；`adapter_off` 是**归因控制臂**，不是"更差的基线"，也不能拿另一个有损档代替。
- ❌ **只报平均相对误差**：该情形的差异是"稀疏 + 整步"，均值恰好等于 Δ，会被误读为"很准"；必须同时报分布形状
  （跨桶元素占比、范数比、方向相关性）。

## 3. 形态选择判据（三形态）

| 形态 | 权重存储 | 运行时代价 | 等价性 | 代价 |
|---|---|---|---|---|
| ① **运行时施加** | 基座权重 | 该链**完整付费**（device + 每次调用引发的 host 下发） | 最好：唯一"精确施加"形态 | 收益拿不到 |
| ② **高精度合并 + 高精度服务** | 2 字节/元素 | 该链消失，但**所有 GEMM 从低精度退回高精度** | 存活（§2：增量与半步同量级） | 付**格式代价**：GEMM 吞吐与权重带宽同时变差 |
| ③ **低精度合并 + 低精度服务** | 1 字节/元素 | 该链消失，GEMM 与显存与交付档**完全一致** | **不等价**（§2 的稀疏整步跳变） | 需过 §4 的**可用性**收口 |

**形态选择（按序执行）**：

> 形态① 这条链自己的成本结构（算力 / 访存 / 下发三分，"上限在哪、该减算子还是该把算子做快"）归
> `../../dit-perf-opt/SKILL.md`，本文件只把它当"合并能省下多少"的输入，不重复其判据。

1. **目标档是低精度权重** ⇒ 在 ② 与 ③ 之间选，**"高精度合并 + 低精度服务"（③）通常优于"高精度服务"（②）**：
   两者都让该链消失，但 ② 额外付出格式代价；本组合观测（作用域见文首，须本地重测）该**格式代价与合并收益同量级、方向相反**
   （纯高精度服务会把收益吃掉、甚至更慢）⇒ **② 只是首证形态**（用于回答"合并能否把模型救活"），
   **不是目标形态**；首证在 ② 上做，采纳在 ③ 上做，并用 §4 收口 ③ 的可用性。
2. **目标档本就是高精度权重** ⇒ ② 即终态，且 §2 判据天然落在"存活"一侧。
3. **排序固定**：**先证可用性，再比性能**。③ 的"不等价"是**已知事实**而不是否决理由——能否采纳取决于 §4 的
   服务端可用性收口，不取决于 §2 的数值距离有多远。
4. **磁盘与产物流转要计入**：合并产物几乎要重写**全部**权重（不是只改被合并的那几个张量）⇒ 磁盘代价
   量级 = 权重总字节；可选把它预先量化成 1 字节/元素以**减半**（只省磁盘与装载时间，**不改变 §2 的数值**）。

## 4. 判据修正纪律（纯数值研究判不了可用性）

**规则：纯数值研究只能推翻「等价性」主张，不能推翻「可用性」主张。**

- 数值研究能给出的结论上限：*"合并结果不是适配器的 faithfulness 复现"*、*"某形态下增量被舍入吃掉"*；
- 数值研究**给不出**：*"合并后的模型生成塌陷 / 不可用"* —— 那必须由**服务端产物级 A/B + 产物健康度**收口；
- **正反例（同源数据的两个方向）**：
  - **反例（数值判"更远" → 服务端实测产物健康）**：离线对拍给出"距参考比直接关掉适配器更远"的结论并据此建议不落地；
    随后服务端 A/B 实测该形态**产物健康**（内容健康度落在同窗健康带内），而"关掉适配器"那一臂才是**塌陷**臂
    ⇒ **"距 faithful 远" ≠ "塌陷"**，原结论在产物层面被证伪（本组合即为此情形）；
  - **正例（数值判"存疑" → 服务端确认不值得）**：若服务端 A/B 显示"合并臂 ≈ 关适配器臂、两者都远离 faithful 臂"，
    则数值结论被确认，该路线不落地。⇒ **决策判据写在服务端，不写在数值侧。**

**收口条件（缺一不可）**：

- **三臂、同窗、同脚本、唯一变量 = ckpt 与是否加载适配器**：`faithful`（参考）/ `merged`（被测）/ `adapter_off`（控制）；
  四条 arm 各自多次请求产物**逐字节一致**（确定性）才可用来比较；
- **决策规则预注册**（先写下来再跑）：合并臂在健康度上明确优于关适配器臂、且不塌陷 ⇒ 采纳；两臂同级 ⇒ 无价值；
- **产物健康度 = 机器可读内容量 + 视觉门**：先把内容健康量（帧间变化量、均值亮度、截断像素占比一类）
  **在同窗多臂上取健康带**，被测臂落带内才算健康；**PSNR 在"同题跨配置"的生成任务上不可作门槛**
  （跨配置采样是混沌的：塌陷臂可能拿到更高的 PSNR）——判读口径见 `../../accuracy-gate/references/quality-gate.md`；
  **视觉门未判时记"待判"，不得记"通过"**；
- **绝对读数、md5、字节数一律留会话产物**；正文与交付表只写**降幅 / 排名 / 是否落带**。

## 5. loader 与摆位契约

- **drop-in 面（可写死）**：§1 的三项一致性检查通过 ⇒ **无需改 loader**。
- **摆位陷阱（框架解析约定；勿把某个具体目录名当普适规则）**：服务端的**模型根解析**常按"给定路径的 basename
  是否恰为约定的**组件名**"分支：命中则上溯一层取父目录，未命中则把给定路径本身当模型根、并在其后拼接组件名
  ⇒ 给一个 basename 不匹配的目录，服务会去找 `<你给的目录>/<组件名>/…` 而失败。
  - **如何判定它仍存在（复核方法，换版本先做这一步）**：
    ① 读该框架模型根解析函数的**当前**实现：是否仍按 basename 分支、约定的名字集合是什么（改了就没有本陷阱）；
    ② 看 **worker 启动日志**里 `FileNotFound` 的**路径形态**——若路径中**组件名重复出现**（被多拼了一层）即命中；
    ③ 最小复现：同一个 ckpt 起两次服务，只改目录 basename（一次匹配约定、一次不匹配），前者起得来、后者失败即确认。
  - 若该函数已改为不依赖 basename（或支持显式指定模型根），**本陷阱作废、整条绕行删除**，不留"以防万一"。
- **另一条已知摆位坑**：直接服务**父目录**可能触发 API 侧模型类型自动探测失败（报"无法判定 model_type"）
  ⇒ 需要一个**同时满足两侧**约定的中间层目录（顶层放 index 与各组件名，被合并的组件用软链接指过去），
  或优先改用服务端支持的**显式模型根参数**。同样按上面的复核方法判定是否仍需要。
- **声明侧变更清单（每次都要逐条确认，不要凭记忆）**：启动参数里去掉适配器相关项、请求体里去掉适配器字段
  （**仍在发该字段的客户端要单独处理**）、模型根指向新产物。
