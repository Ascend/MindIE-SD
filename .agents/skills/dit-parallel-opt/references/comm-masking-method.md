## 1. 术语与适用面

**掩盖（masking / overlap）**：把集合通信放在独立流（comm stream）上，与计算流上的 AI-core 算子
并发执行，使通信**不进入关键路径**。它不减少通信量，只改变通信的**暴露时间**。

**分块流水掩盖**：把一层里本来「一次整块通信」的载荷按**头（head）维度**切成 `n` 份，逐块
「通信 → 计算」，形成通信流与计算流的流水。适用前提：

- 通信的载荷与计算都可按同一维度（这里是头）切分，且切分后**语义不变**（Ulysses 的 a2a 是纯置换，
  头维切分只是把一次大交换拆成 `n` 次小交换）；
- 稠密/稀疏注意力后端**逐头线性**（本组合：稀疏 FA 核耗时与头数成正比，是分块流水的前提，
  先测这条再谈掩盖）；
- 框架允许「通信在别的流上」且能表达块级依赖（本组合在三方框架里由 env-gated `[探针]` 补丁注入；
  若框架自身无该机制，属结构性缺口，见 `framework-integration`）。

**不适用**：通信与计算存在严格**全局**依赖（例如必须先拿到全量 K/V 才能开始算），
或后端不是逐头线性的。

## 2. 上限判定：三个量决定一切

先测三个量（都按**每层**口径）：

| 量 | 含义 | 取法 |
|---|---|---|
| `C` | 每层**通信总量**（要掩盖的对象） | kernel 级把**被掩盖那一族**（本组合 = a2a 族）的耗时求和 ÷ 层数；**不要**直接用 `step_trace_time.csv` 的 `Communication` 列（它含不可掩盖的族，会把上限算歪） |
| `F` | 每层**可与之并行的计算量** | 被掩盖侧的计算（本组合 = 稀疏 FA 核总耗时）÷ 层数 |
| `n` | 分块数 | 实现参数（必须整除每 rank 本地头数） |

派生量：每块通信 `c = C/n`，每块计算 `f = F/n`。**判据只有一个比值 `c/f`（等价 `C/F`）。**

### 2.1 `f >= c`（等价 `F >= C`）：理想界成立

通信流始终能被计算流喂饱，暴露量 = 流水填充（第一块的通信）≈ `c`，于是

```text
掩盖率上限 = 1 - 1/n
```

这就是「切 n 组头最佳掩盖 1-1/n、只暴露 1 组头的通信」的来源，**它是有前提的**：
前提不成立时这个界不可达，继续增大 `n` 也不会接近它。

### 2.2 `f < c`（等价 `F < C`）：真正的上限更低

每块通信都大于该块的计算，流水稳态每块净暴露 `c - f`，再加上填充与排空：

```text
暴露下限 ≈ c            (填充：第一块前向通信)
        + (n-1)*(c-f)   (稳态：每块吃不完的部分)
        + drain         (排空：最后一块的反向通信，前向 q/k/v + 反向 o 时约 c/4 ~ c/3)
掩盖率上限 = 1 - 暴露下限 / C
```

要点：

- **稳态项与 `n` 无关**：`(n-1)(c-f) = (1-1/n)(C-F)`，`n` 越大越逼近 `C-F`。所以 `F<C` 时提高 `n`
  几乎没有收益，只会引入更多每次调用的固定开销（本组合：单个 a2a 的固定开销约十几微秒量级）。
- **要提升掩盖率，只能压通信分子或抬计算**：压通信（量化载荷、减少跨岛流量、减少 rank 数、
  合并 q/k/v 为一次集合）或让更多**独立**计算落进同一段（把非依赖的计算搬进来）。
- **判定顺序**：先算 `c/f` → 再看实测掩盖率占了上限的多少。二者差距大说明流水没跑起来
  （填充/排空被序列化、变换拷贝挤占计算流、块间事件排序过紧），而不是上限算错。
- **`C` 本身会被分块改变（取数陷阱）**：分块把一次大集合拆成 `n` 次小集合，每次调用都有固定
  开销（本组合量级：单次十几微秒），`n` 越大 `C` 越大 ⇒ **同一配置「开/关掩盖」两档的 `c/f`
  不是同一个数**。报数时必须写明 `C` 取自哪一档；判「该不该加块数」用的是**当前档**的 `C`。
- **缩小载荷的动作（量化前移等）改的是 `C`，而且改不到一半**：同一段通信里常夹着未量化的
  张量（输出回传等），且**有效带宽随消息变小而下降** ⇒ 「字节减半」不等于「时间减半」，
  落地后必须重测 `C` 与 `c/f`，不要用理论减半值去预测新的掩盖上限
  （账目算法与尺寸扫描要求见 `../../quantization-dev/SKILL.md` §四·B 与
  `parallel-plan-attribution-method.md` §6）。

### 2.3 本组合观测（仅作量级参照，禁止当预期值）

| 形态 | `c/f` | 理想界 `1-1/n` 是否可达 | 上限（`f/c`） | 实测掩盖率 | 实测 / 上限 |
|---|---|---|---|---|---|
| US P8（8 卡序列并行） | ~1.3 | 否 | ~3/4 | ~0.54 | ~0.7 |
| 复合 CP2USP4（4 卡，AG-KV×Ulysses） | ~2.0 | 否 | ~1/2 | ~0.50 | ~0.98 |
| US P4（4 卡） | ~0.46 | 是 | ~6/7 | ~0.43 | ~0.5 |

读法：**复合形态把上限压到一半，但流水跑满了（实测≈上限）；8 卡形态上限更高却只跑到七成；
4 卡形态上限最高（理想界可达）却只跑到一半。** 「没达到 6/7」的根因在 `c/f > 1`
（要 `C ≤ F`，即每层通信压到 FA 以下），而不是实现没写好 —— 但 4 卡那一格说明实现侧
仍有填充/排空损失，两条都要一起看。

## 3. 分块实现要点（recipe）

> `[探针]` 本节来自一次**未正式合入的 env-gated 补丁**（默认关、配 `.bak`、可整体删除），
> 适用窗口 = 该框架该版本无原生 comm-stream 分块能力时。其中「侧流只放集合通信」「块级 event」
> 「不交错 communicator」「块索引放最外层」是**机制级约束**（换框架仍成立）；
> 而「补丁注入在哪、门控叫什么」属探针细节，**框架升级后先复核是否已有原生能力**
> （判定：关掉补丁跑一次，看 `Overlapped` 列是否已非零），已提供则删除本探针。

以下顺序与两个「反直觉」点是实测出来的，照做可以省一轮返工。

1. **一次预置换，块索引放最外层**：把 `(bs, s_local, world, chunks, w, hs)` 一次 `permute` 成
   `(chunks, world, s_local, bs, w, hs)` 并 `contiguous()`，之后每块 `[g]` 就是**连续切片**。
   直接对非连续视图做 `as_strided` 物化会退化成大规模拷贝（本组合实测：v1 因此多出
   `InplaceCopy_AsStrided` 一类算子，每步百毫秒量级）。
2. **侧流上只放集合通信，所有 AI-core 算子留在计算流**（预置换、每块的逆置换、写回）。
   v1 把变换也放进 `with torch.npu.stream(comm)`，profile 显示侧流上出现了
   1400 个 AI-core 核（换位 + as_strided 物化），直接和 FA 抢 vector core；
   改成 v2 后侧流 AI-core 核数 = **0**，`InplaceCopy_AsStrided` 回到基线量级。
   **这条是最容易犯且最贵的错**：profile 里「新流」应当只承载通信算子。
3. **用块级事件，不要 `wait_stream`**：`wait_stream` 会等到对端流上**所有已入队**的工作完成，
   把流水压成串行。正确姿势是每块一个 event：comm 侧 `record`，计算侧 `wait_event(g)`；
   反向（输出 a2a）时 comm 侧只 `wait_event` 该块变换完成的事件。
4. **同一时刻只让一个 communicator 活跃**：把不同并行组的集合通信交错下发，实测会让 HCCL
   进入不一致状态（跑一两分钟后报 collective 内部错误）。正确顺序是
   **先把 A 组的所有块发完，再发 B 组的所有块**，不要 `a2a(g0), AG(g0), a2a(g1), AG(g1)…`。
5. **块数取「整除本地头数的最大值」**：`chunks = max{d <= requested : heads_local % d == 0}`。
   本组合 8 卡每 rank 7 头 ⇒ 只能 7（或 1 = 关）；4 卡 14 头 ⇒ 7 也可用（每块 2 头）。
   强行用别的数会让载荷不是整数头。
6. **输出写成独立张量再按块拷回**：避免原地写回与非连续视图别名（否则会多出隐式拷贝，
   且顺序难以推理）。
7. **门控与回退**：env 门控 + 默认关；任何形状不满足（`world<=1`、头数不整除等）时
   **返回 None 让调用方走原路径**，不要抛异常。全部改动配 `.bak`，可一键整体删除
   （不要写成长期分裂的两条代码路径）。
   ⚠️ **回退必须留计数器**：本组合实测出现过「开了门控但每次调用都静默回退」的臂——
   产物 md5 与基线逐字节相同、耗时无差别，看上去像"这个优化没用"。
   正确姿势是**命中/回退各计数并打进日志**，交付时先报命中数再报收益。
8. **下发顺序就是调度（承重，最容易被忽略）**：同一 communicator 的集合通信**按下发顺序串行执行**
   （实测该族 `union/sum == 1.00`，一个接一个，零并发）。因此「先把所有前向发完、再发所有反向」
   这类写法会让**反向通信整段落在本层计算之后**，在计算流上表现为空泡。
   本组合观测：反向输出的 a2a 只占该族字节的 1/4，却贡献了**过半的暴露通信**，
   且与注意力核的重叠率是 **0**（结构上不可能重叠——它排在本层所有注意力之后）。
   改进方向是**软件流水式下发**：把「第 `g+1` 片的前向」排在「第 `g` 片的反向」之前，
   用块级 event 表达依赖，使除最后一片外的反向都落进计算流仍忙的窗口。
   ⚠️ 别做成「逐片交替」（前向→反向→前向…）：反向要等该片注意力完成，会把后一片的前向堵在
   它后面，反而把流水压成串行；也**不要把两个不同 communicator 交错**（见第 4 条，会失步）。

## 4. 生效验证判据与静默失效清单

**判据（缺一不可）**：

| 证据 | 期望 | 说明 |
|---|---|---|
| 集合通信算子**次数** | 相对不开掩盖时上升 ≈ `n` 倍（每张量） | 次数没变 ⇒ 路径根本没进 |
| 侧流上的 AI-core 核数 | = 0 | 有核说明变换漏在侧流上（见 §3.2） |
| `InplaceCopy_AsStrided` 一类物化算子的耗时 | 回到基线量级 | 它是「非连续视图被物化」的指纹 |
| `step_trace_time.csv` 的 `Communication(Not Overlapped)` | 明显下降 | 精确匹配列名：`Communication` 是该列名的**子串**，模糊匹配会静默取错列 |
| 产物 md5 | 与不开掩盖时**逐字节一致** | Ulysses a2a 无规约 ⇒ 掩盖是纯置换；md5 变了说明实现有语义错误，不是「数值波动」 |
| 掩盖率实测 | 与 §2 上限对比（达成率） | 只看「快了」不够，要报达成率 |

**静默失效清单（都实际发生过，且都不报错）**：

- **门控读取顺序**：分派函数在进入并行形态分支**之前**就读取了父门控值，导致只开子门控
  （复合形态的专用开关）时走不到子分支 —— 必须**同时**开父门控与子门控，且把门控读取
  挪到分支之后。
- **运行脚本把门控 `unset` 了**：共用启动脚本里的一句 `unset VAR` 会让新加的开关永远为 0。
  启动后 grep 一次实际生效的环境变量，不要只信导出语句。
- **`profile` 里看不见但也没生效**：日志打了「已启用」不等于生效（打印时机可能早于注册），
  以算子次数与流归属为准。
- **冷/热与并发租户污染**：同机其他任务或微基准轮询会把首请求与固定开销拉高，
  造成「开掩盖反而变慢」的假结论；对比前后必须确认无并发占用（见
  `../../perf-gate/references/measurement-discipline.md` §2）。

## 4.5 归属与空泡归因：下一步该往哪投

一条命令给出三个判据（`scripts/bubble_attribution.py`）。**只做第一个判据会得出错误结论**——
本组合就是这么踩过一次坑，三个都要看。

1. **暴露的是哪一族**：某族通信的耗时**大部分落在计算流空隙里** ⇒ 它才是关键路径上的那一族。
   本组合观测：反向输出 a2a 的时间几乎全部落在空隙里（暴露），前向 q/k/v 只有约三成
   （大部分被掩盖；与注意力核重叠过半）。精确读数见归档 `{run_results_dir}/archive/`。
2. **空隙是不是真在等通信（释放判据）**：空隙里"有集合通信在跑"**只是必要条件，不是充分条件**——
   跑着的那条传输可能服务的是**更晚**的工作。判据是**释放点**：空隙**恰好在某次集合通信完成时结束**
   （`--release-delta` 容差内）才算真依赖。本组合观测：空隙里"有通信在跑"的那部分中，约八成才是
   "被集合通信完成所释放"的（占全部空隙约七成半）⇒ 其余是**在传输还在途时就恢复执行**
   的空隙（等的是别的东西），另有约一成空隙什么都没跑（真空气泡）。
3. **生产-消费判据（通信是否已跑在前面）**：比较消费者核的启动时刻与"它依赖的那次集合通信的完成"。
   本组合观测：注意力核与**它自己那片**前向 a2a 完成的间隔**中位数为毫秒量级**（逐例都远大于容差，
   无一例"紧接着就启动"）⇒ **前向通信跑在消费前面约两片**，注意力核**从来不等自己的数据**
   （"在 FA 之前"的空隙合计占单步可忽略）。此时"压前向载荷"换不来步时——
   卡住的是别处（见判据 1 与 §3 第 8 条的下发顺序）。

> 报数纪律：三个判据必须一起报（暴露归谁 + 空隙是否被通信释放 + 消费者是否已跑在前面）。
> 只报「通信未重叠 XX%」不足以定位问题；只报「空隙里有通信在跑」会把归因引向错误的族；
> 只报「有空泡」则会把人引向错误的下发优化方向。

## 5. 上限计算工作流

```text
1) 采集：同窗口、同卡组，掩盖 OFF / ON 各一次 profile（捕获放在被排除的 warmup 请求里）
2) 取数：step_trace_time.csv（Computing / Communication(Not Overlapped) / Overlapped /
        Communication / Free / Stage）+ kernel_details.csv（按算子名分类通信族与 FA 族）
3) 取 C：**只算「被掩盖的那一族」**，并且**认到具体的 communicator**（`--mask-gid`）——
        同族名字下常同时存在不可掩盖的通信（逐层 offload 的权重 gather 与序列并行的 gather
        族名相同），混进去会把 C 抬高、把上限算歪。注意**复合形态被掩盖的族与纯序列并行不同**：
        本组合纯 Ulysses 掩的是 a2a 族，复合 AG-KV×Ulysses 掩的是 all-gather 族
4) 算 C、F（每层）与 c、f；算 c/f
5) 出上限：c/f<=1 → 1-1/n；否则 1-(c+(n-1)(c-f)+drain)/C
6) 出达成率：实测掩盖率 / 上限；差距大 → 查流水填充/排空与侧流核数
7) 自检：达成率 >100% 说明输入有问题（C 取错族，或侧流上的 AI-core 核被 profiler 计成了通信）
   —— 先用 `collective_attribution.py` 的 per-stream 表核对
8) 判下一步：c/f>1 → 先压通信分子（量化载荷、减跨岛、合并集合），而不是加块数
```

脚本：`scripts/mask_bound_calc.py`（零依赖；`--mask-family` 选 C 的族，`--chunks`/`--layers`
给分母，输出上表与自检告警）。

## 6. 声明纪律

- 掩盖率、加速比都必须带**同窗口 A/B**：掩盖开关必须与其它变量（offload、量化、步数）解耦。
  本组合出现过一次「有掩盖 vs 无掩盖」两臂的 offload 状态不同的采集，收益里混了 offload 的贡献，
  必须重采才能引用。
- 报「掩盖率」时同时报**达成率**（实测 / 上限）；只报实测会让人误以为上限已到顶。
- 混淆项优先排查顺序：offload 开关 → 量化档 → 步数档 → 卡组与窗口。
- 绝对耗时与绝对带宽只作量级参照，不进结论句。

## 7. 维护与更新

- **后端换代**：FA 后端换实现（稠密 / 别的稀疏后端 / fp8 / mxfp4）时，逐头线性的前提要**重测**，
  且量化粒度会改变 `C`（量化后通信量可能减半）⇒ §2 的上限必须重算。
- **框架升级**：若框架自带 comm-stream 机制或原生分块掩盖，先复核本文的 monkey-patch 是否仍有必要
  （判定方法：把门控关掉跑一次，看 `Overlapped` 列是否已非零），已修复的绕行条目**删除**。
- **拓扑/规模变化**：卡数、UB 岛结构、跨岛比例变化会同时改变 `C` 与可达带宽 ⇒ `c/f` 重测。
- **新增形态**：支持新的复合并行（如 USP×CP×TP）时，本方法按「每层每 rank 的 C 与 F」就地套用，
  不改判据。
