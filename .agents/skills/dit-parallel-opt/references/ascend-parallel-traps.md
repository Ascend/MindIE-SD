## 0. ⚠️ 陷阱是有寿命的：**不要把它当成永久事实**

**本版本需要绕行的问题，下个版本可能已经是正常功能。**
所以记录陷阱时必须**同时记录"靠什么判定它仍然存在"** —— 否则下个版本这份文档会变成
"**为不存在的问题做无用绕行**"，甚至**阻止 agent 使用已经修好的原生路径**。
**这比不知道更糟。**

### 0.1 按寿命分三类

| 类别 | 例（本文档中的） | 寿命 |
|---|---|---|
| **物理 / 硬件限制** | §1 的 AIV grid 上限、vector core 数、UB 容量 | 换硬件才变 |
| **框架 / 编译器缺陷**（**最易过期的一类**） | §2 的"仅支持纯 Ulysses"过严守卫；§5 的 `auto_pad` 与 mask-free 后端互斥；§6 的 ring 绕过 backend 导致**稀疏被静默丢弃**；§7 的对齐约束；§9–§11 的算子对 Q≠KV / 池化前 cat 的假设 | **可能在下个版本直接修好** |
| **设计选择 / 契约** | §8 的量化粒度与舍入、对齐倍数、池化语义 | 相对稳定，但升级也可能改 |

### 0.2 强制义务

1. **每条陷阱必须写"如何判定它仍存在"** —— 一条命令 / 一个探针 / 一个最小复现。
   让人能**自己验**，而不是只能照抄绕行。**本文档每条陷阱的"复核触发"从句即为此。**
2. **升级软件栈后逐条复核**；**不再复现的条目必须删除**，不能留着"以防万一"。
3. **优先记录判定方法，其次才是绕行方案** ——
   判定方法在版本变更后仍然有用，**绕行方案会作废**。
4. **不要把一次性缺陷固化成结构**：绕行必须走**可一键关闭并整体删除**的开关；
   不要长期分裂代码路径、不要写兼容 shim、不要把绕行写进默认路径。
5. 某条陷阱若"已修好"，**从清单中移除或移入"历史"小节**，并注明**从哪个版本起不再需要**。
6. **升级后必须重跑第 10 步那类探针**（打印状态量而非日志），确认修复的语义仍然成立。

> **一句话**：**记录"怎么发现"，而不是"必须怎么做"。**

## 1. `EE1003 … value N for parameter coreDim is invalid. Expected value: less than or equal to 65535`

**症状**：只在长序列/大规模时崩，短序列正常。

**原因**：设备的 AIV grid / coreDim 存在上限（**具体数值查设备属性或算子 UT，勿硬编码**）。Triton kernel 若用 `[ (rows,) ]` 作 grid（一个 program 一行），`rows` 一旦超过上限即报错。
**关键**：很多调制类 kernel 的 grid 直接取自 `x.shape[0]`（序列行数），所以**崩溃本身就是"这个张量没被分片"的信号**。

**判别**：把报错里的 `N` 与 `seq_len` 对比。

| 关系 | 含义 |
|---|---|
| `N == seq_len` | **未分片**（拿到全序列） |
| `N == seq_len // sp_world` | 已分片，上限另有问题 |

**陷阱**：小规模（`seq_len` 明显低于 grid 上限，如短序列档）时**不会报错**，于是"能跑"被误认为"跑对"。**这是本类故障最危险的地方。**

**处置**：先按 `scope-effectiveness-check.md` 的流程确认分片，再考虑 kernel 侧。

**复核触发**：跑一个 `grid=(70001,)` 的空 triton kernel（或直接把报错里的 `N` 与 `seq_len` 对比）—— 仍报 `EE1003 … coreDim` 则上限未变（属硬件/环境限制，处置照旧）；若 `N == seq_len // sp_world`，说明**分片已生效、本条的"未分片"成因不再成立**（此时若仍报错，是 grid 上限本身，见上表第二行）。

## 2. 静默关闭全部序列并行：模型层的"仅支持纯 Ulysses"守卫

**症状**：并行配置生效（组构造正确、hooks 已注册），但张量仍是全序列；小规模不报错，大规模 `EE1003`。

**原因**：模型里可能有形如

```python
if world_size <= 1 or ulysses_world_size != world_size:
    return 0, seq_len          # 返回全跨度
if ring_world_size != 1 or allgather_world_size != 1:
    return 0, seq_len
```

的跨度计算函数。**任何非纯 Ulysses 的分解（如 Ulysses × AllGather-KV）都会触发，返回整条序列的跨度**，导致整个模型跑在未分片状态。

**处置**：判断该守卫是否真的必要。若复合分解下**每 rank 仍均匀拥有 `seq_len / world_size` 行**（Ulysses 分 head、AllGather-KV 聚合序列即属此类），则跨度算术不变，守卫可以放宽。**Ring 会真的改变序列归属，其守卫应保留。**

> ⚠️ 放宽这类守卫属于**模型层语义假设**的改动，必须独立复核。

**复核触发**：在非纯 Ulysses 分解（Ulysses × AllGather-KV）下打印该跨度函数的返回值 —— 若返回 `seq_len // world_size`（或新版本已无 `ulysses_world_size != world_size` 这条守卫），说明**该版本缺陷已修好、原生复合分解可用：直接走原生路径，删掉本地放宽补丁并删除本节**；若仍返回 `0, seq_len`，缺陷仍在，绕行保留。

## 3. 深度记账的静默破坏

**症状**：分片 hook 明确返回了新对象（`same=False`）、shape 也对，但下游仍看到全序列。

**原因**：`ForwardContext._sp_shard_depth` 的增减必须在同一模块上配对。若同一 hook 被绑到一处而解除绑定的路径被调用两次（例如模型里 `sp_gather` 有两处调用），`max(0, depth - 1)` 会把深度提前归零，后续逻辑即判定"已离开分片作用域"。

**判别**：在递增点与递减点各打印一次（含模块名与 `depth_before`），对比调用序列，而不是只看最终值。

**复核触发**：在 `ForwardContext._sp_shard_depth` 的递增点与递减点各打印一次（模块名 + `depth_before`），并数一遍同一模块上 `sp_gather` 的调用次数 —— 若增减已严格配对（不再出现 `max(0, depth - 1)` 被二次触发）、下游能看到分片张量，说明记账缺陷已修好，**删除本节**；若深度仍提前归零，处置照旧。

## 4. gloo 在 8 rank 下报 `ss1.ss_family == ss2.ss_family. 2 vs 10`

**原因**：容器 hostname 同时解析到 IPv6 链路本地（`fe80::`）与 IPv4，多进程分到的地址族不一致。4 rank 往往不复现。

**处置**：

```bash
export GLOO_SOCKET_IFNAME=<实际 IPv4 网卡名>     # 用 ip -o -4 addr 取，勿照抄示例名
```

容器里可能没有 `ip` 命令，用 Python 取网卡名：

```python
import socket, struct, fcntl
for n in [l.split(":")[0].strip() for l in open("/proc/net/dev").readlines()[2:]]:
    try:
        s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
        ip = socket.inet_ntoa(fcntl.ioctl(s.fileno(), 0x8915,
              struct.pack("256s", n[:15].encode()))[20:24])
        print(n, ip)
    except Exception:
        pass
```

**复核触发**：8 rank 下**不设** `GLOO_SOCKET_IFNAME` 跑一次最简 `init_process_group("gloo")`，并用上面的片段打印 hostname 解析到的地址族 —— 若不再报 `ss1.ss_family == ss2.ss_family. 2 vs 10`（容器已只解析 IPv4，或 gloo 已支持混合地址族），本环境限制已消失，**删除本节并撤掉该 export**；若仍复现，继续指定 IPv4 网卡。

## 5. `auto_pad` 与不支持 attention_mask 的后端互斥

**症状**：`Sequence length (N) is not divisible by SP world size … Cannot use <BACKEND> which does not support attention_mask.`

**原因**：SP hook 的 `auto_pad=True` 走通用补零路径，该路径**强制要求后端支持 attention_mask**。声明了 `supports_packed_mask_free=True` 的后端（如稀疏 FA）不满足。

**处置**：若补零只是**尾部 pad**、且后端本来就会按 `used_len` 裁掉尾部，则**不需要掩码**。绕开通用的 auto_pad 路径，直接补零后 `sp_shard` 即可。

**陷阱**：`pad_len` 必须由**余数**推出（`align - remainder`），不能写成 `align - seq_len`（后者会是很大的负数）。

**复核触发**：非整除序列长度下**直接**开 `auto_pad=True` 配该后端跑一次 —— 若不再抛 `Cannot use <BACKEND> which does not support attention_mask`（后端已支持 mask，或 auto_pad 已改走尾部 pad 免 mask 路径），说明**该版本限制已修好、原生路径可用：删掉手工补零 + `sp_shard` 绕行并删除本节**；若仍报错，绕行保留（`pad_len` 仍须由余数推出）。

## 6. Ring 与稀疏 FA 互斥，且会静默丢稀疏

**症状**：配了 ring 后稀疏"看起来还在"，但结果不对或性能异常。

**原因**：分块稀疏 FA 需要**整条 key 序列**来挑选稀疏块；ring 只给每个 rank 一段序列。部分实现会用显式校验拒绝（错误信息里会写明"needs the whole key sequence"），**但更要紧的是：ring 路径可能绕过 backend**，于是稀疏被静默丢弃。

**处置**：需要 CP 且要保持稀疏时，**走 KV all-gather 类方案**（聚合后每 rank 持有完整 key 序列），不要走 ring。

**复核触发**：配 ring 后给稀疏路径加一次命中计数（或 `grep` 运行日志里的 backend 名）—— 若新版本 ring 下稀疏仍被真正命中、或框架已显式拒绝 ring × 稀疏（不再静默绕过），说明**该框架缺陷可能已修好：复测后改回原生 ring 配置并删除本节**；若稀疏计数仍为 0 而结果悄然不同，静默丢弃仍在，继续走 KV all-gather。

## 7. 序列长度对齐：块大小 × 并行度

**症状**：CP 下稀疏块分组与基线不一致 → 输出发散；或分片边界落在块中间。

**原因**：稀疏 FA 按固定块（如 128 token）做池化与稀疏排名。若每个 SP 分片不是整数个块，池化分组就会与基线不同。

**处置**：把 **packed 序列本身**对齐到 `128 × sequence_parallel_size` 的倍数，**且 pad 必须在尾部**，这样 rank0 的窗口全是真实数据、只有最后一个 rank 携带 pad。

**要点**：对齐要在**产出 `seq_len` 的权威位置**做（例如 packed sequence 构造函数），让 `input_ids`、mask、position、`cu_seqlens`、spans **全部自动一致**。
**只在分片 hook 里改分片尺寸是错的** —— 全序列长度没变，各消费者不一致，会直接崩。

**复核触发**：取 `seq_len % (block_size × sequence_parallel_size) != 0` 的输入，**不打对齐补丁**跑一次并与基线位级对比 —— 若分组仍与基线逐位一致（新版本已按分片边界自适应分块），说明对齐约束已非必需，**删除本节**；若仍发散，对齐仍必须在产出 `seq_len` 的权威位置做。

## 8. 量化器的 scale 粒度与舍入规则

**症状**：自研融合量化 kernel 与框架算子逐字节对不上。

**两条实测规则**：

| 规则 | 值 |
|---|---|
| 舍入 | **RNE**（就近取偶）。截断会差约 50%，不是小误差 |
| scale 粒度 | **每个 64-token 块一个**（不是每个 tile 一个） |

**性能与精度的调和**：用大 tile（如 256 行）但**内部按 64 行子块各自求 amax**，既对齐了粒度又不牺牲并行度。

**已验证的加速**（转置 + 量化融合，含尾块处理）：两档都在 2–3 倍量级（15s 档略高于 5s 档），字节差异为万分之几量级（尚未完全字节精确，残差疑似来自 amax 归约序）；精确读数见归档 `{run_results_dir}/archive/`。

**复核触发**：对同一个 256 行 tile 分别按「每 tile 一个 scale」与「每 64 行子块一个 scale」实现，与框架算子位级对拍 —— 若「每 tile」粒度也能到 100.000000%（或算子 schema 已暴露 `block_size`、该契约已被文档化），说明粒度/舍入规则已变或已公开，**按当前版本契约重写并删除本节**；若仍只有 64 行子块粒度对齐，「大 tile + 64 行子块 amax」继续必需。

> ⚠️ **本节只是指针，量化契约本体在 `quantization-dev`**（`../../quantization-dev/SKILL.md`）：
> MXFP8 字节编码公式、scale 布局与**恒等 swizzle**、RNE + ±448 饱和、退化块规则、
> **除数必须从内存载入**、bf16 整数 RNE 技巧、**8-bit 转换是回绕而非饱和**、组尺度耦合、位级对拍 SOP。
>
> **证据等级提示**：MXFP8 契约证据**强**；而 int8 的「RNE / 截断差约 50%」证据**弱**
> （仅一句话来源、原始日志不在手），引用时必须标注。
>
> **两套字节口径不要混用**：`字节一致率 98%+`（fp8 量化级近似）与 `字节差异 0.00x%`（残差比）
> **分母定义不同**，前者是"近似通过"门、后者是"尚未精确"的残差，**不可互算、不可互替**。

## 9. 梯度/掩码类算子对 Q≠KV 的假设

**症状**：`Q, K, and V must have identical sequence lengths`。

**原因**：分块稀疏路径的排列/池化按"Q/K/V 同长"设计。CP 下若 Q 只覆盖本地窗口而 K/V 是聚合后的全序列，即触发。

**处置**：把置换域取全序列（KV）、Q 只取落在自己窗口内的置换条目并重基到 Q 的坐标系，同时给 Q 单独的 inverse。**注意不能靠"丢弃行"来对齐** —— 反向 all-to-all 要求输出行数精确，丢行会报 `expanded size ... must match`。

**复核触发**：CP 下（Q 只覆盖本地窗口、K/V 为聚合全序列）**直接调**该算子一次 —— 若不再抛 `Q, K, and V must have identical sequence lengths`（该版本缺陷已修好、算子已原生支持 Q≠KV），说明**原生路径可用：删除置换域重基绕行并删除本节**；若仍报错，处置照旧（不得靠丢行对齐）。

## 10. Q/K/V 不等长的**池化/拼接**陷阱（与 §9 同族，但处置不同）

**先区分**：§9 是"算子**拒绝** Q≠KV"，处置是**置换域重基**；本节是"**池化前的 cat 无法成立**"，处置是**分开池化**。**两者处置不同，不要混用。**

**症状**：CP 下池化/拼接处报错，或池化结果与基线不一致。

**原因**：`avgpool(torch.cat((q, k, v), dim=0))` 要求 Q/K/V **除 dim0 外形状完全一致**。CP 下 Q 是**本地窗口**、K/V 是 allgather 后的**全序列** → 长度不同 → `cat` 无法成立。

**处置**：**分别池化 Q/K/V**。依据是 `avgpool` **只沿序列轴归约**，因此与"仅为喂给它而存在的 dim=0 cat"**可交换** ⇒ 分别池化**逐位一致**，且**移除了每次调用 3× 大小的中间物化**。

**实测**：pool 区 5s 档约 3 倍、15s 档约 4 倍（单次调用耗时同量级下降，读数见归档 `{run_results_dir}/archive/`）；e2e DiT 收益为个位数百分比量级，4/4 ABBA 同号，**16/16 输出 md5 相同（bit-lossless）**。

**消费方形状约束**：`qkv_pool` 的消费者会 `torch.chunk(qkv_pool, 3, dim=0)` **拆回三段**，因此唯一要求是保持 `(3, S/128, N, D)` 形状。**改造前先确认消费者的真实契约**，不要凭形状猜。

> **可迁移手法**：门控 `OMNI_H3_SPARSE_POOL_SPLIT`（另有 `_FILE` 哨兵变体）**每次调用重新求值**，
> 使**同一 serve 进程内可逐请求翻转分支**。源码注释给出的理由值得记住：
> *"效应与共享机器上的热漂移相竞争"* —— 这正是
> `../../perf-gate/references/measurement-discipline.md` §2（交错对照 ABBA）的落地形态。

⚠️ **同族的 `_grouped_pool`（分组池化）已被证伪、停止使用**：实现经单测证明与 `avgpool` **逐元素相同（max|diff| = 0.0）**，但 e2e 反而**恶化近一倍**（绝对耗时见归档 `{run_results_dir}/archive/`）。源码原话：该假设 *"is falsified, not merely mis-implemented"* —— **实现无误、想法错误**，该被推翻的是**假设**而不是代码。函数仍在文件里但未被调用。
（另注：早期版本因 **bf16 累加**导致池化行偏移 ~1e-2；`avgpool` 在 **fp32** 累加，自定义实现必须对齐累加精度。）

**复核触发**：CP 下对 Q（本地窗口）与 K/V（全序列）**直接**跑一次 `avgpool(torch.cat((q, k, v), dim=0))` —— 若不再报形状错、且与分开池化逐位一致（框架已提供原生等价路径），说明**原生 `cat` 形态可用：回到原生实现并删除本节的分开池化改造**；若 `cat` 仍不成立，分开池化继续必需（`_grouped_pool` 已证伪，勿复活）。

## 11. Q 窗口（query 范围 ⊆ key 范围）

**症状**：CP 下把 Q 本地化后，出现索引错行、掩码失效、或输出接缝。

**契约（代码实际形态，参数名是 `query_start`，不是 "Q window"）**：

| 要素 | 作用 |
|---|---|
| `query_start` | Q 窗口在 KV 上的起始位置 |
| 越界检查 | `< 0` 或 `>= kv_len` → **明确报错**，不要静默 |
| `q_eff = min(q_len, kv_len - query_start)` | 尾窗口截断 |
| `q_split` | 仅在"Q 覆盖全序列"时才走对齐路径 |
| 分开的 `actual_seq_lengths` / `_kv` | Q 与 KV 各报自己的长度 |
| 输出按 Q 宽度**零填充** | 保证反向 all-to-all 的行数契约 |
| `_local_query_start()` | attention backend 侧计算本地窗口起点 |

**生效判据**：打印 `query_start`、`q_eff`、`q_split` 与 Q/KV 的 shape —— **必须看到 Q 宽度 < KV 宽度且 `q_split=True`**。

> **头号风险是"静默索引错行"**：**不能**用 KV 置换块空间的下标直接索引 Q
> （源码原话：*"indexing Q with them directly would **silently target the wrong rows**"*）。
> 凡是"**索引空间从对端推导、再去索引本端**"的地方，都要**显式记录基底偏移并断言**。

**复核触发**：打印 `query_start`、`q_eff`、`q_split` 与 Q/KV 的 shape —— 若新版本已无 `query_start` 参数、或 `q_split=False` 也正确（后端已原生支持 Q 窗口），说明**该版本限制已修好、原生路径可用：删除本地 Q 窗口绕行与本节**；若仍须「Q 宽度 < KV 宽度且 `q_split=True`」才正确，按上表继续核对。

## 12. CP + 稠密 attention 回退：**不受支持，是使用限制不是 bug**

**症状**：CP 下报 `npu_attn_varlen` 守卫拒绝 Q≠KV 的填充行，例如 `valid_kv_length=37736, seq_len=18944`。

**原因**：**CP（Q 本地 / KV 全序列）+ 稠密 attention 回退**这一组合不受支持 —— 稠密回退有它自己的"Q 与 KV 填充行必须一致"守卫。**这是使用限制，不是 bug**，不要在框架里绕它。

**处置**：CP 下**必须**使用支持该形态的后端（如稀疏 FA 的 Q 窗口路径 / 分段掩码），**不要指望稠密回退兜底**。

本条目与 §5（`auto_pad` 与不支持 attention_mask 的后端互斥）、§6（ring 与稀疏 FA 互斥且**静默丢稀疏**）同属
**"CP/SP 机制 × attention 后端能力"互斥条目群** —— **配 CP 前把这三条一起核对**，否则会得到"能跑但结果不对"或"配了没生效"。

**复核触发**：CP 下**故意**让稠密回退兜底跑一次短序列 —— 若新版本不再触发 `npu_attn_varlen` 的填充行守卫（不再出现 `valid_kv_length=…, seq_len=…` 报错），说明**该使用限制已解除、稠密回退可用：删除本节并允许原生兜底**；若仍拒绝 Q≠KV 填充行，继续禁止依赖稠密回退。

## 13. 排查这类问题的通用姿态

1. **先证明生效，再讨论对错**；**每个判别量两侧都测**；**日志 ≠ 生效**（很多框架的
   “Applying …” 日志打印在真正注册之前）—— 完整判据、探针模板与判读表见
   `scope-effectiveness-check.md`（本文件不复述）。
2. **小规模不报错 ≠ 正确** —— 上限类错误会被小规模掩盖（见 §1）。
3. **区分“实现有 bug”与“想法被证伪”** —— 单测通过却 e2e 更差时，要推翻的是**假设**，
   继续改代码是纯浪费（§10 的 `_grouped_pool`）。
4. **形状必须按 rank 核对** —— `(1, S, 56, 128)` 是**全局**形状，生产每 rank 看到的是
   `(1, S, 14, 128)`（heads / world_size）；**按全局形状建 A/B 会偏 ~7×**。
