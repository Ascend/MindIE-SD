## 何时用（触发）

- 运行时施加秩-r 适配器（LoRA）后**该链成为最大单项成本**，要判它贵在哪、能不能收；
- 要**给"融合 epilogue"定收益上限**（宣称前必须先算出上限）；
- 换**权重精度档**（1 字节/元素 ↔ 2 字节/元素）后要**重估该链成本**；
- 同一条链上已有若干"微融合"候选，要判哪一类**结构上值得做**（减算子数 vs 把单个算子做快）。

## 成本结构判据

标号（全部符号化，不写具体几何）：目标模块数 `M`、秩 `r`、隐藏维 `d`、激活行数 `L`、
激活/权重元素字节宽度 `w`。

每个目标模块的运行时施加 = **down GEMM（`L×d → L×r`）+ up GEMM（`L×r → L×d`）+ 加回**（epilogue 或独立 add）。

- **算力极次要**：该链的 FLOPs 与同位置的主 GEMM（`L×d → L×d`）之比 ≈ `r/d`。秩远小于隐藏维时
  （工程上通常差一个数量级以上），**算力占比可以忽略**。
- **成本主项 = 激活侧访存 + 算子下发**：down 要**读整份激活**，up 要**写整份 delta**，加回还要再读/写一次
  ⇒ 每模块至少 **2 次激活往返**（含中间张量落地时更多），字节数按 `L·d·w` 计；同时每个模块多出
  **至少 2 个算子实例**（外加量化档下的量化/反量化与布局算子）。
- ⇒ **判据：当 `r ≪ d`（一个数量级以上）时，该链的成本按「激活字节数 × 目标模块数」与「新增算子实例数」
  估，而不是按 FLOPs 估。** 由此推论："把每个小 GEMM 换成更快的实现"上限很低；
  "少一次激活往返 / 少一个算子实例"才是数量级上的着力点。

## 现场取数方式：三档 profile 对比

同一窗口、同一请求、同一 seed、同一 profiler hook（同一 step、同一 elected worker）下跑三档：

| 档 | 配置 | 用途 |
|---|---|---|
| **A 带适配器** | 运行时施加 | 该链的**整条成本** |
| **B 不带适配器** | 同权重、**同精度**，仅去掉适配器 | 该精度档下的对照底（**不是**可交付档，见下） |
| **C 离线合并** | `W' = W + (α/r)·B·A` 合并进权重，服务端不加载适配器 | 验证"成本确实在这条链上"：`C ≈ B` ⇒ 链上成本整段消失，而非被权重格式吃掉 |

每档取三个量，**看三者的关系而不是单看某一个**：

- `Δwall` = A − B 的墙钟（`forward` 与每步都要）；
- `Δdev` = A − B 的 **device 侧算子时间**差（同一 step）；
- `Δcount` = A − B 的 **device 算子实例数**差。

取数纪律：profile 的单步读数会被 profiler 抬高，**墙钟仍是权威口径**（同 `../../perf-gate/SKILL.md`）；
op census 与逐算子差可用仓内 `tools/prof_summary.py`（支持 pairwise `--diff`）；
同窗之外的历史读数不可比。

## 归因规则（核心）

**若 `|Δwall| ≥ 2 × |Δdev|`（墙钟差显著大于 device 算子时间差，量级 2 倍以上）⇒ 差额归 host / 下发。**

此时优化方向是**减少算子数量（融合 / 去冗余 / 消除中间态）**，**不是把单个算子做快**：

- device 侧可回收的上限就是 `Δdev`——把 `2M` 个小算子逐个调快，最好情况也只能取走 `Δdev`；
- 差额 `|Δwall| − |Δdev|` 只能靠**减算子数**拿：把 down/up 与加回折进生产者（或消费者）的 epilogue、
  合并同一激活上的多次读写。

**反之**（`|Δwall| ≈ |Δdev|`，差额落在噪声内）才去**算子级优化**（换实现 / 调 tile / 换 kernel）。

判据要点：

- **`Δcount` 与 `Δwall` 同向，归因才算成立**；若 `Δcount ≈ 0` 而 `Δwall` 显著，
  先查 host 侧（下发 / 同步 / 编译与 plan 缓存命中），**不要动 kernel**（否则会把时间花在 `Δdev≈0` 的地方）；
- 若 `Δwall` 显著为正而 `Δdev` 与 `Δcount` 都≈0，先怀疑**门控没真正生效 / 走了退化路径**
  （同 `../SKILL.md` Step 4「开了 ≠ 生效」），而不是"成本在别处"。

## 融合 epilogue 的收益上限

**把低秩增量折进生产者 epilogue（或消费者）的收益上限 = 该链的 `Δwall`，不得宣称超过。**

- 价值来源是**消除激活的重复读写与中间张量**，不是省 FLOPs：down 的输入就是生产者的输出、
  up 的结果就是 epilogue 本来要加回的量 ⇒ 折进去后激活只留一次读写；
- **上限纪律**：候选融合的宣称收益 ≤ `Δwall`（`Δwall` 是全部收益的来源，不是其中一项的分母）；
  把 `Δwall` 分给多个候选时**不得相加超限**；
- **测得收益 > `Δwall` 时不要当超额收益上报**：先怀疑两臂**不同源**——最常见是基线档没有忠实施加适配器
  （旁路了 `...WithLoRA` / hook 包装层，delta 被静默丢弃），按 `../accuracy-gate/SKILL.md`
  「保真口径必须先定」重做基线；
- 融合后仍须过精度验收：折进 epilogue 会改变**累加顺序与累加精度** ⇒ 按 `../accuracy-gate/SKILL.md`
  选层级（逐位 / 明确层级的数值门），拿"站点级逐字节精确"不能替代端到端产物的门禁结论。

## 精度档维度

**同一条运行时链的成本随权重/激活精度档变化，量级不同：**

- 激活侧访存是主项 ⇒ 成本主要随**激活元素字节宽度**走。**2 字节/元素档（bf16）的该链成本
  约为 1 字节/元素档的 1.3–1.4 倍**（本组合观测，比值非承诺；随 dtype 宽度与实现细节变）；
- 量化档下该链还会**额外附带**量化 / 反量化与布局类算子（`_quantize_kernel`、`Sort`、`Slice` 之类），
  这些全部计入 `Δcount` ⇒ 量化档的 `Δcount` 往往比非量化档更大，去冗余空间也更大；
- ⇒ **换精度档后必须重测该链的 `Δwall`/`Δdev`/`Δcount`**，不得沿用另一档算出的收益上限；
- 另注：**离线合并（C 档）的可行性本身受精度档限制**——低精度档下每元素增量可能小于一个量化步长，
  合并会吞掉适配器。可行性判据与产物级判定见
  `../../accuracy-gate/references/content-health-gate.md`「载重件的 off-identity 会反转」。

## 去冗余判据（结构上值得做的四类）

1. **同一激活被多个目标模块重复读** ⇒ 收成一次读（或按生产者融合让激活不落地）；
2. **打包权重上的非连续列切片加回** ⇒ 会额外产生 `Slice` + `Add` + `ViewCopy` 三段中间往返；
   优先用**按行跨步累加**的单 kernel 写法消除。**注意两点**：① 站点级微基准可以做到**逐字节精确**，
   但这**不保证在端到端兑现**——换并行度 / 形状后该链路的调用计数与绝对占比都会变，
   必须回端到端同窗 A/B，且**产物 md5 门必须过**（站点级无损 ≠ 管线内无损）；
3. **小 GEMM 与元素级算子交替**（Add / 量化夹在中间）⇒ **先数算子实例**（`Δcount`），再谈融合；
   算子数不减的"融合"不会拿到 host 侧那部分差额；
4. **多模块共享同一投影** ⇒ 收缩为一次计算（此类通常可做到逐位，`torch.equal` 可证）。

## 判定要点

- **环境作用域（强制）**：本文件的比值门限（`≥ 2×`、"1.3–1.4 倍"、"一个数量级"）来源是
  **一次「硬件 + 拓扑 + 软件栈 + 模型」组合的快照**，不是普适事实。换任一维度后**必须本地重测**
  三档再归因；套用任何历史结论前先按本节流程复算 `Δwall / Δdev / Δcount`。
- **方向每次都按最新实测重判**：历史 Round 里的"该链贵 / 已被证伪"只作参照，不得替代本任务复测。
- **`Δwall` 的"收益"只有在过门禁后才是收益**：该链去掉后产物若塌陷（载重件），
  B 档的读数只是**归因工具**，不是可交付档（同 `content-health-gate.md`）。
