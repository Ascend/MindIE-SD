## 0. ⚠️ 适用范围：数字与结论**硬绑定到具体硬件/拓扑/软件栈**

来源环境：**一次特定的「硬件 + 拓扑 + 软件栈 + 模型」组合** —— 设备型号/代际、核数、UB 容量、
卡数与拓扑、各软件栈版本、模型几何与每 rank 形状的**具体取值一律见案例归档**
（`{run_results_dir}/archive/`）；需要现场核对时用 `npu-smi info -t topo` / `npu-smi info -t memory`
与设备属性、算子 UT 取数，**不要照抄归档里的常量**。

**换任何一项，本文档的判断都可能翻转。** 特别地：

- **§5.1 的硬约束要重新确认**（grid 上限、core 数、UB 容量）——
  `multibuffer` 默认值、`num_warps` 语义、`tl.where` 的退化行为**都是该版本的表现，换版本必须重跑**；
- **§2 / §5.3 的性能与收益数字不可移植**（随拓扑、并发、机器负载变化）；
- **§4 的噪声地板与可分辨性判据是该模型/该任务类型的属性**，不可跨任务类型迁移；
- **§7 已证伪清单在新环境值得各复测一次** —— 证伪结论也可能只在原形状/原版本下成立
  （例如"整行归约压 UB 上限"就与 UB 容量强相关）。

### 0.1 默认动作：**枚举多个方案、逐一实测、择优使用**

**不要照抄本文档的参数值**（BLOCK_S、tile 形状、DSL 选择、是否融某个算子…）。默认流程：

1. **先算上界**（§1.1 组合理想式）筛掉明显不值的；
2. **列出候选（≥2）**，含本文档证伪的那些；
3. **逐一实测**，用统一口径 + 交错对照；
4. **先比正确性，再比性能** —— **最快但数值错的配置必须淘汰**
   （实践中出现过：`BM=2/BN=2688` **最快却数值错**，是"很容易误采纳的改动"）；
5. **留下两侧读数**，形成本环境自有基线；
6. 只有**在本环境复测过**的结论才写进交付。

> 一句话：**本文档给的是"方法与候选集"，不是"参数答案"。**

### 0.2 结论也有寿命：**不固化为永久事实**

**本版本需要绕行的问题，下个版本可能已经是正常功能。**
这比"数字过时"更危险 —— "**X 已被证伪 / 必须绕行 X**"这类结论会**阻止 agent 使用已经修好的原生路径**。

本文档中**最易过期**的是：

| 条目 | 为何易过期 |
|---|---|
| §5.2 的编译器/bits 行为（cast 被静默消除、`tl.where` 退化、常量除数被强度削减、`multibuffer` 默认值） | 多为**该版本 triton-ascend / CANN 的保守实现或缺陷**，一次升级就可能改变 |
| §7 已证伪清单 | 其中多项是"**在这个后端上 X 不行**"，属于**工具链能力**判断而非数学结论 |
| §6 的实验机制陷阱（pkill 误匹配、md5 误读） | 属**当时的脚本/流程**问题，换了驱动脚本就不再适用 |

**强制义务**（与 `../../dit-parallel-opt/references/ascend-parallel-traps.md` §0 一致）：

1. 每条结论须写清"**如何判定它仍成立**"（一条命令 / 一个最小复现）；
2. **升级软件栈后逐条复核，不再复现的必须删除**，不要留"以防万一"；
3. **优先记录判定方法而非绕行方案** —— 判定方法在版本变更后仍有用，绕行方案会作废；
4. 绕行必须走**可一键关闭、可整体删除**的开关，**不要固化成结构**（不长期分裂路径、不写兼容 shim）；
5. **§7 是"优先复测清单"，不是"禁止清单"** —— 换环境/换版本至少复测一次。

> 一句话：**记录"怎么发现"，而不是"必须怎么做"。**

## 1. 三条决策判据（按顺序过，先算再写）

### 1.1 组合理想式 —— 必做，但只作前置筛

```text
fused_ideal = 半A + 半B − 共享I/O
实测输入（只留结构，绝对 µs 见归档 `{run_results_dir}/archive/`）：
          半A = RMSNorm 多行（含一份 bf16 写）
          半B = group-32 量化器（含一份 bf16 读）
          共享 I/O：两半各含一份**同量级**的 bf16 读写
→ fused_ideal = 半A + 半B − 共享I/O < 未融合对  ⇒ 预测**小幅赢**
→ 实测最佳融合核反而**输**（性能比约为未融合对的四分之三）
```

**价值在于把问题从"能不能快"变成"差在哪里"**：真正的待攻目标是**"为什么实测比自身两半的组合还差一截"**（差额量级为数百 µs 的一小部分，具体见归档）。主假设：full-row variance 逼出一个 one-shot 融合核无法表达的**两趟**结构（要证伪它，得先把两趟结构建出来做对照 —— 该假设**尚未验证**）。

### 1.2 部件不可加 —— 必须实测组合

两部件单独计时**合计小于**合并后的实测读数 → **负交互**（差额只有数十 µs 量级，符号却是反的）。**不要用单点收益外推组合收益。**

### 1.3 噪声地板先行 —— 在写内核之前决定"值不值得写"

见 §3。**预测效应低于噪声地板的项，直接关项。**

## 5. 内核编写期的 Ascend 硬约束与陷阱

### 5.1 硬约束与默认值（写内核前核对）

| 约束 | 值 | 后果 / 说明 |
|---|---|---|
| **AIV grid / coreDim 上限** | **从设备属性 / 算子 UT 现场取** | 超出报 `EE1003`。**小规模会静默通过**（未分片行数未超上限时） |
| **vector core 数** | **从设备属性现场取** | 用于 wave 估算 |
| **UB 容量** | **从设备属性现场取** | 见下方"UB 临界" |
| `num_warps` | triton-ascend 上 **no-op** | NPU 无 warp，调它毫无效果 |
| `multibuffer` | **默认值随芯片代际/软件版本变**（本组合的取值见归档）⇒ 以设备属性 + 真机 A/B 实测为准 | **仅当存在可流水化的循环时才有用**：RMSNorm 上必需（**约 1.3 倍**）；无循环的 kernel 上是 **no-op**。**判据**：先在本环境 dump 编译产物或跑一次开关 A/B 确认默认值，再决定是否显式开启 |
| **一 program 一行** | **反模式** | grid 直接映射物理核（核数现场取），多余部分**串行**：`programs ÷ 物理核数` = 串行 wave 数（每 wave 数 µs 量级 ⇒ 累计数百 µs；本组合读数见归档）→ **延迟被完全暴露，未被 ILP 隐藏** |

**UB 临界的两种命运（对照解释成败）**：

| | (a) RMSNorm+MX 融合 | 自研融合转置量化器 |
|---|---|---|
| tile | 行宽 × 4 B（fp32）**现场换算**：单行字节数已 ≈ 现场取到的 UB 容量（**压在 UB 上限**） | tile 字节数**现场换算**：约 UB 容量的四分之一 |
| grid | `programs ÷ 物理核数` = **大量串行 wave**（现场换算） | 同公式，wave 数小得多（读数见归档） |
| 归约 | **整行**，跨 program | 小、寄存器内 |
| 结果 | **输**（性能比约四分之三） | **赢**（性能比约一半，即约 2 倍加速） |

### 5.2 内核级陷阱（都有实测数字）

1. **`clamp` 可能是最大向量成本，且常可证冗余**：去掉 `min/max` clamp → **耗时降约三分之一**；每 tile 一次 reciprocal → **再省一个更小的固定项**。`scale = amax/127` 使 `|x/scale| ≤ 127` **按构造成立**，故 clamp 冗余。
2. **⚠️ 统一 int8 转换是 wrap-around，不是 saturation**：强制 `inv=1e5` 得到 **256 个分布大致均匀的输出值**（峰值 358–378 k），这是**回绕签名**。**因此去掉 clamp 只在"归一化保证了范围"时才安全** —— 任何破坏该不变式的后续改动会产生**静默回绕垃圾**，而不是饱和值。
3. **⚠️ 常量除数会被强度削减成 reciprocal 乘法**（约 2 ulp 偏差）：**divisor 必须"载入"而非在 kernel 内计算**，否则**静默污染千分之一以下的 payload 字节**；改为载入后**完全匹配**。
4. **⚠️ 看起来最快的配置可能是错的**：`BM=2/BN=2688` 数值**错误（匹配率不足 100%）却最快** —— "一个很容易误采纳的改动"。**性能与精度必须同时核对**（绝对值见归档）。
5. **"它编译了"和"scale 是对的"都不是正确性证据**：double-`tl.reshape` 形式**编译通过**，payload **接近但不等于 100%**、scale **完全匹配**。
6. **`tl.where` 整数比较会退化为标量循环**。**精确归因**（见 §6.2）：致命构造是"**其结果喂给 shift+bitcast 的 `tl.where(reduced_bool, int_a, int_b)`**"，**不是**寄存器内广播。用 `tl.minimum` 做 guard（无 `tl.where`）即可编译。
7. **整 tile 上 `split + maximum` 比 `vreduce` 贵得多**：**约 4 倍损失**（已测、已证伪；绝对值见归档）。

### 5.3 自研融合转置量化器实测

**链路成本**（生产形状 **(1,S,14,128)/rank** —— 注意**不是**全局 56 head；下表以 `clone()` 纯拷贝为基准，绝对 µs 见归档）：

| op | 5s（S=37 736） | 15s（S=109 088） |
|---|---|---|
| `clone()` 纯拷贝带宽参考 | **1 倍（基准）** | **1 倍（基准）** |
| `transpose(1,2).contiguous()` ×3 | **约 3 倍** | **约 3 倍** |
| `_perblock_quant` | **约 2 倍** | **约 2 倍** |
| **→ 链路合计** | **约 3 倍** | **约 3 倍** |

**BLOCK_S 扫描**（strided BSND 读 → full-tile amax → BNSD int8 存 + 每 (head, block) 一个 scale；比值 = 相对同档链路合计）：

| BLOCK_S | vs 链路合计 @5s | vs 链路合计 @15s |
|---|---|---|
| 64 | **约 0.7 倍** | **约 0.7 倍** |
| 128 | **约 0.6 倍** | **约 0.6 倍** |
| **256** | **约 0.5 倍（最优）** | **约 0.5 倍（最优）** |

**整 tile 单循环（recip + no-clamp）**：

| | 5s（卡 A） | 15s（卡 B） | 15s（卡 A） |
|---|---|---|---|
| base（div + clamp） | **基准 1 倍** | **基准 1 倍** | **基准 1 倍** |
| **recip + no-clamp** | **约 0.68 倍** | **约 0.68 倍** | **约 0.67 倍** |
| ⇒ 结论 | **省约三分之一** | **省约三分之一** | **省约三分之一** |

**跨卡一致（两卡比值只差千分之几）**。对链路：**5s / 15s 均约 2.7–2.9 倍**（保留 clamp 只有约 2 倍 ⇒ **clamp 占 kernel 的三分之一**）。
**正确性**：**逐字节零差异**（5s / 15s 两种形状下 int8 字节与 scale **均为 0 差异**；对拍规模见归档），覆盖 randn / uniform[-1,1] / all-equal-7，**两张卡**。**"丢掉 clamp 与保留它逐位相同。"**

**尾块收益被低估**：`PadV3` + `Slice` **占链路四成**，它们**只**为处理尾块而存在（`37 736 % 64 = 40`）。融合核的 masked load 原生处理尾块 ⇒ **两个 kernel 整块消失**。
**管道级解释**：链路是 **DRAM 饱和**（有效带宽已到该机器上限量级）；融合核是**计算约束**（有效带宽只用掉约五分之一）。**"把 DRAM 饱和的 4-pass 序列换成向量约束的 1-pass kernel"** —— 这是它能传导的机制性理由。

> ⚠️ **同一内核有两组口径不同、数字不一致的读数，且差异来源未记录**：
> 一组为「BLOCK_S=256 + 64 行子循环」：**约 2.5 倍，字节差异极小但非零（未字节精确）**；
> 另一组为「BLOCK_S=256 整 tile 单循环 + recip/no-clamp」：**约 2.7–2.9 倍，逐字节精确**。
> 引用时**必须连口径一起标注**，不要合并成一组"权威数字"（两组绝对值见归档）。

## 6. 实验机制本身是 bug 来源（**最容易被忽略的一类**）

6.1 **`pkill` 模式必须运行时拼装** —— 把模式**字面写在脚本里**（包括写在 `echo` 字符串里）会**匹配到自己的命令行**，实践中曾**两次杀掉自己的 shell**。

6.2 **一个错误的 `pkill` 模式可以伪造一整轮"数据"**：模式用**连续**匹配 `vllm-omni serve --host … --port …`，但真实命令行中间夹着模型路径与 `--omni` ⇒ 上一臂的 server 存活、下一臂死于 *Address already in use*，**每一臂都被同一个 OFF 进程静默服务**（md5 相同、全部计时来自一个配置）。**靠"请求数不对称"诊断出来**（OFF 日志 3 个请求却存了 8 个请求的计时）。修法：通配模式 + **硬性端口空闲检查** + **跑后自检**。

6.3 **跑后自检是让重跑可信的东西**：断言 `<stage> 行数 == 请求数 × rank 数`。

6.4 **逐字节相同的 md5 不是"模式没生效"，而正是逐字节精确优化所预测的结果** —— 实践中曾把它误读为失败信号。

6.5 **形状必须按 rank 核对**：`(1,S,56,128)` 是**全局**形状，生产每 rank 是 **`(1,S,14,128)`**（heads/world_size）⇒ **按 56 建 A/B 会偏 ~7×**。同理"调制 kernel 是 37 760 行"是错的（那是 all-to-all **之后**的 attention 形状；DiT block 跑在**序列分片**的 hidden state 上，**≈9 434 行**）。

6.6 **必须 warmup**：Triton JIT 落在第一个 ON 请求上（**首个请求被编译污染、单次达秒级**）⇒ 会伪造出"回退"，也会伪造出假收益。

6.7 **不做无法表达的消融**：若某实验会破坏 AIC↔AIV 同步握手（去掉 payload store → **可复现 fault `507015`**），就承认它**不可测**，而不是把结果当归因。

## 7. 已证伪清单（**不要重复**）

> 条目沿用 §2 的 `(a)/(b)/(c)/(d)/sparse` 简写（**以 §2「改动」列为准**，简写仅作指代）：
> (a) RMSNorm 调制族 · (b) V 量化 / 转置链 · (c) 门控调制变体 · (d) FFN 融合 · sparse 稀疏池化。
> **本清单是「优先复测清单」，不是永久禁令**（见 §0.2）：换环境 / 换版本至少复测一次。

| # | 假设 | 证伪它的实测 |
|---|---|---|
| 1 | (a)：fp8 store 是瓶颈 | A4（payload 存 bf16）与 A7（去掉 store）的读数都**落在噪声内** ⇒ **fp8 cast 与 store 免费**；真成本是**归约及其 scale-byte epilogue**（占该核的主要部分） |
| 2 | (a)：用 `tl.split`+`tl.maximum` 替代每次归约 | **约 4 倍损失**（绝对值见归档） |
| 3 | (a) 两半可独立看待 ⇒ 量化器需 **数倍**改进 | **错**：两半**共享一块 I/O**；真问题是"实测为何比自身组合还差一截"（差额见 §1.2） |
| 4 | (b)：perchannel 限制是 16 位溢出，边界在 (57 344, 65 536) | 精细扫描定在 **(61 184, 61 440]**；跨 `N/D/B` 全部**同一 S** fault；"总元素数上限"假设被算术证伪 ⇒ **切 head 轴完全无用** |
| 5 | (d)：存在小 M 正确性缺陷 | **无缺陷**：数亿个对拍值 min **接近 1（偏差 1e-4 量级）**；恒等式 max\|(kernel vs chain) − (ref vs chain)\| **≈ 0** ⇒ 旧数字是 **harness bug**；该 op **比链路更精确** |
| 6 | (d)：epilogue 是 headroom | `nocmp` **约 1.03 倍** ⇒ epilogue 只值**个位数百分比**；**即便 epilogue 完全免费，仍有个位数百分比的差额存在** |
| 7 | (d)：折叠两次 mmad 可提收益 | 消除 NaN 却换来 **aicore timeout `507014`**（一次 mmad 改变每轮 flag 计数 → AIC↔AIV 死锁）；收益有界在**约 1.0 倍（无收益）** vs 易死锁返工 ⇒ **不值得采用** |
| 8 | (d)：权重缓存指纹需收紧 | 陈旧性**真实**，但**修复没改变任何可测的东西**（md5 相同）；且收益上限**远低于噪声地板** ⇒ 关项 |
| 9 | (c)：T2 = 寄存器内广播 reduced 值无法编译 | V0/V2/V3 都编译且 **100% 相符**；广播在所有版本里都存在且相同 ⇒ 真凶是 **`tl.where` 喂给指数 bitcast**。**两个 agent 曾花时间绕过不是问题的构造** |
| 10 | (c)：修好 T2 就能救回性能 | 修复后耗时仍**约为 CANN 原生算子的 5 倍** ⇒ **是 reduction 调用次数**，不是 T2 |
| 11 | (b)：给 op 传 BSND 即可省掉三份 transpose | op **硬拒**（`TORCH_CHECK(q_input_layout == "TND" \|\| == "BNSD")`）⇒ **"一行修复"不存在** |
| 12 | (b)/稀疏：拆三个转置可靠库捷径 | **五个捷径全部逐字节精确但只省几十 µs 量级，而非预期的数百 µs** ⇒ **转置 view 是被计价的，不是被吸收的** |
| 13 | 稀疏：`rain_fusion_attention_v3` permute 链 / fp8 Hadamard 路径是候选 | 运行时 monkeypatch trace：**进入 0 次**，是**死代码** |
| 14 | 稀疏：`(1,S,56,128)` 是做 A/B 的形状 | 那是**全局**形状；生产每 rank `(1,S,14,128)` ⇒ 偏 ~7× |
| 15 | 稀疏：没有尾块路径在跑 | **实测是错的**：`37 736 % 128 = 104`、`109 088 % 128 = 32` ⇒ **每次调用都走尾分支** |
| 16 | 稀疏 kernel 占 DiT 的 61%→87% | **DiT 全宽实测 15s 是约三成**；61→87% 是稀疏模块**内部**占比 ⇒ **据此做的 Amdahl 论证偏强** |
| 17 | (a)：单测通过即收益已确立 | `_grouped_pool`：单测 **max\|diff\| = 0.0**（与 `avgpool` 逐元素相同）却 e2e **几乎翻倍** ⇒ **想法被证伪**（绝对值见归档） |
| 18 | (b)：站点每次省 ms 量级 ⇒ 外推 e2e 应省数百 ms | 实测稳态**明显小于外推值**（约七成） ⇒ 流水线内每次调用节省更小（**可能是两 kernel 路径的额外 launch 开销**） |
| 19 | 站点外推可解释 e2e 收益 | (d) **低估约 3 倍**、(b) **高估约 1.5 倍**、(a1) **高估到不可分辨** ⇒ **两个方向都会错** |

**共性教训**：**静态阅读不可信，运行时 trace 才算数**（逐行阅读"有一半是错的"）；**死代码必须由运行时证据排除**，否则会资助不存在的东西。

## 8. 错误码台账（常见错误码与成因）

| 错误码 | 含义 | 成因 |
|---|---|---|
| **EE1003** | `coreDim` 超**设备上限**（数值现场取：设备属性 / 算子 UT） | 未分片 → `coreDim` = 该张量行数 |
| **507035** | `perchannel` V 量化 fault | plog 指名 **`reduce_max_apt/ReduceMax_bfloat16_int64_high_performance.o`** |
| **507014** | **aicore timeout** | mmad 折叠改变每轮 flag 计数 → AIC↔AIV 节奏死锁 |
| **507015** | 同步握手 fault | 去掉 payload store（握手与 epilogue store 配对） |
| 161002 | 权重布局错误 | **`aclnnQuantMatmulV5`**：需 `[K,N]`/`[C_K/2,N,2]`，误用 `[N,K]`/`[N,c,2]`。⚠️ **与 `aclnnCat` 无关** |

**`w` 与 `w_scale` 必须同序置换** —— 只换 `w` 不换 `w_scale`，结果**静默塌到接近 0**。

## 9. 工程集成事实（第二个 DSO / profiler）

- **第二个 DSO 不能用 `TORCH_LIBRARY(mindiesd, m)`**（PyTorch 会 abort："Only a single TORCH_LIBRARY … consider using TORCH_LIBRARY_FRAGMENT"），必须 **`TORCH_LIBRARY_FRAGMENT` + `TORCH_LIBRARY_IMPL`**。
- **`dir(torch.ops.mindiesd)` 是缓存的**，列不出后加载的 op → 用 `hasattr` + **`torch._C._dispatch_get_all_op_names()`**。
- **`msprof --pid` 在容器内常不可用**（对平凡的 NPU-busy 进程也报 "no valid pid values"）⇒ 动态 attach 是死路。
- **`torch_npu.profiler` 的 `tensorboard_trace_handler` 在某些配置下不会自动解析**；需显式：
  `from torch_npu.profiler.profiler import analyse; analyse(profiler_path, max_process_number=128, export_type=None)`
  产出 `ASCEND_PROFILER_OUTPUT/{kernel_details,op_statistic,api_statistic,task_time,step_trace_time}.csv`。**没有这一步就只有原始 `PROF_*/`**，拿不到可读的统计表。
- **原始数据可复用**：`PROF_*` 带 `end_info.done` 后，离线 `analyse()` 只需 **~4 s**；提前 kill server 无代价。
- **增量 DSO + `torch.ops.load_library`** 是"不改共享库"的落地方式（共享库 **UNTOUCHED**）。
