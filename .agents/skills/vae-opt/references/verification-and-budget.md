# 交换预算、验证闸与健康指标

分片的价值 = “省下的时间/显存” − “交换与实现代价”。本文件给出可套用的算式、四道验证闸的判据，以及同环境实测的量级（**绝对数字按数字纪律出库**，见 `{run_results_dir}/archive/`）。

> **作用域（强制）**：文中所有耗时 / 显存 / 字节数 / 阈值 / 占比都是**一次观测**，来源环境为 Ascend 950PR
> 8 卡 · CANN 25.7.rc1.6 · torch_npu · 容器内 vLLM-Omni 0.28 + MindIE-SD，口径为 15 s / 768P。
> 换硬件 / 版本 / 形状 / 步数即须重测，**算式与判据可迁移，数字不可照抄**。

## 1. 交换预算（先算再实现）

```text
交换量   = 输出张量字节数 × (pieces-1)/pieces × (1 - 可压缩比)
交换耗时 ≈ 交换量 / 有效链路带宽          # 8 卡同岛 UB 与跨岛 SYS 差一个量级，按最差算
可接受  ⇔ 交换耗时 < 切分省下的计算时间
```

同环境实测的量级（15 s / 768P 视频解码；绝对值见归档 `{run_results_dir}/archive/`）：

| 方案 | 交换量/卡 | 结论 |
|---|---|---|
| 空间分块后 all-gather **fp32** 视频 `(1,3,362,768,1344)` | **数 GB 量级** | **不可接受**（解码本身只有亚秒级） |
| 同上但按 **uint8** 交换（输出已 clamp 到 [0,1]） | **降到约其四分之一** | 可谈，需实测链路带宽 |
| 不交换：按 tile 直接写进编码器/落盘 | 0（仅 halo） | 最优方向（未实现，属待办） |
| 帧轴/状态携带切分（同环境采用） | 0 | 无需交换，代价是段间顺序执行 |

判别要点：**先看解码本身的绝对耗时**。若它只占 e2e 的个位数百分比，任何“需要交换”的方案都要先过上面这笔账。

## 2. 四道验证闸

### 闸① CPU 等价性（实现完立刻做，别上卡）

```bash
python scripts/shard_equivalence_check.py --model-spec my_decoder:build --axis time --pieces 2 4
```

合格：**max|d| = 0**（整段 vs 每档段数）。不为 0 的常见原因：

1. `state` 存的是块**输出**而非块**输入**；
2. `state` 未 clone / 跨段 dtype 未对齐；
3. 切分点没落在潜帧边界（半帧位置）；
4. 首段没复现 zeros pad 语义（例如用了 `view[:, -1:]` 当首段 mem）。

### 闸② 端到端产物（同窗口 4 请求：1 冷 + 3 热）

合格判据：

- 4/4 请求 **md5 一致**（同配置内确定性）；
- 开/关分片的产物：**无损分片应逐字节一致**；若分片带来“换了解码器/换精度”，md5 会变，此时必须另做闸③的真值对照，**不能**用 md5 一致当无损证明。

⚠️ 实测中踩过的坑：**md5 一致只证明“优化没改变本链产物”，不证明解码器忠实**——基线自己也可能用了劣质解码器（实际发生过：全血缘基线都在用“预览版”解码器，逐字节一致掩盖了画质问题）。

### 闸③ 帧级/张量级健康指标（定位“从第几帧开始坏”）

三个指标，桶化（每 24 帧一桶）后看趋势：

| 指标 | 定义 | 异常特征 |
|---|---|---|
| `hf`（高频能量） | 相邻像素差的均值 `mean(\|Δx\|)+mean(\|Δy\|)` | 后半段**塌陷**：实测坏片后半段各桶 hf 明显低于正常档（正常档应回到健康量级；读数见归档 `{run_results_dir}/archive/`） |
| `d_prev`（帧间差） | `mean\|frame_t − frame_{t−1}\|` | 反复尖峰（频闪/冻结）、或长串 <0.5（冻结帧）；实测 2-D 预览含 **数十段**冻结帧 |
| 近重复段 | `d_prev < 0.5` 的连续段计数 | 健康解码应为 0 段 |

辅助：单帧 PNG 体积可快速判别“平坦帧”——实测坏帧 1344×768 PNG 体积只有健康帧的几十分之一。

工具：`scripts/frame_health.py`（支持 `.npy/.pt` 张量与 `.mp4`）。

### 闸④ 预算与代价复核

记录并对比：解码耗时、**峰值显存**、交换量、端到端 e2e。同环境状态携带切分：耗时降到约四成、峰值显存约减半（既快又省），端到端 `decode` 阶段耗时**同等**（说明该优化在整请求里是“零成本换正确性”）；绝对数字见归档 `{run_results_dir}/archive/`。

## 3. 有损/条件性分片：必须写清前置条件

分片只有在特定长度/形状下才逐字节精确时，实现里必须同时有：**前置条件判定 → 自动修复 → 回退整段**。

同环境实测案例（音频 VAE 时间维分片）：

| 项 | 数值 |
|---|---|
| 精确性前置条件 | 片长 `T//2 + halo ≥ 359` 潜帧 ⇔ **T ≥ 590（≈14.75 s 音频）** |
| 不满足时 | T=500 档实测**绝大多数样本不逐字节相等**（相对偏差极小，读数见归档） |
| 修复 | 加 `MINLEN=359`：短片补零至 ≥359 帧后 **ndiff = 0** |
| 片数扩展否证 | 扩到 8 片**不逐字节精确**（同一实现仅改片数）⇒ 片数由等价性判据决定，不由“卡多”决定 |

## 4. 把“切分绕过设备缺陷”写进验证

若分片的动机是绕开设备算子缺陷，验证要额外包含**缺陷本身的判定实验**（否则无法区分“切分治愈了缺陷”与“缺陷本来就不出现”）。

判定实验的模板、判读规则、规避手段与回退条件**单点在本技能** `troubleshooting-cann-upsample.md`
（§2 判定实验 / §3 规避手段 / §4 修复与回退），**本文件不重复**，只要求：闸④ 的复核记录里必须包含
“缺陷仍存在”或“已被修复”的结论与它的判据（形状 + dtype + 干净/坏档 + 首坏索引，阈值只写区间），
并按该文件 §4 的回退条件决定分段是否继续保留。

> 同环境实测读数（阈值点值、首坏帧号、跨运行相关性等）属会话产物，换版本 / 形状即失效，按数字纪律
> 不入库；需要时从会话产物目录取（`{run_results_dir}/`，如 `{run_results_dir}/CANN_UPSAMPLE_BUG.md`）。

## 5. 报告模板（写进交付物）

```json
[分片等价性]
轴/段数: <轴> / <pieces>，切分点: <潜帧边界/空间块>，halo/state: <无 / 宽度 / state 定义>
闸① CPU: 整段 vs 2 段 vs 4 段 max|d| = <0 / 值>
闸② 端到端: 4/4 md5 <一致/不一致>；开-关产物 <逐字节一致 / 变化(原因)>
闸③ 健康: 桶化 hf <前后段对比>；近重复段 <段数>；异常起点 <第 N 帧 / 无>
闸④ 代价: 解码 <ms>，峰值显存 <GiB>，交换 <GB>，e2e <s>（相对整段 <快/持平/慢>）
前置条件与回退: <条件 / MINLEN 类修复 / env 回退开关>
```
